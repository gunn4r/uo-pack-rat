# Contributing to Pack Rat

How to work on Pack Rat. Clone the repository (`git clone https://github.com/gunn4r/uo-pack-rat.git`), then `npm ci`. Start the bare server with `npm start -- --open`; tests with `npm test`. See `docs/architecture.md` for how the Electron shell (`electron/`), the inbox watcher (`app/watcher.mts`) and the installer (`app/installer.mts`) fit around the server described below.

New tests need a tag (`[smoke]`, `[fast]`, or `[slow]`) prefixed on the test's own name — see `TESTING.md` for what each tag means and how the runner uses them.

Cutting a release follows the checklist in `RELEASING.md`. Everyone participating is expected to follow `CODE_OF_CONDUCT.md`. `docs/threat-model.md` is what the Security section below is short for — who the app defends against, what each boundary is holding, and which findings were left standing on purpose; `SECURITY.md` is how to report one.

## Contracts

The scan file, the bridge protocol, and shard rules are the app's external contracts — anything reading or writing them (an adapter, a shard's rules file, a future client) needs to match these documents, not this file's prose:

- `docs/scan-schema.md` — every scan field, the v1→v2 upgrade, and the fold rules.
- `docs/bridge-protocol.md` — the queue/status files, command/result/status shapes, actions, and safety rules (the offset rule, the wrong-character confirm, local-only messaging).
- `docs/shard-rules.md` — every key in a shard's rules file, and how to add or override one without touching the app.
- `docs/adapter-guide.md` — what a new adapter must ship, the transports, which shards an adapter must never target, and the attended-only statement.

## Dependencies

No new runtime dependencies without a spec change. `highs` (MIT, compiled to WebAssembly) is the one: `app/mip-solve.mts` loads it to run the exact suit solve (`docs/solver.md`), and `optimize-worker.mts` falls back to the core's own heuristic when it fails to load. Everything else — the server, the page, the adapters — is Node's standard library and plain browser APIs, no npm imports.

## Working in TypeScript

Every source and test file the project ships is TypeScript (`.mts`), and a module imports another by its real extension (`import { x } from "./y.mts"`, not `./y.mjs` or extensionless) — `verbatimModuleSyntax` plus `rewriteRelativeImportExtensions` handle rewriting that to the compiled extension wherever a compile step is actually involved. Node (the `engines.node` floor, 22.18) and Electron run `.mts` files directly through native TypeScript type stripping, so there is **no build step** for the server, the tests, the worker threads, or the Electron main/utility processes — edit a file and rerun it. Type stripping only erases type syntax, it doesn't transform anything, so `tsconfig.json` sets `erasableSyntaxOnly`: no `enum`, no `namespace`, no parameter properties. The compiler refuses any of those at typecheck time, since they'd otherwise fail at run time the moment Node actually strips and runs the file.

The **one** compile step anywhere in the project is the page, because a browser can't strip types itself: `npm run build:ui` (`scripts/build-ui.mts`, `tsc -p tsconfig.browser.json`) turns `app/ui/**` and the shared modules it imports into `app/dist/`. The `pre*` npm hooks, `scripts/start.mts`, `scripts/test-runner.mts`, `app/server.test.mts`, and (in development) `electron/main.mts` all call it for you — see Run / dev loop above for exactly when you need to trigger it by hand.

`npm run typecheck` (`tsc -p tsconfig.json`, no emit) is what CI enforces on macOS, Windows and Linux, and it checks the whole project, build step or not.

`app/schema/types.d.mts` is **generated** from the four JSON Schema files by `npm run build:types` (`scripts/build-schema-types.mts`, see Run / dev loop above). The schemas remain the authority — a shape change is made there, never by hand-editing the generated file, which is git-ignored and simply overwritten on the next build.

A type describes a shape; it proves nothing about data that crossed a boundary the compiler never watched. Anything read from a scan file, a pasted document, an adapter, or an HTTP request body starts as `unknown` and stays that way until a runtime check has actually run against it — a document only earns the `ScanV2` type once `validateScan()` has passed, the way `app/import.mts` and `app/watcher.mts` do it (and the way `scripts/make-adapter-fixture.mts` learned to do it too, after shipping without the check — see `CHANGELOG.md`). Runtime validation is never deleted just because a type now describes the same shape it checks; the type and the check are two different guarantees, and only one of them runs against real data.

## The scrub guard

This repository is public. `scripts/scrub.test.mts` (`[smoke]`, so it runs even in `npm run test:smoke`) fails the whole suite if any tracked file carries the maintainer's name or machine, the private workspace this project grew out of, a real in-game character name, the project's retired product name, or a `/Users/<real name>` home path outside the `/Users/example` placeholder. Each pattern's exact allow-list — the handful of files deliberately permitted to carry the maintainer's public GitHub handle, such as `package.json`'s `author` field or the repository URL in `README.md` — lives in `scripts/scrub.test.mts` itself, next to the reason it's there.

If it fires on something you wrote: reword the offending line so the information isn't there — a real name becomes "the maintainer," a real path becomes `/Users/example` or `~/…`, a real character name becomes one of the fixture names the test suite already uses (`Dorran`, `Kestrel`, `Rowan`, `Sable`). **Never edit the guard's patterns or allow-lists to make a failure go away** — if you genuinely believe a new file needs a new allowance (a new place the maintainer's handle legitimately has to appear, for instance), say so in your PR description and let a maintainer decide; don't add yourself to the allow-list to get a red test green.

## Run / dev loop

- Start: `npm start -- --open` (serves the app on the configured port and opens the browser). `npm start -- --demo` serves the bundled fixtures in `app/fixtures/` instead of your own scans. `npm start -- --data <dir>` points at a different data directory (default `~/.pack-rat`, or the `PACKRAT_DATA` environment variable); `--port <n>` picks a different port (default 8765, or `PACKRAT_PORT`, `0` for an OS-assigned port); `--token <t>` (or `PACKRAT_TOKEN`) requires `Authorization: Bearer <t>` on every `/api/*` request — see Security below; the bare page carries no token, so `--token` is for testing the header, not for daily local use. Restart the server whenever you change `vault-server.mts` or the optimizer core — both are loaded once at startup.
- **Bare server vs. the desktop shell.** Most feature work only needs the bare server — it's `startServer()` either way, same routes, same page. Reach for `npm run desktop` (runs `electron .`, which loads `electron/main.mts`) only when the change is actually in `electron/` itself, or you need to exercise something the bare server can't do on its own: the native folder picker / Finder integration behind `POST /api/host/*` (501 without an embedder), the per-launch bearer token attached out-of-band (see Security below), or the utility-process/single-instance/restart-once lifecycle. `npm run desktop -- --demo` and `--data <dir>` work the same as `npm start`'s. Electron main-process changes need a full relaunch to pick up (no hot reload); the page inside the window reloads the same way it does under the bare server. `docs/architecture.md` has the process diagram and the token/host-bridge writeups.
- **The inbox watcher.** Dropping a `*.json` file into `<data>/inbox/tazuo/` (by hand, or via a real adapter script) gets picked up within its 300 ms debounce and normalised into `<data>/scans/` — useful for exercising the watcher/import path without a live game client. `--demo` starts no watcher (its `scans/` is the committed `app/fixtures/`, which must never be written to), so watcher work needs a non-demo run.
- **The installer's running-script guard.** `POST /api/setup/install` refuses with 409 (`RUNNING_MESSAGE` in `app/installer.mts`) when `<data>/bridge/<adapter>/status.json` — the adapter actually being INSTALLED, from the request body, not necessarily the currently-configured client — looks like a Legion script is still alive in the client (an `alive` timestamp inside the last 30 s, not `stopped: true`) — this is the same "orphaned script thread" trap the TazUO adapter's README warns about, guarding against overwriting a script file mid-run. Testing the install path against a real `LegionScripts/` folder: make sure nothing is running in the client first (or write a `status.json` with `stopped: true` / an old `alive` timestamp into a scratch data dir), or the 409 is expected behaviour, not a bug.
- **Browser gates in the window.** `electron/main.mts`'s `BrowserWindow` refuses to navigate anywhere but the local server's own origin (`will-navigate`) and sends anything the page tries to open in a new window/tab (`target=_blank`, `window.open`) to the OS browser instead of a second Electron window, and only for `http(s)://` links (`setWindowOpenHandler`). A link to an external site (e.g. a GitHub URL in a future changelog view) is expected to open in the player's regular browser, never inside the app's own window — that's this gate working as designed, not a bug to route around.
- `npm run build:types` (`scripts/build-schema-types.mts`) derives `app/schema/types.d.mts` from the four JSON Schema files (`app/schema/scan.v2.schema.json`, `bridge.v1.schema.json`, `rules.v1.schema.json`, `profiles.v2.schema.json`) — `ScanV2`, `BridgeV1Command`/`Result`/`Status`, `RulesV1`, `ProfilesV2`, plus a named type for every nested object the schemas define. `app/schema/types.d.mts` is generated and **git-ignored**, the same as `app/dist/`; the JSON Schemas are the authority, and a shape change is made in the schema, never in the generated file (a hand-edit is simply overwritten on the next build). It's a hand-written, dependency-free generator — no JSON-Schema-to-TypeScript library — that understands exactly the keyword subset described in its own header comment and throws, naming the construct and where it appeared, on anything else, rather than silently emitting `any`. It's the first of the five `pre*` hooks (`tsconfig.browser.json` includes the generated file, so it must exist before `build:ui` type-checks the page), and `scripts/start.mts`, `scripts/test-runner.mts` and `app/server.test.mts` each call `buildSchemaTypes()` themselves ahead of `buildUi()`, the same pattern `build:ui` below uses. It only rewrites the file when the generated content actually changed, so it doesn't needlessly invalidate anything watching it.
- The optimizer core (`scripts/optimizer-core.mts`, a real ES module, kept paste-able: no imports/exports beyond the one export line) needs **no build step** — every caller (the server, both test harnesses, the bench) imports it straight from source, by the path `config.mts`'s `corePath()`/`paths.core` resolves, via Node's native `node:module` type stripping (no external compiler; requires the `engines.node` floor in `package.json`). `PACKRAT_CORE` (env var) overrides that path for every caller at once — point it at an alternate copy without touching `config.mts`. This holds in the packaged app too: `build.files` ships `scripts/optimizer-core.mts` as source (no `asarUnpack` entry needed for it — Electron's asar fs/module patches serve a dynamic `import()` of a `.mts` file straight out of `app.asar`, worker threads included, verified against a real `electron-builder --dir` tree).
- `npm run build:ui` (`scripts/build-ui.mts`) compiles everything the browser loads — all of `app/ui/**` (every module is TypeScript now) plus the shared modules it imports (`vault-lib.mts`, `item-query.mts`, `scan-schema.mts`, `schema/validate.mts`) — into `app/dist/` with `tsc -p tsconfig.browser.json`, rewriting each `./x.mts` import to `./x.mjs` on the way out. The server serves the page's modules from `app/dist/` and never from the source tree, because a browser cannot parse TypeScript; stylesheets still come from `app/ui/`, since `tsc` copies only what it compiles. The same `pre*` hooks run it, and `scripts/start.mts`, `scripts/test-runner.mts` and `app/server.test.mts` each call `buildUi()` themselves so that invoking them directly, with no npm hook, still serves a current page. It always recompiles — a cold build takes well under a second — and it throws with the compiler's output if the build fails, so a broken page is never served silently. **A page-source edit therefore needs a rebuild before a browser reload picks it up** — `npm run build:ui` by hand, or restart `npm start`/`npm run desktop` (its `prestart`/`predesktop` hook runs it); a plain reload against a stale `app/dist/` just re-serves the old compiled page. `npm run typecheck` checks the whole project without emitting anything, and CI runs it on all three platforms.
- `app/vault-lib.mts` is hot: the server re-imports it whenever its mtime changes, and the page loads it fresh on every reload. Parser/fold/pool changes need only a browser reload.
- `app/index.html` is served as-is; `app/ui/*.mts` needs a `build:ui` rebuild first (see above), but `app/ui/styles.css` is served as-is straight from the source tree (the `/ui/<name>` allowlist route — see Files below) since `tsc` never touches it — a stylesheet edit only needs a reload. Restart the server only if you change `vault-server.mts`, `vault-lib.mts`'s import graph, or the optimizer core.
- Routes are hash routes, so a reload keeps your place: `#/inventory`, `#/characters`, `#/containers`, `#/builder/<Character>` (the builder's selected character rides in the address; switching character replaces the entry, switching tab adds one, so back/forward walk the tabs). Unknown hashes fall back to the inventory.
- Tests: `npm test` (full run, including the optimizer harness and brute-force checks of the exact search), `npm run test:smoke` / `npm run test:fast` for the quicker subsets, or `TEST_SKIP_SLOW=1 npm test` to run everything except the `[slow]` exhaustive-search proofs. Results land in `test_logs/latest_summary.json` — read that, not the console output. Everything runs on Node's built-in `node:test`; see `TESTING.md` for the full tag scheme and how the runner counts todo/skip. **To add a test:** write an ordinary `test("[smoke] what it checks", () => { ... })` (or `[fast]`/`[slow]`) in the matching `*.test.mts` file — the tag is a prefix on the test's own name, not a separate parameter, and an untagged test only runs in full mode. `[slow]` is for exact/budgeted-search proofs (`opts.exact` + a real `timeBudgetMs`); everything else is `[smoke]` (proves the pipeline is alive) or `[fast]` (cheap, no exact search). Tests that use the fixtures must sit below the `const kestrel = …` / `const dorran = …` lines (loaded from `app/fixtures/`) in `app/gear-vault.test.mts`.
- Verify visually with a browser automation tool if you have one available (navigate, then read/evaluate the page). One gotcha worth knowing regardless of tool: navigating to a URL that differs from the current one only by its hash is a hash navigation, not a reload, so the page keeps running the code it first loaded — after editing the page, navigate to a different query string (e.g. `/?r=2#/builder/Kestrel`) to force an actual reload.
- Read real data for checks against the running server with `curl http://localhost:8765/api/inventory` (adjust the port if you changed it).
- Embedding: `startServer(config)` (exported from `app/vault-server.mts`, `config` defaults to `ensureLayout(resolveConfig())`) starts a server with no side effects at import time and returns `{ server, port, url, close() }` — `close()` tears down every timer, SSE stream and worker so the process can exit cleanly. This is what `app/server.test.mts` uses to run isolated instances per test, and what a future desktop shell would call directly instead of shelling out to `node app/vault-server.mts`.

## Security

`docs/threat-model.md` is the reasoning behind everything in this section: the processes, each trust boundary, which defence is load-bearing against which attack, and the findings deliberately left standing. This section is the mechanics; read that one before changing any of them.

The bare `node app/vault-server.mts` / `npm start` path is loopback-only and runs with no token at all — this is the default. Only the **token** stays inert until an embedder opts in; the Host, Origin and content-type checks below are always on, which is what keeps every route closed to a web page even in this mode. What the missing token leaves open is another process on the same machine, which is out of scope for the same-user case but is **not** out of scope on a machine shared with other people: there, use the desktop app. The Electron shell (`electron/main.mts`) generates a per-launch token and sets it as `PACKRAT_TOKEN` in the server child's environment when it forks it (a developer can do the same thing by hand against the bare server with `--token <t>` or `PACKRAT_TOKEN`); `resolveConfig()` reads it into `config.token`, and `startServer()` prints `token: set` or `token: none (dev)` on start — it never prints the token itself, in a log or anywhere else. See `docs/architecture.md`'s "The token" section for how the shell then attaches it to every request without the page ever seeing it.

Every request goes through this order, before any route runs:

1. **Host.** The `Host` header must be exactly `127.0.0.1:<port>` or `localhost:<port>` — the port the server actually bound (read from `server.address().port`, not the requested `--port`, since `0` asks the OS to assign one). Anything else is a 403. This is a DNS-rebinding guard: a hostile page a browser tab has open cannot make same-origin-looking requests to this server by pointing a different hostname at 127.0.0.1.
2. **Origin.** When an `Origin` header is present, it must be `http://` + one of the same two host:port forms, or 403. A missing `Origin` is fine — same-origin `GET`s, curl, and the TazUO adapters never send one.
3. **Token.** With `config.token` set, every `/api/*` route except the per-job optimize SSE stream (see below) must carry `Authorization: Bearer <token>` or get a 401. The comparison is `crypto.timingSafeEqual` on two equal-length buffers (unequal lengths fail closed without calling it, since `timingSafeEqual` throws on a length mismatch rather than returning false). Static routes (`/`, `/ui/<name>`, `/vault-lib.mjs`, …) never need the token — only `/api/*` does. `GET /api/events`, the shared inbox stream, is **not** exempt.
4. **Content type.** Any `PUT`/`POST` whose body is read must declare `content-type: application/json` or get a 415 (body drained, not left unread). This is not a convenience check: a cross-origin form post cannot produce that content type, and a cross-origin `fetch` that declares it triggers a preflight this server never answers with allow headers. Together with the Host check it is what closes every route to a web page.

**The bare page never carries a token or an `Authorization` header** (spec §4.5: no token code lives in the page at all) — every page `fetch` instead goes through `app/ui/api.mts`'s `api(path, {method, body})`, which adds `X-Client-Id` (a `crypto.randomUUID()` cached in `sessionStorage`, or an in-memory fallback if storage throws) and throws with the server's own `{error}` message on any non-2xx response. Running the dev server with `--token` set therefore 401s the bare page's own fetches — that is the intended state until an embedder adds the header itself; see the Run / dev loop section above for what that looks like in a browser.

**Why the SSE events route is exempt from the token, and how it stays safe anyway:** `EventSource` cannot set custom headers, so it cannot carry `Authorization`. `GET /api/optimize/<id>/events` skips the token check but still passes Host/Origin, and separately confirms the request's `?client=` query parameter equals the job's own `clientId` (403 otherwise) — the page opens the stream as `new EventSource(`/api/optimize/${id}/events?client=${CLIENT_ID}`)`. Job ids are `crypto.randomUUID()` (not the old `Date.now()`-based id) so they are not guessable, which is what makes "no token, but the right id" an acceptable substitute for this one route.

**One running optimize job per client.** `POST /api/optimize` reads `X-Client-Id`; if that client already has a job in `state: "running"`, the server cancels it before starting the new one (`cancelJob`, which also ends any attached SSE stream) and the response carries `{superseded: <old id>}`. A caller with no `X-Client-Id` (curl, a test) is never deduped against itself — only the page's own header enables this.

**Every body is an object, and every route checks its own fields.** `asObject()` turns a body that parsed to `null`, an array, a string or a number into a 400 `body must be a JSON object` rather than an internal error, and every body-reading route calls it. Past that, a route validates each field it uses by name and type — never a bare destructure — and returns the reason it refused: `POST /api/optimize` takes an allowlist of `opts` keys with bounded ranges, whitelists five `meta` fields and caps the result, and refuses past four concurrent jobs with a 429; `POST /api/forget` requires a string `name`, caps it, and checks the tombstone it is about to write against the scan schema before writing (one file per root, named from the serial); `POST /api/setup/install` and `PUT /api/settings` both run the folder through `validateScriptsDir` and persist the **resolved** path.

**Body caps.** `readBody`'s default is 50 MB, but most routes are far tighter: 1 MB for `PUT /api/profiles` (`tooLargeMsg: "profiles too large"`), 64 KB for `POST /api/bridge`, 8 KB for the setup/import/host/runs/forget routes. The 50 MB default is left only where a large body is legitimate (a pasted scan, an optimize request carrying pools). Byte counting is on raw Buffers, and an overflow answers 413 and closes the connection rather than reading the rest.

**Profiles: size cap + schema.** `PUT /api/profiles` validates against `app/schema/profiles.v2.schema.json` before writing, 400 with the first error (`{path, msg}`, e.g. `/characters expected object`) otherwise. `app/schema/validate.mts` supports `additionalProperties` as a **subschema**, which is how the arbitrarily-keyed maps in `scan.v2.schema.json` (`stats`, `skills`, `containers`, …) get their values checked at all; `profiles.v2.schema.json` does not yet use it to walk every character and template, so that document's nested fields are still only shape-checked at the top level. That is the remaining gap, not a limitation of the validator.

**Stack-free 500s.** A route that throws no longer returns the stack to the caller. The catch-all handler generates an 8-character ref (`crypto.randomUUID().slice(0, 8)`), appends `<timestamp> <ref> <method> <path>\n<stack>\n` to `config.paths.log` (`<data>/logs/server.log` — the directory is created by `ensureLayout()`), and responds `{ok: false, error: "internal error", ref}`. A bug report only needs the ref to be actionable; the optimizer's own job-failure path (`runJob`'s catch, reported through the SSE `failed` event and `GET /api/optimize/<id>/status`) follows the same rule — a ref-keyed line (`<timestamp> <ref> job <job id>\n<stack or message>\n`) is appended to `config.paths.log`, same as a route-level 500, and only `internal error (ref <ref>)` reaches the job's `error` field. `safeAppendLog` never rotates or trims — a deliberate ruling, recorded in `docs/threat-model.md`, not an oversight to fix in passing.

**Response headers and file modes.** Every response sent through `send()` carries `x-content-type-options: nosniff`, `cache-control: no-store` and `x-frame-options: DENY`; the HTML response also carries the CSP, whose `frame-ancestors 'none'` is what actually stops the page being framed (`frame-ancestors` has no `default-src` fallback, so `default-src 'none'` does not deliver it). `ensureLayout()` creates the data directory and its subdirectories `0700` and writes files `0600` (`DATA_DIR_MODE`/`DATA_FILE_MODE` in `app/config.mts`) — use those constants for any new write into the data directory rather than letting the umask decide.

### Rules to keep when changing any of this

These are the invariants the phase-7 review turned into commitments. Breaking one is a review comment, not a style note.

- **Every route validates a JSON-object body field by field.** New route, new validation: call `asObject()`, then check each field you read for type, and for length or range where one applies. Return the reason you refused. A `as Record<string, unknown>` destructure with no checks behind it is how a whole family of 500s and a disk-fill primitive got in last time.
- **No HTML sinks in the UI. DOM nodes only.** `el()` has no `html` path, and `innerHTML`, `outerHTML`, `insertAdjacentHTML` and `document.write` appear nowhere in `app/ui/`. Keep it that way: everything reaching the page from a scan file — item names, engravings, tooltip lines, character names — is a stranger's text. A dynamic attribute value must be regex-constrained (the tooltip colour is the only one, and it must match a strict hex pattern).
- **Every write into a player-chosen folder goes through the atomic helper.** `atomicReplace` (`app/installer.mts`, with its `copyFileAtomic`/`writeFileAtomic` wrappers) is the one way to write there: a random `O_EXCL` temp name, an `lstat` refusal of any destination that is not absent or a plain regular file, a rename, and cleanup on failure. A bare `writeFileSync`/`copyFileSync` at a fixed, published name follows whatever symlink is sitting at it.
- **Adapters treat the queue as hostile.** `<data>/bridge/<adapter>/queue.jsonl` drives a real character in a live game and can be written without the server's involvement, so an adapter re-checks every line itself — freshness, duplicate ids, rate, chain length, container-ness, walk distance, grab source — rather than trusting that the server validated it. Server-side validation is real but it is not the boundary. Keep the grab destination hard-coded to the player's own backpack and out of the protocol.
- **Actions are pinned by SHA.** Every `uses:` in `.github/workflows/*.yml` names a full 40-character commit SHA with the tag in a trailing comment. A `@v4` is a mutable pointer; see `RELEASING.md` for how to resolve a SHA and why the trailing comment matters to Dependabot.
- **A new schema keyword must be enforced by the validator AND known to the types generator.** `app/schema/validate.mts` implements a deliberate subset and silently ignores anything outside it, so a bound written into a schema file that the validator does not implement is documentation, not a check. `scripts/build-schema-types.mts` throws on a construct it does not understand rather than emitting `any`. Adding a keyword means both files, plus a test that a document violating it is actually rejected.

## Data model (what the fold produces)

`inventory = { characters, containers, items, scans }`. Items keyed by serial with `name, kind, gear, slot, twoHanded, props (optimizer keys), extras (other numeric lines), flags (non-numeric lines, lowercased), tags, rarity, strReq, weight, slayers, gargoyle, lines (raw tooltip), root, container, equippedBy, layer, seenAt, scannedBy, location {kind, text, character, rootName}`. Fold rule: snapshots in time order; a scan REPLACES everything under each root it lists (and the scanner's worn set); roots it could not open are not listed, so their old contents survive; an opened-but-empty root is listed with no items, which clears it. Nested containers are items too (kind container, named by engraving), roots are not. Pseudo-character `_vault` = tombstone from Forget. **Quick refresh:** the quick-refresh script (`adapters/tazuo/`) writes `<Char>-<stamp>-quick.json` with the worn set + stats/skills/maxes/resists and the BACKPACK as its only root (nested bags walked). Because the fold replaces the worn set whole, that root is what keeps a just-removed piece — it reappears in the backpack instead of vanishing; bank and ground roots are not listed so their last scan survives. Its extra `meta` key (`{mode, name, roots}`) is ignored by the fold.

## Gotchas learned building it (don't relearn)

- Tooltip name line carries the stack count ("2 Greater Heal"): stripped in `parseTooltip`; `amount` is separate.
- Spell scrolls are named after the spell ("Recall", "Blade Spirits"): `SPELL_NAMES` set gates both `classify` (not gear — "blade" would match the weapon regex) and `kindOf` (scroll).
- Don't put bare words like `mystic`, `leather`, `rune`, `chest`, `scale` in the skip/spellbook regexes: "Mystic Ring", "Leather Gorget", "Rune Blade", "Woodland Chest" all broke that way.
- Engraved bags are named by their engraving (e.g. "DEXXER Armor") — force kind `container` for nested containers (except spellbooks/runebooks) or they classify as armour.
- Gargoyle gear: name `Gargish …` OR tooltip flag `gargoyles only` (throwing weapons only have the flag).
- Rarity line carries the client's colour as `<BASEFONT COLOR=#…>`; the shard's `rules.rarity` list (`app/rules/<shard>.json`) mirrors those in the same ascending order (uoalive: Major Artifact #FF8000, Greater Artifact #C9A800, Lesser Artifact #A335EE, Major Magic #0070FF, Greater Magic #1CB5B7, Lesser Magic #20E31C, Minor #A0A0A0).
- Worn totals on the character sheet include pieces outside the optimizer's 12 slots (sandals etc.). Unexplained diffs vs the in-game sheet (small HP regen / LMC amounts that don't match any equipped item) come from non-item sources; not a parser bug.
- Resisting Spells adds a resist bonus toward the shard's resist cap, from the shard's rules file (`resistSkillBonus.breakpoints`, e.g. uoalive: `+0.4/pt to 100, +0.2/pt 100-120`; a shard with no such bonus ships an empty `breakpoints` array — see Shard rules below); the sheet applies it.
- Layout: grid items need `min-width: 0` or a wide table pushes the page sideways; a sticky `th` cannot cross an `overflow-x` ancestor, so the inventory table scrolls inside its own box; Inventory and Suit Builder tabs are app-shell layouts (page never scrolls, columns scroll independently); Inventory is fluid, other tabs cap at 1800px; prose never gets a max-width (this app's own layout rule, applied consistently across every tab).
- The page's CSS classes are global: the build-progress panel owns the `.run` class, so the saved-run rows are `.runrow` (reusing `.run` once stacked every row into a column with an accent border). Check for an existing class before naming a new one.
- `API.HeadMsg` on TazUO is LOCAL-ONLY (unlike the web client) — used by the bridge for highlights.

## Optimizer notes

`optimizeSuit(pools, current, profile, opts)`: greedy + 200 restarts of single-slot hill-climbing with the weapon/shield pair handled together, then (with `opts.exact`) dominance pruning per slot and branch-and-bound with a per-dimension optimistic bound; returns `method`, `proven`, `nodes`, `pruned`. Caps are hard (`w·min(total,cap)`). Floors are HARD by default (profile `hardFloors`, bonus 1e7 — no mix of other gains can buy a miss; the page sends every floor not listed in the profile's `softFloors`); soft floors pay `floorBonus` (1000) when met with partial credit below. Lesson learned early: with soft floors the optimizer can trade away a hard requirement (e.g. a reagent-cost floor) for two resist floors plus a casting-speed stat, which is why hard is the default. Locked slots = empty pool for that slot and the slot removed from `optionalSlots` so only the current item remains. Verified against brute force in the tests (a hand-built case plus 150 random suits with caps, hard and soft floors and the tag penalty).

**Tighter bound.** Besides the per-dimension optimistic bound, the search tries an item-coupled one: for dimensions whose weight is >= 0 and whose item values are all >= 0, `w·min(t, cap)` is concave, so the most the remaining slots can add is the sum, over slots, of the best single item's gain at the current totals. It stops the bound from combining the best of every property from different items. It is computed only when the cheap bound fails to prune and 2+ slots remain, and the smaller of the two is used. Measured on a real inventory: a melee-profile build went from 148.4 s / 1.24 billion nodes to 0.7 s / 1.0 million nodes for the same proven suit. Tried and rejected: folding floors into the coupled bound through their concave envelope (valid, but the huge floor bonuses dominate the per-slot sum and it was 4-50x slower).

**Exact search.** `opts.exact` runs dominance pruning per slot then the core's own branch-and-bound with a per-dimension optimistic bound (see Tighter bound above) — this is what the `[slow]` brute-force tests in `app/gear-vault.test.mts` prove against, and what `optimize-worker.mts` falls back to when HiGHS is unavailable. In the app itself, `opts.exact: true` instead goes through `app/exact-solver.mts`: the core's heuristic for a fast incumbent, then HiGHS (`app/mip.mts` + `app/mip-solve.mts`) explores the tree itself and proves optimality or reports a bound gap — see `docs/solver.md`. There is no longer a multi-thread branch-and-bound pool to escalate to when a single thread can't prove a cell (retired along with `app/shared-search.mjs`, Phase 3): one job, one worker, HiGHS does the exploring.

**Other suits.** `opts.alternatives = {count, tolerance}` (exact phase only) makes the search keep its best `count + 1` leaves scoring within `tolerance` of the best: pruning then drops only subtrees whose bound is strictly below `max(best − tolerance, the list's lowest score once full)`, so ties survive, and dominance pruning is skipped because a dominated piece can still belong in a runner-up. The result carries `alternatives` (other suits, best first, never the best itself) and `altTolerance`. `app/exact-solver.mts` gets the same list from HiGHS by walking `k − 1` more no-good cuts (`addNoGood`) after the winning solve. Brute-force tested against every suit's score in `app/gear-vault.test.mts`. The page's Other suits / Within points inputs (defaults 5 and 0) feed it; the result panel lists each suit's differing pieces and every property total that moves (unweighted ones too), and Show renders that suit's sheet, plan and fetch list (`state.builder.altView`).

**Shield rule in dominance pruning.** A two-handed weapon may no longer knock out a shield on properties alone: the shield leaves a hand free for a one-handed weapon, so the swap is not always legal. The hill climbing usually hid this; the exact search could have missed a shield + weapon optimum.

**Scale.** See `bench/README.md` and `bench/REPORT.md` for the full write-up (fold time, payload size, per-slot pool sizes, dominance pruning, heuristic and exact phases, and the MIP-solver spike, `bench/mip-spike.mts`, that led to `app/mip.mts` + `app/exact-solver.mts` proving the optimum well past where the branch-and-bound search alone gives up). Read `REPORT.md` before touching the exact search's scaling — it documents where the cliff is and which levers are already tried.

**Warm start.** The server passes the character's newest saved suit as `opts.warmStart` (slot → serial); the core maps it onto this run's candidates and uses it as one more search start. It can never lower a result.

### Saved runs, instant repeats, weapon filter

Every finished build is saved (`data/runs/`). `POST /api/optimize` computes `runKey` first: a match that cannot be bettered returns `{cached: true, run}` and the page renders it at once with a "reused the run from …" pill. Saved runs live in a drawer that slides in from the right (the Saved runs button with a count in the sidebar's Character panel; closes with ×, Esc or a click outside; opening or comparing a run closes it; a filter box matches names and changes). It lists a character's runs newest first; each row's text is its name, or what changed from the run before it (`settingsDiff` in `vault-lib.mts`: floors, weights, soft/hard, locks, tags, pool flags, weapons, STR, restarts, budget). Opening a run shows its suit against today's worn gear, the sidebar-vs-run differences and a Load these settings button; ticking two runs and Compare shows settings A → B, slot by slot, and property totals with each run's floors. A run made before the latest scan carries an "inventory changed" pill. The page sends `meta: {character, settings, inventoryStamp, poolSize, skipped}` with each build; meta is not part of the key.

Weapons filter: profile `weaponSkill` (archery / swordsmanship / fencing / mace fighting / throwing, from the tooltip's Skill Required line). With a skill set the hands hold only that skill's weapons plus a shield (none for archery); spellbooks drop. `buildPools` returns `blocked` for a worn weapon the filter rules out, and the page drops it from the optimizer's `current` so the keep-what-you-wear rule cannot sneak it back.

### Profile semantics: paperdoll resists, pools, skill bonuses, race

- **Resist floors and caps are paperdoll values.** `effectiveProfile(p, character)` (`vault-lib.mts`) subtracts the character's Resisting Spells bonus (`resistSkillBonus`, from the scanned skill) from resist floors and caps before the optimizer sees them, and a race can raise a resist's cap (`getRules().raceCaps[p.race]`, e.g. an Elf's Energy cap of 75). So the floors stay right as Resist rises, and item resist past `(cap − bonus)` scores nothing. The requirement pills and the compare view add the bonus back for display. `optimizerProfile()` and saved-run views both go through `effectiveProfile`, which reads its caps from `getRules().caps` merged with any per-profile override (`p.caps`) — `setRules()` must have run first, or it throws. Both the Resisting Spells formula and the race cap overrides are shard rules now (`app/rules/<shard>.json`, see Shard rules below) rather than constants in this file.
- **Pools** (`toOptItem`): `stamPool` = DEX bonus + Stamina Increase, `manaPool` = INT bonus + Mana Increase, `hitsPool` = STR bonus ÷ 2 + HP Increase. Floor the pool when a breakpoint depends on the total (swing speed needs stamina = base DEX + stamPool), weight the parts.
- **Skill bonuses** from tooltip lines ("Magery +10") become properties `sk:<skill>` (`SKILL_NAMES`), weightable and floorable; `labelOf`/`fullOf` name them. `excludeSkills` (profile, "Forbid skill bonuses" chips) drops any piece with a bonus to those skills and blocks a worn one — useful for classes whose rules forbid mixing certain skills.
- **Locked one-hander:** when the one-hand slot has no empty option, two-handed weapons are not candidates (core). Before this fix the hill climber could swap in a two-hander and drop a locked one-handed weapon.

### Shard rules

Everything that is shard-specific rather than OSI-standard lives in a rules file, `app/rules/<id>.json`: property caps (`caps`), the Resisting Spells resist-bonus formula (`resistSkillBonus.breakpoints`, a list of `[to, rate]` pairs applied to successive slices of the skill — `resistSkillBonus(skills)` in `vault-lib.mts` walks them: `bonus += rate · max(0, min(skill, to) − prev)`; a shard with no such bonus ships `[]`), race cap overrides (`raceCaps`, e.g. `{elf: {energyResist: 75}}`), tag-penalty units (`tagUnits`, e.g. Cursed/Brittle/Antique/Prized — a shard can add its own, e.g. uoalive's Massive/Unwieldy), the rarity ladder (`rarity`: `[{name, colour}, ...]` in ascending order — rank is the array index + 1), the gargoyle race-lock policy (`raceLock.gargoyleOnly`), and the free-skill list shown on Characters-tab cards (`freeSkills`). Two ship with the app: `uoalive` (the default) and `generic-osi` (no flat Resisting Spells bonus, no Massive/Unwieldy tags, empty free-skill list). `app/schema/rules.v1.schema.json` is the contract every rules file is checked against.

`app/rules.mts` (Node-only — it reads files, so `vault-lib.mts` never imports it) is the loader: `loadRules(id, {userRulesDir})` looks in `userRulesDir/<id>.json` first (when given), then the builtin `app/rules/<id>.json`, validates, and throws naming the file path on failure; `listRules({userRulesDir})` enumerates every builtin plus every file in `userRulesDir`, keyed by each file's own `id` field (not its filename) so a user file overrides a builtin of the same id. `<data>/rules/` (config `paths.rules`) is where a user drops a custom or overriding shard file without touching the app.

`vault-lib.mts` never reads a rules file itself — it only exposes `setRules(rules)` / `getRules()` (the latter throws `"rules not loaded"` until the former has run, so a forgotten call is loud, not silently wrong). The server loads rules once at startup (from `<data>/settings.json`'s `shard`, defaulting to `uoalive` if the file doesn't exist yet — `ensureLayout()` writes it) and calls `setRules()` before any request that needs the lib; a page load fetches `GET /api/settings` and `GET /api/rules` first and calls `setRules()` itself, so caps/rarity/tag-units/gargoyle-lock are all correct before the inventory or profiles load. `GET|PUT /api/settings` reads/writes `<data>/settings.json` (`{schemaVersion, shard}`); `PUT` validates the new shard against `listRules()` (400 on an unknown id) and reloads the rules. `GET /api/rules` returns `{shard, rules, available}`. The header's shard `<select>` lists `available`, `PUT`s on change, and reloads the page — simplest way to re-apply a new shard's rules everywhere (caps, rarity colours, tag units, pool gargoyle filtering) rather than hot-swapping every consumer.

`profiles.json`'s own `caps` key (schemaVersion 1) moved out into the rules file at schemaVersion 2 — `migrateProfiles()` drops it on read; nothing in the page or the optimizer reads `profiles.caps` any more.

### Templates

A template is a full set of builder settings with no character in it: `floors`, `softFloors`, `weights`, `floorBonus`, `lockedSlots`, `excludeTags`, `excludeSkills`, `allowOthersWorn`, `allowGargoyle`, `medOnly`, `weaponSkill` (`TEMPLATE_KEYS` in `vault-lib.mts`; `templateFrom(settings)` snapshots exactly those, so race, STR limit and skipped containers never enter one). A character's profile stays its own full working copy and carries `template`, the name it was last applied from. `profiles.templates` replaced an earlier `archetypes` shape (which only held weights + floors); `migrateProfiles(file)` in `vault-lib.mts` is the pure conversion (returns `{profiles, changed}`, idempotent on the new shape, characters' `archetype` becomes `template`, other template fields defaulted); the server runs it in `readProfiles` and, when it changed anything, copies the old file to `profiles.backup-<date>.json` once and rewrites `profiles.json`; the page runs it on load too. Sidebar: a template `<select>` with Apply (copies the template into the working profile and sets `template`; Save profile persists it, as before), Save as… (prompt; snapshots the sidebar's settings as a new template), Update (overwrite the selected template, confirm) and Delete (confirm; the built-ins are not special). Template edits go through the whole-file PUT, so `saveProfile` stores a deep copy of the working profile: sharing the object would let later sidebar edits ride along with a template save. The pill beside the picker is `settingsDiff(templateFrom(template), templateFrom(working))`: "matches X" / "modified from X" (hover lists the diff lines) / "template X missing" after a delete; it is recomputed on every input/change/click in the sidebar. `readControls()` copies the pool checkboxes, weapon, race and STR into the profile (`allowOthersWorn` is a profile field now, set per character; saved runs still call it `allowOthers` and `settingsDiff` reads either), `poolControls(p)` sets them back.

### Build jobs and the progress panel

`optimizeSuit` takes `onProgress(p)` + `progressEveryMs` (default 250). The snapshot carries `phase` (heuristic → prune → exact → done), `restartsDone/restarts`, `nodes`, `explored` (fraction of the exact search tree behind the search, pruned subtrees included, so it is a true 0..1 bar that reaches 1 exactly when the optimum is proven), `budgetMs`, `improvements`, `lastImprovementMs`, `floorsMet/floorsTotal`, `candidates`. The end of every phase emits unconditionally (the throttle once swallowed the last heuristic snapshot when all restarts ran inside one millisecond). The page (`runPanel` / `runBuild`) opens an `EventSource`, keeps one job in `state.builder.job`, disables the Run button, and ticks a heartbeat every 200 ms: green while progress arrives, warn after 4 s of silence, bad after 12 s ("probably hung, cancel and retry"), warn with "reconnecting" when the stream drops. Cancel posts to the cancel route and closes the stream; a cancel during the initial POST cancels the job once its id arrives; `pagehide` sends a beacon so a closed tab does not leave a worker running. Custom SSE event names must not be `error` (the `EventSource` native error event fires for it too): failures are sent as `failed`.

## Bridge protocol

The Suit Builder's Highlight / Grab / Go to buttons queue commands for the in-game bridge script: `POST /api/bridge {action: highlight|grab|goto, serial, name, chain: [root … parent], pos: {x,y,z}|null}` appends to `<data>/bridge/<adapter>/queue.jsonl` with an id, where `<adapter>` is the currently CONFIGURED client (`settings.client.adapter`, falling back to `tazuo` only when nothing is configured) — not a fixed `tazuo` (`docs/bridge-protocol.md`'s Files section). The bridge script (`adapters/tazuo/`, see its README, for the reference implementation — `adapters/razor-enhanced/` is the other one) starts reading at the end of the file (old commands ignored), re-checks every line itself rather than trusting that the server validated it (freshness, duplicate ids, rate, chain length, container-ness, walk distance, grab source — `docs/bridge-protocol.md`'s "What the bridge refuses" is the list, and it is a contract an adapter with a bridge is expected to implement), walks to the item when out of reach, opens the chain of containers down to it, then highlights it for a few seconds or moves it to the backpack with a landed check, and writes `<data>/bridge/<adapter>/status.json {alive, character, current, results{id:{ok,msg}}, counts}` every couple of seconds. The page polls status every 2.5 s (online = alive < 8 s old) and toasts results for the ids it queued. `sendBridge(action, item)` is the one POST both per-item buttons and Grab all use. **Grab all**: one `grab` per piece of the suit currently shown (the alternative suit's list when Show picked one), sent one after another a few hundred ms apart and stopping at the first refusal; pieces worn by anyone or already in this character's backpack are left out (the count next to the button says so); disabled with a title while the bridge is offline or nothing is left; a running "Grabbing 3/7: name…" then a summary; each grab's result toasts through the same poll as a single Grab. It confirms first when the bridge is running on another character, because the pieces land in that character's backpack.
