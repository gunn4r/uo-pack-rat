# The page's UI: tokens, components and rules

How the page (`app/index.html`, `app/ui/`) is styled and built. Read this before changing a screen. The approved design is the round-1 redesign spec; this file is what a contributor needs from it.

## Hard rules

1. **Text never caps its own width.** No `max-width`, `ch` width or measure token on `p`, `li`, headings, labels or any text element. Width is decided by containers only: the page, a grid track, a card, a drawer, a dialog, a table column. The token set has no measure token on purpose.
2. **Grid and flex never split an inline flow.** Any element that is `display: flex | grid | inline-flex` holds only element children; every run of text is one `<span>`, and a run that mixes text with inline elements (`<strong>`, `<code>`, a muted number) is wrapped as a whole in one `<span>`. A button is `[icon svg] [span label]`, a switch label is `[input] [span text]`, a nav item is `[svg] [span label] [span count]`. The builders in `app/ui/components.mts` enforce this (see "The one-span rule" below).
3. **Verify the rendered output, not the source.** Look at the screen in light and dark at 1440, 1280 and 1024 wide before calling a change done.
4. **Electron UI tests use the real window size.** No test emulates a viewport larger than its real window; `fitWindow()` in `scripts/electron-window.mts` sizes the window within the screen and the test drives the layout that width shows (TESTING.md has the details and `PACKRAT_TEST_SCREEN` for trying a small screen).

## Tokens (`app/ui/tokens.css`)

Three layers, so a second theme family is a value swap rather than a rewrite:

- **Brand constants** (`--brand-*`): the logo palette. Never changed by mode; used directly only by the logo tile.
- **Semantic roles** (`--color-*`, `--res-*`, `--rarity-*`, `--font-*`, `--radius-*`, `--shadow-*`, `--border-width-frame`, `--frame-image`, `--surface-texture`): every component reads only these. A theme family supplies a light and a dark set.
- **Structural tokens** (`--space-*`, `--text-*`/`--lh-*`, `--control-*`, `--row-*`, layout widths, `--z-*`, motion): shared by every theme, so no screen reflows between themes.

Selection is two attributes on `<html>`, set by `app/ui/theme.mts` from the ui-prefs `theme` and `appearance` fields (`GET/PUT /api/ui-prefs`, kept in `<data>/ui-prefs.json` because the desktop app's page origin changes every launch): `data-theme="default|britannia"` and `data-mode="light|dark"`. Appearance "System" follows `prefers-color-scheme` live. Any subtree can flip mode by carrying its own `data-theme` + `data-mode` (the item tooltip `#tip` is always dark; under a Britannia page it takes Britannia's dark mode, see below). A new theme family is described under "The Britannia theme and adding a theme family".

**The on-* rule.** Every filled surface has a paired `--color-on-*` text token, and the rule that sets the fill sets its on-* text too (`background: var(--color-danger); color: var(--color-on-danger)`). No filled component inherits its text colour. `--color-border` is decorative (dividers, card edges); `--color-border-strong` is for anything the user must find the edge of (inputs, selects, chips, secondary buttons). Disabled controls use `--color-disabled` / `--color-on-disabled`, never opacity.

**Rarity** is data: the shard rules carry each tier's game colour, but most fail on a light page, so a tier is painted through its `--rarity-*` token (`rarityToken()` in `app/ui/items.mts`, `rarityColor()`/`rarCell()` in `app/ui/dom.mts`). A tier with no token falls back to its raw game colour inside a dark subtree.

**Fonts** are bundled: IBM Plex Sans 400/500/600 and IBM Plex Mono 400/500 (latin subset, woff2) in `app/ui/fonts/`, served by `GET /ui/fonts/<name>.woff2` under the page's `font-src 'self'` CSP. `--font-display` is the face for page titles (the top bar `h1`), card titles (`.card-head h2`), drawer and wizard titles (`.overlay-head h2`), Settings' section titles and KPI numbers (`.t-xl`, `.t-2xl`); in Default it is Plex Sans, so those elements look like the body text until a theme family swaps it. Mono is for identifiers only (serials, paths, pasted scan text, key hints); numbers use the body face with `font-variant-numeric: tabular-nums`.

## The shell and where each screen lives

Overlays sit outside `#app`, which goes inert while a drawer is open. Each screen's markup is its own delimited block of `index.html` (or is built by its module), and each has its own stylesheet, linked from `index.html`, so work on one screen rarely touches another's files:

The full logo stays the favicon and the window icon. The bridge status control at the sidebar foot has four states (ready, busy, offline, no client set up), worded by `bridgeView()` in `ui/messages.mts` and redrawn by `pollBridge()` in `ui/bridge.mts`; its popover says the state in words, the client, when it last answered, and offers Check again and Client settings. The shard picker and the Theme and Appearance controls are in Settings › General.

## Stylesheets

- `app/ui/tokens.css` — the tokens and `@font-face`.
- `app/ui/britannia.css` — the Britannia theme family's two mode blocks and its display face, linked right after `tokens.css`.
- `app/ui/components.css` — base resets and the shared component classes. Resets are wrapped in `:where()` (zero specificity) and variants are compound classes (`.btn.btn-primary`), so a reset can never outrank a component: `.pr button { color: inherit }` (0,1,1) would beat `.btn-primary` (0,1,0) and every filled button would inherit dark text.
- `app/ui/shell.css` and one file per screen (table above).
- `app/ui/styles.css` — the older shared classes the screens still use (`.panel`, `.stack`, `.field`, `.empty`, `.small`, plain tables, the item tooltip, the scrollbars) until each screen moves onto components. No literal colours anywhere: every colour is a token.

`<body class="pr">` is the root the resets hang off.

## Components (`app/ui/components.mts`)

Small DOM builders over `el()` (`app/ui/dom.mts`); their CSS is `app/ui/components.css`, ported from the approved design canvas. Nothing sets `innerHTML` (scan files are hostile input, `docs/threat-model.md`); icons are built node by node from a fixed path table.

**The one-span rule.** `txt(text, cls?)` returns exactly one `<span>`. `box(tag, attrs, ...kids)` builds a flex/grid container and throws on a bare string or number child. Every builder that takes a label wraps it itself. `FLEX_CLASSES` lists every class `components.css` draws as flex or grid; `app/ui-components.test.mts` checks the list against the stylesheet and that no builder puts a text node inside one, and `scripts/ui-components.test.mts` checks the rendered result. A new flex/grid class in `components.css` must be added to `FLEX_CLASSES`.

What exists:

- Text and containers: `txt`, `box`, `icon(name, {size})`, `kbd`.
- Buttons: `button({label, icon, iconAfter, variant: primary|secondary|ghost|danger|danger-outline, size: sm|md|lg, iconOnly, kbd, disabled, block, cls, onClick, attrs})`. An icon-only button's label becomes its `aria-label`.
- Fields: `input`, `select`, `textarea`, `searchInput({label, placeholder, hint})`, `field({label, control, help, error})` (wires `for`, `aria-describedby`, `aria-invalid`), `check` and `switchControl` (`[input] [span]` rows; a switch is off as a hollow track, the surface inside a strong edge with a small muted knob on the left, and on as an accent-filled track with a larger knob on the right, so the two never read alike), `segmented({label, options, value, onChange})` (radiogroup, arrow keys).
- Chips and labels: `filterChip({label, set, add})`, `token({label, removeLabel, onRemove})`, `pill({label, pressed, off})`, `badge(text, tone)`, `tag(text, tone)`.
- Status: `message({tone, title, text, actions})`, `meter(value, max, {tone})`, `progress(value, max, label)`, `stepper(steps, current)`.
- Layout: `keyValue(pairs)`, `card({title, actions, body})`, the resist tile (`.resist`; with `tint tint-<phys|fire|cold|poison|energy>` it gets a soft wash of its `--res-*` colour from the top-right corner and a semibold name, as on the Builder, the character sheet and the item peek; the contrast probe composites text under the wash at its strongest, `--tint-a`), `table({label, columns, rows})`, `tableFoot(...facts)`, `rowActions(actions)` (a disabled action carries its reason as a tooltip).
- Overlays: `popover(anchor, content, {label})` (anchored, light dismiss, Esc, focus back to the anchor), `menu(anchor, items, {label, width})` (an action menu as wide as its longest item, so no item wraps: `width` is only its minimum, 360 px its maximum), `tooltip(anchor, text, {side?})` (above, or `"right"` beside the anchor) and `tipWrap(control, text)` for a disabled control, `createDrawer({id, title, subtitle, body, footer})` / `bindDrawer(root)` for drawer markup already in `index.html` (focus trap, Esc, scrim, hidden + inert when closed, focus back to the opener, the shell `#app` inert while open), `openDialog({title, body, actions, role})` on the native `<dialog>`, `confirmDialog({title, body, confirmLabel, danger})` → `Promise<boolean>` (Cancel focused; the page's only yes/no question — never `window.confirm`), `showToast(text, tone, {action})` and `clearToasts()` (bottom-right stack of three; errors stay). A "⋯" menu's items take an optional icon, count or key hint, "divider" rules separate them, arrow keys move between them, and a disabled item carries its reason. `dom.mts`'s `toast(text, cls)` and `dialog.mts`'s `promptText()` sit on top of these.

## The Inventory screen

`ui/inventory.mts` draws the Items view; its pure rules (the query string, the active-filter tokens and their wording, the counts and plurals, the empty-result sentence, the row window and the keyboard model) are in `ui/inv-model.mts`, tested under plain `node:test` by `app/ui-inventory.test.mts`.

- **Filter state** is `state.query`, the shape `item-query.mts`'s `parseItemQuery` reads. Character, Slot, Location (as bag texts `loc` and whole root containers `root`) and Kind are any-of lists; Rarity is a range (`rarityMin`, `rarityMax`; an item with no tier counts as below every tier); property rules carry an operator (`prop=lmc:le:4`) and can name a numeric tooltip line no property models (issue #133: the facets' `extraKeys`, such as `prop=splintering weapon:10`); tags are hidden (`hide`) or required, any of them (`tag`), from the one Tags… popover. Every control goes through `setQuery()`, which redraws the chips (in place, so an open popover keeps its anchor) and the active strip, and refetches.
- **No pager.** The table is virtual: the body holds only the rows in view between two spacer rows, patched rather than replaced so a focused row is never detached, and rows load from `GET /api/items` in 500-row chunks as they scroll into view. A new query keeps the old rows on screen until its first chunk lands; the header (sort arrow, grouped columns) follows the data, not the click.
- **Keyboard.** The toolbar is one tab stop (`role=toolbar`, ←/→ between controls, the search's arrows move its caret until an end); the table is one tab stop (↑/↓, Home/End, Page Up/Down), row actions are reached with Tab from the focused row, and `/` focuses the search.
- **Bridge gating.** Row actions are always drawn and disabled with a reason (`bridge.mts`'s `bridgeActionReason`: worn, client can't, no position for Go to, bridge offline); `pollBridge` dispatches `bridgechange` on `document` when the bridge's state changes, and the table redraws its rows.
- **Columns.** Name, Rarity, Slot and Location are always shown; every other column is the player's choice. The item's tags (Cursed, Prized, …) are their own Tags column, drawn right after Name wherever the list names it and on by default; the Name cell holds only the name and a stack's quantity.
- **Preferences.** The chosen columns (`cols`), the column set they were saved against (`colsVersion`: a list saved before a column joined the defaults gets it once, then an "off" sticks — `view-state.mts`'s `colsFromPrefs`) the row density (`density`: `dense` 32 px or `regular` 40 px) and the column widths dragged on the header edges or set with ←/→ on a focused resize handle (`colWidths`: `{colKey: px}`, 40 to 1200, cleared by table settings' "Reset column widths") are ui-prefs fields.
- **Item peek** (`ui/peek.mts`): a row click, Enter or Space opens the selected item in a panel docked beside the table (400 px, 360 below 1280, laid over the table below 1180); while it is open, ↑/↓ step through rows with the peek following and Esc closes it (focus goes back to the row) from the table, the panel or the bare page — a click on the panel's text leaves focus on `<body>`, so the keys are heard on the document; a field being typed in, a popover, a dialog or a drawer keeps its own keys. Its tag chips carry the shard's meaning for each tag (the rules' `tagInfo`, `dom.mts`'s `tagChip`) as a tooltip on hover and focus. Its footer's Highlight, Grab and Go to are gated like the row actions.
- **Item tooltip** (`dom.mts` `tipNode`, `installTooltip`, `showItemTip`): the one `#tip`, always dark, 280 px, shown 400 ms after the pointer settles on anything with `data-serial` (Inventory rows, the Suit Builder's current suit, Plan and Fetch list pieces) or after a row has had keyboard focus for 400 ms; `pointer-events: none`.
- **Responsive.** Below 1180 px the unset facet chips fold into "+ Filter" and List | Grouped moves into the table settings popover, so the toolbar never wraps.
- **Classify this…** (`ui/kinds.mts`, issue #150) in a row's ⋯ menu, for an item that is neither gear nor a scanned container: a dialog with the kind (every kind but gear and container, which Organize never moves), whether it applies to every item with this name (the default) or with this graphic, and **Reset to automatic** when one of the player's kinds applies (it takes away the entry the dialog names: the name's when there is one, else the graphic's). It saves through `POST /api/item-kinds` and runs `reload()`, so the table, the Kind filter and the Organize plan follow at once. Organize's catch-all row and the ⋯ menu of Auto organize's Other rule have **Review unclassified items**, the Inventory filtered to kind `other` (`showKind`). Settings › Data has **Item kinds you set** with Export… (a download of `item-kinds.json`: a Save dialog in Electron, the browser's download elsewhere) and Import… (a file input; `POST /api/item-kinds/import` merges it in and the toast says what it left out).
- **Containers view** (`ui/containers.mts`): one row per root container, grouped by character with the ground last, with a Fill column and a ⋯ menu (Show these items, Label…, Blacklist…, Forget…). A root with items missing since its last scan (issue #99) shows an "N missing" warn tag after its name and gets **Show missing items**: a dialog listing each item's name, amount (a stack that shrank in place reads "N fewer") and when it was last seen there, sorted by name, fetched from `GET /api/missing?root=`; `GET /api/inventory` carries only the counts (`missingCounts`). The server computes them beside the fold in `app/missing.mts`: a root's previous scan against its latest, less anything the fold still has somewhere else (moved to another scanned container, or worn), and less what a vanished stack could have been merged into: the whole amount of each same graphic, hue and name stack seen elsewhere since the previous scan, and what one in the root grew by (Organize drops items onto matching stacks, and only the receiving stack's serial lives on). Only the shortfall is reported, as "N fewer", so a sale can be under-reported while more of that kind is kept elsewhere; a merge is never reported.

## House map

The House map (`#/map`, issue #10) draws each house a scan captured, one level at a time, from `GET /api/houses` and each house's model (`GET /api/houses/<id>`). Three panes: levels with their status, rooms and the yard with chest counts on the left (a room zooms the map to it); the map in the middle; the details on the right; one column below 1100 px. The top bar holds the house picker (the deep-linked house; a link to a house that no longer exists falls back to the last house shown, else the house with the most chests), Game angle | Top-down, Contents | Free space, and a pill per level. Every rule and number comes from `ui/house-map-model.mts` (no DOM, tested by `app/ui-map.test.mts`): the projection (`screenX = (x − y)·W/2`, `screenY = (x + y)·W/2 − z·K`), the painter's order, bounds and fit, the joins of a stack with the inventory and the Organize labels, the colour modes, the cut-away, callouts, totals and the plain grid. `ui/house-map.mts` builds the SVG with `createElementNS` once per level, view, mode or data change; pan (drag), zoom (the wheel, or the zoom in and zoom out buttons) and fit (the Fit the level button) change only the `viewBox`. Hovering or focusing a stack shows an HTML callout at a fixed size and fades the stacks in front of it, which also stop taking the pointer; stacks are one tab stop (roving tabindex in code order), arrow keys move to the nearest stack that way (one outside the view is brought to its middle), Enter selects, Esc clears; a redraw (a level, a room, a crumb, a reload) keeps the keyboard focus on the same control or, when it is gone, on the nearest stand-in, and Back to the house or Esc from the panel returns it to the stack. Every chest is `role="img"` with "<code> <name>, <fill>" as its name. Floors take `--color-map-<family>` from their material, chests their Organize label colour through `safeColor` (always with a `--color-border-strong` edge) or a `--color-map-*` token; every `--color-map-*` token is set in both modes of both theme families. Without a `tiledata.mul` the house is still drawn in neutral colours under a note naming the reason, with a link to Settings › UO folder (house map). A chest a capture saw but no scan opened is drawn dashed and listed as not opened yet: Highlight finds it by the place the capture saw it; Label… and Show items wait for a scan that opens it. Ground chests outside every drawn house are drawn on a plain grid, grouped by facet and distance. **Renaming a house** (issue #164): the ✎ inline after the panel's house heading (Rename house, so it follows the last word of a name that wraps) turns it into a name field; Enter or leaving the field (not the window) saves through `PUT /api/house-map/<id>` (with the house's footprint), Esc cancels, a refused name keeps the field open with the server's reason under it until a save or a cancel, and a redraw rebuilds the field with the draft and the reason; focus goes back to the ✎; the picker (`<name> · <facet>, <w> × <h>, <n> containers`), the house crumb and the page title then use the name. An unnamed house whose footprint overlaps a named house no longer captured, on the same facet (a redesign or a move gives it a new id), gets a one-line offer to use that name (`carryOver` in `ui/house-map-model.mts`). **Where the house is** (issue #164): under the heading, the plot's centre tile (the front steps left out, as the size), its facet and its sextant reading in one line with a copy button (`copyText`; when the clipboard refuses, the line is selected and a toast says to press ⌘C), and its corners. The reading is `ui/sextant.mts`, after TazUO's `Sextant.cs`. The Location section below (headed "Location - <facet> - <x> <y>", `whereTitle`) shows 600 × 450 tiles of the facet's overview around the house (`cropAround`, slid inside the facet), fetched once from `GET /api/facet-map/<facet>.png?x0&y0&x1&y1&w=600` and shown as a `data:` URL (the page's CSP allows `data:` images, not `blob:`), so the same request gives the region the server drew (`x-region`, slid inside the facet when the crop reached past it; `parseRegion`) or the 404's reason, with an SVG overlay in that region's tiles (`preserveAspectRatio="none"` over an image of the crop's aspect): a `--color-map-marker` dot on the house (`role="img"`), a smaller `--color-map-marker-other` one on every other captured house of the facet inside the crop, each an SVG `<a href="#/map/<id>">` named by the house (name, else its coordinates), so a click or Tab and Enter opens its map. Marker radii are screen pixels turned into crop tiles from the frame's width (`markerRadii`, kept by a ResizeObserver): a 24 px target per link, and a two-tone focus ring (dark under light) that shows on pale and dark ground. A crop was chosen over the whole facet plus an inset: one image, legible at the panel's width, and Felucca's 7168-tile width would make the house a speck. When there is no image, a muted line in its place says why (`facetMapNote`; a UO folder set in Settings that is gone reads like tiledata's); the coordinates stay. The marker tokens are the same in both modes, since the map under them is the game's own. **The world map lightbox** (`ui/world-map.mts`, its rules in `ui/world-map-model.mts`): the small map is an `<img role="button" id="map-where-open">` (Open the world map; click, Enter or Space; the SVG overlay lets the pointer through but its links) that opens `openDialog` with `cls: "world-map-dialog"` (the window less 24 px a side): Esc, the Close button and a click on the backdrop close it, focus goes back to the small map. The view is a box of world tiles shaped like the viewport (`fit`); it starts with the whole facet fitted in its middle, zooms between that and 2 screen px per tile (`zoomView`, about the pointer for the wheel, a pinch arriving as a wheel with ctrlKey; about the house while it is in view for the +/− buttons and the + / - / 0 keys), pans by a drag or the arrow keys (Shift for bigger steps; these keys work wherever focus is in the lightbox, a zoom button included) and never lets the facet leave the view (`clampView`). The zoom buttons' tooltips name their keys. A marker that scrolls out of view while it has focus hands the focus to the map first. A base image of the whole facet is fetched once at the dialog's size (a region of 8192 × 8192 tiles comes back cut to the facet, whose `x-region` gives the facet's real size); when the view is sharper than it, the visible tiles (`overlayRequest`, whole tiles, at screen resolution times the device pixel ratio, at most 2048 a side) are fetched 150 ms after the view settles, older answers dropped by a request id, and laid over the base at the `x-region` they came back with, while the stretched base shows meanwhile. Every captured house of the facet has an HTML marker of a fixed 24 px (`worldMarkers`): the house shown is a labelled `role="img"`, another an `<a href="#/map/<id>">` that closes the lightbox and opens its map (a drag that starts on it opens nothing), labelled once zoomed to 0.5 px per tile and only where its label does not overlap one already placed.

## Organize

The Organize screen (`#/organize`, issue #11) is two stacked cards at the page's width. Every decision and sentence on it comes from `ui/organize-model.mts` (no DOM, tested by `app/ui-organize.test.mts`); `ui/organize-data.mts` holds the page's copy of the setup (`state.organize`: the config from `GET /api/organize`, the problems its salvage reported, the blacklisted serials, the plan and the presets) and saves it whole with `PUT /api/organize`, dispatching `organizechange` on `document` so the Organize screen, the Containers view and the Items rows redraw.

- **Empty states.** No ground container scanned: say so. Nothing labelled: explain that Organize only touches labelled containers (so a friend's chest is never moved into) and offer Open Containers. Labels but no rules: the Rules card asks for one. A hand-edited `organize.json` the server salvaged shows what was dropped with **Save setup**, since no trip runs until the setup is saved as it now reads.
- **Rules card.** One row per rule in priority order (first match wins): a drag handle (`.org-grip`; ↑/↓ on the focused handle move the rule and a polite live region says where it went), the name with an Auto badge for strategy-made rules, a one-line summary of its filter (`matchSummary`, the Inventory's own token words), the target chain with each container's label colour, fill meter and "61/125" (`targetChip`; a target in no scan keeps its label's name and reads "not in any scan"), the plan's counts (to move, in place, and no room as a warning badge) and a ⋯ menu (Edit…, Move up/down, Delete…). The row is a grid that drops the chain and counts under the name at 900 px of list width or less (a container query; a 1000 px window gets there even with the sidebar collapsed). Under the list, "Everything no rule takes" picks the catch-all from labelled, unpinned containers, and "Empty bags" picks where empty bags are gathered (issue #128), each with its counts.
- **Rule drawer** (`ui/rule-editor.mts`). ## The Britannia theme and adding a theme family

Britannia (`app/ui/britannia.css`, chosen in Settings › General › Theme and saved as the ui-prefs `theme`) dresses the page as an Ultima Online gump: light mode is a parchment ground with aged-paper cards, iron-gall ink text, a deep brass accent and crimson danger; dark mode is a dark-wood ground with leather surfaces, parchment text and a brighter brass. The logo teal is its link colour and its info fill. It changes only what spec 2.5 lets a family change, so no screen moves between themes:

- every `--color-*` role (and the legacy aliases and `--ring-focus`, which are resolved per block);
- `--res-*` and `--rarity-*`, restated per mode: Default's values, with the light ones that fell under 4.6:1 on the parchment darkened just enough;
- `--font-display`: Cinzel 600 (SIL OFL, `app/ui/fonts/cinzel-latin-600-normal.woff2` with `OFL-Cinzel.txt`). Cinzel is capitals and small capitals only, so it goes on titles made of fixed words or names, never on anything whose letter case carries meaning (a serial like `0x700b0000` would read `0X700B0000`); that is why dialog titles, which can name a container, stay in the body face;
- `--radius-lg` and `--radius-xl` (2 px, square gump corners), `--border-width-frame` (3 px);
- `--frame-image`: a brass bevel (dark outer line, brass, pale highlight, lighter corner rivets) drawn as a 9 × 9 SVG data URI and sliced 3 px into a `border-image`. Cards, the old `.panel`, popovers, drawers and dialogs read it. A card inside another framed surface drops back to a plain 1 px edge (`components.css`, "one frame per stack"), and a card whose border colour carries a state (Settings' danger zone, the Import preview) sets `border-image: none` so its colour shows;
- `--surface-texture`: noise from `feTurbulence` as an SVG data URI on the page ground only (never under dense text): fine grain plus a slow mottle on the parchment, long horizontal grain on the wood. Each tile holds the noise four times, mirrored, so the tiling has no seam;
- `--shadow-2` and `--shadow-3`, warmer and deeper.

Nothing in the theme comes from a game or a game client: the colours are the logo's, the frame and textures are drawn in the stylesheet, and the face is an open-licence font.

`britannia.css` is linked after `tokens.css` on purpose. A subtree that flips mode carries `data-theme="default" data-mode="dark"` (the item tooltip, the rarity chips drawn in game colours); under a Britannia page it matches both Default's dark block (its own attributes) and Britannia's dark block (`[data-theme="britannia"] [data-mode="dark"]`, through `<html>`) at the same specificity, and the later file wins, so the tooltip is leather rather than Default's slate.

To add another theme family `<family>`:

1. Write `app/ui/<family>.css` with two blocks, `[data-theme="<family>"][data-mode="light"], [data-theme="<family>"] [data-mode="light"]` and the same for `dark`. Each must set every `--color-*` role Default's light block sets and every property Default's dark block sets (game colours, shadows, `--ring-focus`, the aliases), and nothing Default doesn't define; `app/theme.test.mts` checks both, so a new role added to Default later can't silently fall back to Default's light value inside the family. Structural tokens (spacing, type scale, heights, layout widths, z-layers, motion) are not overridable.
2. Bundle any font as woff2 under `app/ui/fonts/` with its licence text, `@font-face` in the family's stylesheet, and name it only through `--font-display`. Keep images inline (`data:`); the CSP allows `img-src 'self' data:` and the theme test refuses any other `url()`.
3. Link the stylesheet in `app/index.html` right after `tokens.css`, add the id to `BUILT_THEMES` in `app/ui/theme.mts`, the label to `THEMES` in `app/ui/settings.mts`, and the id to `UI_PREF_CHOICES.theme` in `app/vault-server.mts`.
4. Add the id to `FAMILIES` in `scripts/ui-contrast.test.mts`, which then measures every scene in the new family in both modes, and look at every screen in both modes before calling it done.

## Contrast check

`scripts/contrast-probe.mts` measures contrast on the rendered page: every text/background pair (compositing semi-transparent fills down to an opaque layer), field values, placeholders, control boundaries, switch edges and knobs, icons in icon-only buttons and messages, and status dots. `scripts/ui-contrast.test.mts` (`[slow]`, full suite) runs it in the Electron window over the demo data on every scene in each theme family (Default and Britannia) in light and dark, and fails on any pair under 4.5:1 for text (3:1 for large text) or 3:1 for edges, icons and dots; a disabled control only needs 3:1 text. When you add a screen, drawer, popover or dialog, add a scene there. The House map's scenes (the map, a selected stack's panel, a callout, the no-tiledata note and the empty state) are measured by `scripts/ui-map.test.mts` on its own seeded data folder, since the demo scans hold no house.

## Characters and the shared character sheet

The Characters screen has two routes: `#/characters` is the roster (one 48 px row per character: the name, with a warning badge beside it ("2 low", its sentence "2 worn pieces are low on durability" as the badge's accessible name and tooltip) when any worn piece is low on durability, so the warning stays in the sticky Character column however far the table scrolls; last scan, STR · DEX · INT, Hits · Stam · Mana, the five paperdoll resists with a meter to the cap, pieces worn, "Build suit" and a ⋯ menu), filtered by the top-bar search and sorted by its header buttons; `#/characters/<Name>` is that character's sheet, with a breadcrumb, previous/next, "Show <Name>'s items", "Build a suit" and a ⋯ menu. `parseRoute()` returns the sheet's name as `sheet` (the builder's `character` is untouched). The ⋯ menus are `menu(anchor, items, {label})` from `components.mts`: a popover with `role=menu`, ↑/↓/Home/End between the items, a danger item for Forget (which goes through `confirmDialog`). "Show <Name>'s items" opens the Inventory with its Character filter set to that character (`inventory.mts`'s `showCharacterItems`).

The sheet itself is one themed component, `sheetNode(name, before, after, opts?)` in `ui/sheet.mts`, used by the Characters screen and the Suit Builder result:

- `before`: the suit to show, a `SheetAssignment` (`Record<string, SheetItem>` keyed by slot or serial; a `SheetItem` is `{serial, name, slot, props, rarity?, tags?, extras?}`, which both a scanned `Item` and an optimizer `OptItem` satisfy). `wornSet(name)` gives the character's worn set in this shape.
- `after`: `null` for the one-suit sheet; a second assignment for the "now → after" variant, where every figure that moves reads "18 → 22" (the after number in success or danger colour), the slot tiles show the `after` suit with its new pieces badged "New", and the footnote adds the Hits/Stamina/Mana estimate note. Worn pieces the optimizer never touches count on both sides.
- `opts.onSlot(item, tile)`: called when a filled slot tile is pressed; without it the tiles are still buttons carrying `data-serial`, so the page's hover tooltip works on them. The Characters screen opens the piece's tooltip (the same `tipNode` as the hover tooltip) in an always-dark popover (`.item-pop`), with "Open in Inventory", which shows the piece in the Inventory's item peek (`inventory.mts`'s `showItem`).

It returns a `div.sheet` (with `data-character`): a KPI row of seven tiles (five resists as value / cap with a meter and a "cap +N" badge when the raw sum passes the cap, then Attributes with the gear bonus split and Pools), then two cards in a 7fr / 5fr grid: Worn gear (Armour 3 × 2, Weapons and jewellery 3 × 2, Clothing 3 × 2, anything else under Other; rarity-coloured borders, dashed empty slots) and Properties (the chosen properties in Casting, Combat, Leech, Regeneration, Pools and other and Other as key/value lists with the shard cap muted; the card's "Properties shown" popover picks them from every property the tooltip reader knows, saved as the ui-prefs `sheetProps`, default `SHEET_GROUPS`; the skills or an info message when the scan has none, and the Resisting Spells footnote). The sheet lays itself out from its own width with container queries (`ui/characters.css`): below 1040 px the attributes and pools drop under the resists, below 960 px the cards stack, so it fits whatever column it is put in. `resistFigures(name, set)` is the resist maths the roster shares with it. The one-suit sheet badges a worn piece that is low on durability ("Low durability 12/255": at 20% of its max or 10 points, `lowDurability`; a max of 0, no durability line, or a piece at or past its max is never low) on its slot tile, and the Characters sheet page puts a one-line warning under the meta line ("2 worn pieces are low on durability"); nothing shows when nothing is low, and the now → after sheet shows no badge, since an optimizer piece carries no durability. The pure formatters (`capBadgeText`, `atCap`, `bonusBreakdown`, `moveText`, `keyNumbers`, `tagTone`, `plural`, `lowDurability`, `lowDurabilityCount`, `lowDurabilitySummary`) are exported and unit-tested in `app/ui-characters.test.mts`.

## Suit Builder

The panel (`ui/builder.mts`) is drawn from state, never read back from the DOM: `state.builder.profile` holds the template settings, requirements, weights and candidate pool, and the exported `knobs` object holds the solver fields as typed strings (STR limit, which sits beside Race because it decides which pieces are candidates at all, and the Advanced search options), so a bad value can sit in its field with its error until fixed. A build, a saved profile and a saved run's settings snapshot (`ui/runs.mts`'s `settingsSnapshot`) all read from there. Sections redraw one at a time (`redraw(id)`), so an edit keeps the panel's scroll and focus. The numbers and words the screen shows (section summaries, validation messages with the allowed range, resist outcomes, other-changes badges, compare rows and best values, run labels and badges) come from `ui/builder-model.mts`, which has no DOM and is tested directly (`app/builder-model.test.mts`); its `SOLVER_LIMITS` must equal the server's `OPTS_LIMITS` (a test checks).

**Resist caps** is a panel section between Requirements and Weights (closed by default; its summary reads "Shard caps: 70 each", or names the overrides, "Fire 95 (raised from 70) · the rest at the shard's cap"). One row per resist: the cap as a number field, "shard cap" when it is the shard's (race-aware), else an accent outline, a "raised from 70" / "lowered from 70" badge and a reset button. A value outside whole numbers 0-150 keeps its error under the row (`resistCapError`) and is held as typed in `capDrafts` (the profile keeps the last good cap), so Build refuses it even with the section closed, opening the section on the field; a race change drops any override that equals the new race's own cap (`pruneResistCaps`); a cap typed back to the shard's value removes the override (`withResistCap`), so a profile only stores real overrides (`resistCaps`, saved with Save profile, templates and each run's settings snapshot). The result measures resists against the build's caps (`profileResistCaps`): the resist tiles read "86 / 95" with "Cap raised from 70" under them, the outcome lines ("At cap", "N over cap") use the raised cap, the full now → after sheet gets `sheetNode(..., { resistCaps })` (the Characters screen passes none and keeps the shard's), a saved run's badge reads "Fire 86 · cap 95", and compare judges each run by its own caps and adds a "Resist caps" outcome row when any column overrode one. The Requirements note names what gear supplies under each cap (`gearCapsText`). A resist requirement set above its cap is kept (a saved profile may carry one) but counts only up to the cap, as `effectiveProfile` clamps it for the solver: its row warns "Counts only up to the Fire cap, 70" (`floorCapWarning`), and every view that says whether a requirement is met (the headline, the tiles, run badges, compare) uses `effectiveFloor`, min(floor, cap), so they all agree with the solver. The full sheet's Properties header reads "build cap" instead of "shard cap" when the build overrode one.

**Weapons** is a chip in the Candidate pool section holding the weapon skills left out of the pool (`profile.excludeWeapons`). Its label comes from `builder-model.mts`'s `weaponsChipText` ("Weapons: 2 excluded"); its popover is a checklist where a tick excludes that skill's weapons.

A Fetch list row shows its place whole, never cut: the path of containers as crumbs that wrap (`builder-model.mts`'s `locationCrumbs`), selectable so any part can be copied, a same-named chest's serial in faint mono, then a line with the piece count and the container serial with a copy button at its end (components.mts's `copyText`: the Clipboard API, else a selected off-screen textarea and `execCommand("copy")`, since the desktop app's session denies the clipboard permission; its tooltip uses `tooltip(anchor, text, {side: "right"})` so it never covers the path above); the pieces under it are each an item tooltip target (`tipTarget` in `builder-result.mts`, also on the current suit's rows).

The Plan and Fetch list gate their bridge actions with `ui/bridge.mts`'s `bridgeActionReason(action, item)` and run them with `runBridgeAction`; Grab all is `grabAll(items, me)` (Grabs one after another, leaving out what `grabbable()` says is already with the character or worn), and the result redraws on the `bridgechange` event. `setNavBusy(nav, busy)` in `ui/shell.mts` puts a busy dot on a nav item while a build runs. The template and saved-run ⋯ menus are components.mts's `menu()`; a menu opened inside the Saved runs drawer gets `pop-over-drawer` so it sits above the drawer.

The compare view (2-3 suits from a result's Other suits, or 2-3 saved runs from the drawer) replaces the panel and results with a full-width table and swaps the top bar for a breadcrumb (`#b-cmp-topbar`); "Back to result" or the breadcrumb returns. "Full sheet" in "<name> after the change" opens the shared `sheetNode` in its now → after variant.
