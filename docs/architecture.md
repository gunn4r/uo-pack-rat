# Architecture: the desktop shell

How the pieces in `electron/`, `app/watcher.mts` and `app/installer.mts` fit together — the processes, the token, the data directory, and what changes (or doesn't) between the desktop app and the bare `npm start` server. Read `docs/module-map.md` for the modules and `app/vault-server.mts`'s header comment for the routes; this document is about the shell around it.

## Processes

Three processes make up the running desktop app, plus one worker thread spawned per suit-build job.

`electron/main.mts` is the Electron **main process** — the only code in the app that can touch the OS (native dialogs, opening a path in Finder/Explorer, the single-instance lock). It never runs any of the server's own code.

`electron/server-entry.mts` is a **`utilityProcess.fork()`** child of main: an ordinary Node process, not an Electron renderer, with no access to Electron's own globals. It just calls `app/vault-server.mts`'s `startServer()` — the same function `npm start` uses — with one addition, a `host` object (see The host bridge, below). Running the server here rather than inside main means a server bug, a stuck watcher, or a worker thread pegging a CPU core can never take the window or the OS-facing code down with it, and the server process can be killed and restarted on its own. Main restarts a child that exits unexpectedly unless its previous restart was under five minutes ago (`electron/restart-policy.mts`'s `shouldRestart`); a child that dies again that soon is crash-looping, so the shell shows an error dialog naming `shell.log` and quits instead.

The **`BrowserWindow`** is a sandboxed renderer (`sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`, `spellcheck: false`, no preload script) pointed at `http://127.0.0.1:<port>/`. It is a plain browser tab as far as the page's own code is concerned — every `fetch()` and `EventSource` call it makes is the same code that runs under the bare server, unmodified. The guards around it are attached from `app.on("web-contents-created")` so that any future `webContents` inherits them rather than depending on somebody remembering: off-origin navigation refused on `will-navigate`, `will-frame-navigate` and `will-redirect`, `<webview>` attachment refused, `setWindowOpenHandler` denying every new window and handing only a length-bounded, throttled `https:` URL to the OS browser. The session denies every permission request, permission check and device request outright — loopback is a Secure Context, so with no handler Electron would *grant* camera, microphone, geolocation and clipboard to a page that needs none of them. `electron/README.md` has the detail; `docs/threat-model.md` has the reasoning.

Inside the server child, `app/optimize-worker.mts` runs as a **worker thread** per suit-build job (`POST /api/optimize`), same as under the bare server — the shell doesn't change how builds run, only what forks the server that starts them. One job per client (a second request from the same `X-Client-Id` supersedes the first), and at most **four** running server-wide; past that `POST /api/optimize` answers 429 rather than spawning threads on demand. A finished job's result is kept for ten minutes after it finishes and then dropped. A build is never canceled for running long while it is inside its own time budget (the route accepts up to 60 minutes); only one still running ten minutes past that budget is canceled as stuck. Quitting the server mid-build ends the build without logging it as a failure.

The server child can open a **second loopback listener**, the built-in MCP server (`app/mcp.mts`, issue #211), while the player has it on in Settings: same process, same code, its own port (47615 unless `mcp.json` says otherwise, or an OS-assigned one for a run where that port is busy) and its own token, both kept in `<data>/mcp.json`, so an MCP client set up once keeps working across launches, unlike the app port and token, which change every launch. It serves only `POST /mcp`. Its tools call the app's own routes over loopback with the app's token (`app/mcp-tools.mts`), so it adds no route logic of its own; turning it on or off opens or closes the listener at once, and `close()` closes it with the rest. `docs/mcp.md` is the player's guide; `docs/threat-model.md` boundary 14 the reasoning.

Requests are not left open indefinitely, which for a server whose exact searches legitimately run for minutes needs stating precisely: `headersTimeout` is 60 seconds (nothing honest takes a minute to finish sending headers), `requestTimeout` is 300 seconds, and only `server.timeout` — the idle-socket one — is disabled, because an SSE stream is an idle socket by design.

## The token

Main generates a random UUID once per launch and hands it to the server child as the `PACKRAT_TOKEN` environment variable when it forks it, which makes `vault-server.mts` require `Authorization: Bearer <token>` on every `/api/*` route (see "The server's request checks" below — this is the same mechanism a developer can turn on by hand with `--token`/`PACKRAT_TOKEN` against the bare server). The token never reaches the page, a URL, or a log line: once the child reports which port it bound (`{type: "listening", port}` over `process.parentPort`), main registers a `session.defaultSession.webRequest.onBeforeSendHeaders` handler scoped to that origin that stamps every outgoing request to it with the header itself. The page's own `fetch()`/`EventSource` calls carry no token at all and need no knowledge that one exists — `GET /api/optimize/<id>/events` is deliberately exempt from the token check for exactly this reason (`EventSource` cannot set custom headers), authenticated instead by its unguessable job id plus a `?client=` match; `GET /api/events` (the inbox-watcher stream, below) is not exempt, since the shell's header attaches to every request to the server's origin regardless of path.

## The host bridge

Two things only the OS can do — show a native folder picker, open a path in Finder/Explorer — are needed by the setup wizard and the Settings tab, but the server has no window and no Electron APIs of its own. `vault-server.mts` accepts an optional `{ host }` with `pickFolder({title}) -> Promise<string|null>` and `openPath(which) -> Promise<void>`, which back `POST /api/host/pick-folder` and `POST /api/host/open-path` (both 501 under the bare server, which passes no `host`). `server-entry.mts` implements `host` by sending `{type: "host", id, op, args}` to main over `process.parentPort` and awaiting the matching `{type: "host-result", id, result}` reply, keyed by `id` so concurrent calls never cross; main does the real `dialog.showOpenDialog`/`shell.openPath` call and posts the result back. This is the only traffic on the parent-child channel besides the startup `listening` message and the `shutdown` message main sends on quit (`electron/protocol.mts` also defines an `error` message main would log, but the child never sends one today: a startup failure exits the process instead).

**Neither argument crosses that channel unchecked**, because the whole point of the split is that the child is the lower-trust half. `openPath` carries a **discriminator** — the literal `"data"` or `"logs"` — not a path: the route refuses anything else with a 400, and `electron/host-args.mts`'s `openPathTarget` maps it back to one of the two directories main computed for itself, refusing and logging anything it does not recognize. That matters because `shell.openPath` means "open this the way a double-click would", which on every platform can start a program. `dialogTitle` does the same job for the folder picker's caption: strip control characters, trim, cap at 120, and hand back nothing at all for a non-string. A host call that never answers is abandoned after a minute so the HTTP request behind it can return 504 instead of holding a socket forever.

## Data directory layout

One directory holds everything, resolved the same way for the bare server and the shell: `--data <dir>`, else `PACKRAT_DATA`, else (desktop only) `app.getPath("userData")`, else (bare server) `~/.pack-rat`. Run one Pack Rat per data folder: the desktop app points Electron's own `userData` at the data directory, so its single-instance lock is keyed on that folder and a second launch against the same folder just quits, but two bare servers pointed at the same folder can race scan writes.

```
<data>/
  scans/              normalized, schema-valid v2 scan files — what GET /api/inventory folds
  inbox/<adapter>/     where each adapter drops raw scan files (temp-then-rename); watched. putaway-request.json there is the TazUO panel's Put away request, not a scan (Organize, below)
    rejected/          a file that failed to parse/validate after retries, plus a .reason.txt
  profiles.json        the Suit Builder's builds, schemaVersion 3 (app/build-spec.mts): {characters: {"<name>": {race?, template?, spec}}, templates: {"<id>": {name?, spec}}}, each spec a BuildSpec {intent, buffs, pool, goal?, search?}; Automatic's buffs and the buff numbers edited for a character live in its spec's buffs; the built-in templates are never copied here; a v2 file is migrated on the first read, with profiles.backup-<date>.json and ui-prefs.backup-<date>.json kept beside them
  settings.json        {schemaVersion, shard, setupDone, client: {adapter, scriptsDir} | null, retention: {keepAll, scanDays, runsPerCharacter}, autoUpdateCheck}
  scan-blacklist.json  the containers scans skip: [{serial, name, addedAt, where?}], written by the app and by the TazUO and Razor Enhanced packrat-blacklist.py
  organize.json        Organize's setup: {version, labels, rules, catchAll, emptyBagsTo?, pinnedItems} (app/organize-config.mts); written by PUT /api/organize
  item-kinds.json      the player's own item kinds: {version: 1, names: {"<item name, lower-case>": kind}, graphics: {"0x<hex>": kind}} (app/item-kinds.mts; issue #150); written by POST /api/item-kinds and /api/item-kinds/import
  house-map.json       the player's house names and drawn areas: {version: 1, houses: {"<house id>": {name, bounds?: {x0, y0, x1, y1, facet}, areas?: [{id, name, level, color, rects: [{x0, y0, x1, y1}]}]}}} (app/house-names.mts; issues #164, #10); name "" for a house with areas and no name; an area's name follows the house-name rules, level is from 0, color one of area-1 … area-8 (a token name, never a color), rects are world tiles, inclusive, lying within bounds give or take 8 tiles; at most 32 areas a house and 16 rects an area; written by PUT /api/house-map/<id> (the whole entry, 64 kB at most), other entry and area fields kept; a bad hand-edited entry is left out of reads (and logged) and dropped by the next save
  organize-state.json  Organize's results overlay: {version, pending, grabs, moves, seen} (app/organize-state.mts); written by the server only
  ui-prefs.json        the page's view choices ({cols, colsVersion, colWidths, sheetProps, theme, appearance, sidebar, density, areaLabels, mapDrawerWidth, builderMode, manualFor, manualSuit, manualBuffs, manualBuffSkills, buffsCount, dismissedUpdate, copiedScanner}: the Inventory columns and their widths, the character sheet's properties, the look, a pinned-collapsed sidebar, the House map's labels and drawer, the Suit Builder's mode, Manual suit and buffs and No character's buff numbers, the update notice last dismissed, the web scanner last copied)
  mcp.json             the built-in MCP server's settings: {version: 1, enabled, allowActions, port, token} (app/mcp.mts; issue #211), written 0600 by Settings the first time one of its switches changes and on every change after; a file that does not check out reads as off
  tazuo-panel.json     the TazUO in-game panel's hotkey and showAtLogin ({hotkey: {mods, key}, showAtLogin}), written by Settings, the wizard and the panel itself (app/tazuo-panel.mts)
  rules/                user-defined or overriding shard rules files
  runs/                 one file per finished suit-build job, and per suit saved from Manual (scans/ and runs/ are pruned by settings.json's retention on startup and on Clean up now: app/retention.mts)
  bridge/<adapter>/     queue.jsonl (commands) and status.json (the bridge script's heartbeat); the CONFIGURED client's own directory, not a fixed "tazuo"
    panel.json           bridge/tazuo/ only: the in-game panel's heartbeat (adapters/tazuo/packrat-panel.py), same alive/stopped shape as status.json
    putaway.json         the server's answer to the last Put away request (app/put-away.mts), which the panel reads
  logs/
    server.log           the server's own request/error log (ref-keyed stack traces)
    shell.log             the shell's own lifecycle log (desktop only — see Logs, below)
```

`app/config.mts`'s `resolveConfig()` computes the folders' paths and those of `profiles.json` and `settings.json`, and `ensureLayout()` creates the data folder, `scans/` (not under `--demo`), `runs/`, `bridge/tazuo/`, `logs/`, `inbox/tazuo/` and a default `settings.json`. The other single files are not in that function: `app/vault-server.mts` builds the paths of `ui-prefs.json`, `tazuo-panel.json`, `scan-blacklist.json`, `item-kinds.json`, `organize.json`, `house-map.json` and `organize-state.json`, `app/mcp.mts` that of `mcp.json`, and each file is created the first time it is saved. The shell adds nothing to any of this; it just supplies `--data`/`PACKRAT_DATA` before the child ever resolves the config. Under `--demo`, `scans` points at the committed `app/fixtures/` instead of `<data>/scans`, and no inbox watcher starts at all — the demo fold must never be written to. Legacy scans a player already has on disk from before the inbox existed are not moved automatically; they come in through the Import drawer's Scan files mode, which reads each file in the page and sends it through `POST /api/import/paste` like a pasted scan (validated and written to `inbox/<adapter>/` for that adapter's watcher). There is no route that copies a whole folder server-side any more. The Import drawer (`app/ui/import.mts`, Task 1, Phase 6) is the one place in the UI this lives — the Settings tab used to duplicate it with its own adapter-unaware copy (Task 5, Phase 6 removed that and left a pointer instead).

**Versions and migrations.** Each of these files is read through `app/migrate.mts`: `DOC_KINDS` names, for a scan, `profiles.json`, a saved run, `organize.json`, `organize-state.json`, `item-kinds.json`, `house-map.json`, `mcp.json`, `settings.json` and `ui-prefs.json`, the version this build writes and the ordered steps that bring an older document up to it, and every store's reader calls `migrate(kind, raw)`. `version` and `schemaVersion` are read as one field, and each file keeps the field it has always been written with. A file whose version is newer than this build knows is read as far as it can be and is read-only: `organize.json`, `item-kinds.json`, `house-map.json` and `profiles.json` say so in their GET response's `readOnly` ("made by a newer Pack Rat"), which the page shows once, and every save to them is a 409 that leaves the file as it is. `app/fixtures/golden/<kind>/<version>.json` holds one file for every version of every kind, and `app/migrate.test.mts` loads each to the current version and checks it: an old file still loads.

## The inbox watcher's lifecycle

`app/watcher.mts` runs one `startWatcher()` per adapter directory under `adapters/` that ships a `capabilities.json` (today: all three — `tazuo`, `razor-enhanced`, and `classicuo-web`, though the last never sees a folder drop, since its paste transport only ever reaches its inbox via `POST /api/import/paste`), watching `inbox/<adapter>/` non-recursively for `*.json` changes via `fs.watch`, plus one `scanOnce()` sweep at startup so files dropped while the app was closed are picked up immediately.

**Debounce.** A file's change events are collapsed with a 300 ms timer per filename — an adapter script's temp-then-rename write can fire more than one `fs.watch` event for the same drop, and this keeps it to one ingest attempt.

**Ingest.** `ingestFile()` `lstat`s the file *before* opening it: anything that is not a regular file — a symlink, a directory, a device — is refused unread rather than followed, and so is anything larger than `MAX_INBOX_BYTES` (32 MiB, checked off the inode so a padded file never reaches memory). Only then does it read and `JSON.parse` the file, upgrade it (v1 → v2), validate it against the scan schema, and write it into `scans/` under a normalized name (`<slug>-<stamp>.json`, through `app/atomic-write.mts`'s random temp and rename, created `0600`) before removing the inbox copy. A JSON parse failure is reported as one of three fixed reasons rather than V8's own message, which embeds an excerpt of the file's bytes — that string is written into `rejected/<name>.reason.txt` and pushed to the page, and it should not be a channel for the file's contents. It never throws — every failure mode (bad JSON, a failed upgrade, a schema violation, or an I/O error during the write itself) comes back as an ordinary `{ok: false, reason}` so the retry loop always sees ordinary data. It is also idempotent: before writing, it checks whether `scans/` already holds a file under this document's accepted name (with or without a collision suffix) whose own `character`+`scannedAt` match — if so, nothing new is written, which is what makes a file that got stuck in the inbox (e.g. its final cleanup unlink failed once) safe to re-see on a later `scanOnce()`, including after a process restart, since the check reads the scans directory itself rather than anything kept in memory.

**Retry and quarantine.** A file that fails `ingestFile()` is retried up to 3 times, 700 ms apart (a half-written temp-then-rename can look invalid for a moment; a transient write failure such as a full disk counts as a failed attempt the same way). After the last retry it is moved to `inbox/<adapter>/rejected/<name>` with a `<name>.reason.txt` beside it explaining why, and `onRejected` fires so the page can toast it. A duplicate result never fires `onAccepted` — nothing new was ingested.

**Ordering and shutdown.** Every file, whether discovered by a watch event or by `scanOnce()`, is processed through one promise chain, so two files' ingestion never interleaves. `getShard()` is re-read fresh immediately before each `ingestFile()` call (not cached at startup), so a shard switch via `PUT /api/settings` takes effect on the very next file rather than only after a restart. `close()` sets a `closed` flag every await point checks, so a shutdown mid-retry cuts the chain short instead of running past it.

**Self-healing.** The `fs.watch` handle has an `'error'` listener: an error (Windows reports `EPERM` when the watched folder is deleted or moved, and with no listener that would be an uncaught exception taking the server down) is logged once per streak and the watch re-armed, backing off from 700 ms up to a minute between attempts. A deleted inbox is recreated by the next `scanOnce()`, which also re-arms the watch, and a watch event arriving after the folder vanished triggers that sweep itself. A live watch's inbox is also swept every 5 seconds (`sweepMs`): fs.watch can stay silent for a watcher's whole life (the OS drops the notifications, seen on macOS under load), and a Put away request has a player waiting on it in game; ingestion is idempotent, so a file both an event and a sweep find is handled once. `scanOnce()` returns whether it could sweep at all, so `POST /api/import/rescan` answers 503 naming the adapters it could not sweep instead of reporting success over a dead watcher. The server starts its watchers only once its port is bound, so a launch that fails with `EADDRINUSE` has not already moved inbox files into `scans/` or left watchers running.

`GET /api/events` is the one shared Server-Sent-Events stream every connected browser tab listens to: `hello` on connect (which adapters are being watched), `inventory` once a file is accepted, `rejected` once one is quarantined, `ping` every 15 s. `app/ui/events.mts` is the page's one listener; a burst of accepted files (an import, or a full scanner run across several chests) coalesces into one page reload via a 400 ms debounce plus an in-flight guard, rather than one reload per file.

## The installer's guard

`POST /api/setup/install {adapter, scriptsDir}` (backing the wizard's Install step and the Settings tab's Reinstall button, folder-transport adapters only — see below) copies an adapter's scripts into the player's chosen scripts folder (TazUO's `LegionScripts/`, Razor Enhanced's `Scripts/`) and writes `packrat-paths.json` there so the scripts know where this app's data directory is. Before touching anything on disk it checks the adapter's own `capabilities.json` `transport` field and refuses with `code: "noInstall"` for a `"paste"`-transport adapter (docs/adapter-guide.md) — there is no scripts folder to write to at all, so the wizard sends that player to the Import tab instead and never reaches this route. For a folder-transport adapter it then checks the heartbeat files beside that adapter's queue, `bridge/<adapter>/status.json` (the bridge script's) and `bridge/<adapter>/panel.json` (the TazUO in-game panel's), for a script that looks like it's still running in the client (an `alive` timestamp inside the last 30 s, not `stopped: true`) and refuses with a 409 naming the client's own way to stop its scripts if so (`-stopall` for TazUO, the Scripting tab's Stop for Razor Enhanced) — overwriting a script file while a Legion script thread is mid-run against it is exactly the "orphaned script thread" trap the TazUO adapter's own README warns about, so the guard runs first, before any file is copied. Every file is then written through one helper, `atomicReplace` — a random `O_EXCL` temp name beside the destination, an `lstat` refusal of any destination that is not either absent or a plain regular file, a rename into place, and cleanup on failure — so a reader never sees a half-written script mid-install, and a symlink already sitting in the chosen folder under one of these published filenames cannot redirect the write somewhere else. The destination folder is one the *player* picked, frequently an unpacked third-party client archive, and an archive is allowed to contain symlinks; that is the whole reason the helper exists rather than a bare `copyFileSync`. `packrat-paths.json` goes through it too, and is written last, once every script is in position, so an interrupted install never leaves a paths file pointing a partial script set at data it doesn't yet match — except that a hand-authored one naming a *different* `dataDir` is kept rather than overwritten (the documented cross-machine Razor Enhanced setup depends on it), and an unreadable one is copied to `packrat-paths.json.bak` first. `app/installer.mts`'s `candidateClientRoots`/`validateScriptsDir` propose and validate each adapter's own folder shape (`NESTED_SCRIPTS_SUFFIX`) rather than one TazUO-shaped guess for every adapter, rejecting relative paths and Windows UNC forms outright; both `POST /api/setup/install` and `PUT /api/settings` run the folder through that validation and persist the *resolved* path, so the two halves of the wizard cannot drift apart. A successful TazUO install also adds `packrat-panel.py` to TazUO's global autostart list, `GlobalAutoStartScripts` in `<TazUO>/Data/lscript.json` (`app/tazuo-panel.mts`'s `addPanelAutostart`): only when that file sits beside the nearest `LegionScripts` folder above the scripts folder, only while no TazUO process is running (a running client saves its own copy at logout, so the install reports `running` and leaves it alone), merging into the existing document and copying the old one to `lscript.json.bak` first. The response's `autostart` field says which of those happened.

One known limit, recorded as a ruling in `docs/threat-model.md` rather than fixed: the running-script guard reads only the bridge's `status.json` and the TazUO panel's `panel.json`. The scanner, refresh and blacklist scripts are overwritten by an install too and publish no liveness, so an install can still rewrite a scanner mid-run. Closing that needs every adapter script to publish a heartbeat — an adapter protocol change.

## Capability-driven bridge controls

The page never hard-codes which client is running. `GET /api/setup` returns `settings.client` (`{adapter, scriptsDir} | null`, which adapter Settings has configured), `adapters` (every `adapters/<id>/`'s own `capabilities.json`, `listAdapters()`'s output, capabilities included), and `bridgeAdapter` (the adapter id `app/vault-server.mts`'s own `bridgeAdapter()` is routing `POST /api/bridge`/`GET /api/bridge/status` to right now — `null` if that id isn't among `adapters` at all) in one response, cached as `state.setup` at page load and refreshed whenever the wizard or the Settings tab changes it. `app/ui/bridge.mts`'s `currentAdapter()` looks `state.setup.settings.client.adapter` up in `state.setup.adapters` to get that adapter's `capabilities.bridge` — the list of actions (`"highlight" | "grab" | "goto"`) its bridge script actually implements — and falls back to looking up `state.setup.bridgeAdapter` instead when no client is configured at all (a player who pressed Skip in the wizard, or installed an adapter's scripts by hand: `settings.client` is unset on purpose in both cases, but a bridge script may well be running and the server is already routing to it). What the bridge can do is then `bridgeFeatureSet()` (`bridgeFeatures` in `app/vault-lib.mts`): the running bridge's own report from the status poll while it is online, else the newest scan made with that adapter, else that `capabilities.json` (`docs/bridge-protocol.md`, Features). `bridgeActionReason()` disables any action that set lacks, with the reason as the button's tooltip (the Inventory rows, the item peek and the Suit Builder's result panel all draw their buttons through it), and `bridgeNote()`/`bridgeNoteEl()` produce the one-line explanation — no client configured and no fallback either, which of the three actions this client's adapter doesn't support, or (new) that the buttons are working against the fallback adapter by default and where to pin down a real one in Settings — that Settings › Game client shows under the configured client (`bridgeNoteEl()`, the ready-made element form, currently has no caller), so a bridge-less player is told why rather than left to notice a button is unusable. Only one client is ever physically connected at a time, so this is deliberately a single global decision — not something recomputed per item from whichever character's scan happened to produce it (an early version did that, which let a bridge-less character's rows still show buttons whenever any other scanned character's adapter had one).

`GET /api/setup` also returns `dataDirCheck` (`app/installer.mts`'s `checkScriptsDataDir`): whether the configured client's scripts folder, or with none configured any auto-detected one holding a Pack Rat script, writes to this data directory. It reads that folder's `packrat-paths.json` through the installer's bounded, no-follow regular-file read, and a missing file (or an empty `dataDir`) counts as the scripts' own default, `~/.pack-rat`. A relative, UNC or device `dataDir` gives no verdict and is never opened. The search is `startServer`'s `clientSearch` option (default: the real home and `candidateClientRoots`), which tests replace so they never reach a real client folder (`startServer`'s `clientSearch` option in-process, `PACKRAT_CLIENT_HOME` for an Electron launch). `"mismatch"` names both folders, `"unreadable"` says why the file couldn't be read; `"match"` and `"none"` say nothing. The server prints the same sentence at startup and Settings › Data shows it in full; the page's banner above every screen says it in one short line (`ui/messages.mts`'s `dataDirBanner`) with "Show details" (to Settings › Data) and Dismiss, and the bridge pill, when offline, says the scripts write to another folder. Nothing is changed or switched: the fix is `--data` or a reinstall. Always `"none"` under `--demo`.

`ADAPTERS_DIR` (`app/config.mts`'s `paths.adaptersDir`, default `adapters/` at the repo root) is resolved through `resolveConfig()` like every other path — overridable with `--adapters <dir>` or `PACKRAT_ADAPTERS_DIR`, the same pattern `PACKRAT_CORE` uses — so a test can start a real server against a throwaway folder of fixture adapters (one with a full bridge, one with none) instead of the repo's real ones; see `app/server.test.mts`'s `GET /api/setup: an adapter with no bridge...` test.

## Organize

Organize (issue #11) is four pure modules and a handful of routes. `app/organize-config.mts` holds the setup's types and its two checks: `checkOrganizeConfig` refuses any fault on `PUT /api/organize`, and `salvageOrganizeConfig` keeps whatever still makes sense in a hand-edited `organize.json` on every read (`GET /api/organize` lists what it dropped in `problems`; a rule whose target lost its label loses that target, not the rule, so its items never fall through to another rule or the catch-all; a file that is too big, does not parse or is not a version 1 setup is moved to `organize.json.corrupt`, never overwritten by the next save; one made by a newer Pack Rat is read as far as this build understands it and never saved over). `app/organize-presets.mts` holds the preset rule filters. `app/organize.mts` is the planner and `app/organize-state.mts` the results overlay.

`planOrganize(inv, cfg, overlay, opts)` is a pure function of the fold, the setup, the overlay and the blacklist; every walk runs in serial order, so the same inputs give the same plan byte for byte. Its stages, each tested on its own: `applyOverlay` re-homes items a trip moved since the last scan and adjusts container fills, oldest step first (a moved bag takes its new parent, so every chain through it and the root of everything in it follow, and carries its whole fill, issue #153); `scopeOf` decides what may move (items in labeled ground roots, never pinned, blacklisted, never-opened or a bag) and what may be filled (labeled, unpinned containers whose fill the scans state); `claimOf` gives each item to the first rule that matches (later matches are recorded); `homeOf` finds items already filed; `sitesOf` groups labeled roots by facet and single-link 24 tiles, and no move crosses sites; the capacity simulation (`newSim`, `simTake`, `simPut`, an undo log) packs each site's trips, running every take before any put as the bridge does, so freed slots count and a put never depends on a later trip. Within a site the rules take turns filling each trip, so two full chests can trade contents. When every item of a trip's window fails to fit, those items wait until another trip commits, so a rarer three-way trade can still read as no room. Trash containers never move, and the room report's `freeSlots` is how many more items a rule's chain takes, a bag and the chest around it counted once. Empty bags (issue #128): trips move items out of the bags inside a chest and leave the bags, each still taking one of the chest's item slots, so `emptyBagsOf` finds the unlabeled bags in labeled roots that hold nothing once the overlay is applied (never an unopened, pinned or blacklisted one, or one in a pinned or blacklisted container); the plan lists them (`emptyBags`), and with the setup's optional `emptyBagsTo` (a labeled, unpinned container, checked like the catch-all) it moves them there as the pseudo-rule `empty-bags`, in ordinary trips, a bag already in that container counting as in place. The bridge takes a container only once it has opened it and read it empty, and the plan gathers bags only when the bridge has the `trip-bags` feature (`opts.features`: the running bridge's report, else the newest scan's scripts, else the shipped manifest; else an `old-scripts` warning on the gather container). After packing, a target that is, or sits in, a container past `NEARLY_FULL` (90%) of its item or stone cap with no later target of the same rule under it gets a `nearly-full` warning on that container naming the rules that fill it and the empty bags left in it.

The plan carries a `stamp` (a hash of the latest scan time and every move). `POST /api/organize/trip {index, stamp}` rebuilds the trip from the current plan (`tripCommand`, against the fold with the overlay applied, as the plan was built) and queues it with `queueTrip`, refusing a stale stamp, a trip that is not its site's first, a second trip while one has not reported back (a trip its bridge is running counts only while the bridge's heartbeat is fresh, so a client that quit mid-trip frees the queue after 90 s), a setup that needed salvage (until the page saves it again), and a client whose bridge does not declare `trip`. It records the trip as pending in `organize-state.json`. Every `GET /api/organize/plan` first reads finished trips out of the bridge's `status.json` (`harvestTrips`: a take that worked means the item is in the backpack, a put that worked means it is in its destination) and drops overlay entries a newer scan has settled (`pruneOverlay`; an item seen since keeps its entry while the container it left has not been scanned since, and `applyOverlay` then only takes it off that container's fill). A Grab queued through `POST /api/bridge` is recorded in `grabs` with the container it lay in (the command chain's last link) and harvested the same way (issue #148): one that worked is a take marked `grab`, so the container it left has the slot free until a scan says otherwise, and the planner leaves the item with the player instead of putting it away as a trip's carried item. Harvesting also runs on every inventory read and on the page's bridge status poll (`harvestNow`), so a trip that reports back moves its items in every view with Organize closed. A trip's harvested moves name the character whose bridge ran it (`status.json`'s `character`), and every open page is told the inventory changed (a `changed` event on `/api/events`). The inventory every other route serves (`getInventory`: `/api/inventory`, `/api/items`, Find, tooltips, the Containers view, and so the chain Highlight and Grab send the bridge) is the fold with the overlay applied by `overlaidInventory` (issue #127): the same re-homing and fills as `applyOverlay`, each moved item's location read again from its new container, and a carried item at the top of its character's backpack, counted in its fill when it states one (or "Carried by Organize" when that backpack is not in the scans). It is cached apart from the fold, keyed by the fold's signature, `organize-state.json`'s inode, mtime and size, and the hour (so the week-old cut retires moves on a long-running server), so a finished trip re-applies the overlay without folding the scans again. The planner and Auto organize take the fold itself (`getInventory().fold`, which `organizeNow` hands on as `fold`) and apply the overlay on their own, so no move is applied twice. The plan route also names the trip still pending, if any (`running`: its id, index, queue time and whether its bridge is running it now), so a page reloaded mid-trip follows it. The bridge keeps only its last 30 results in `status.json`, so a trip whose result scrolls out before the next plan load is dropped from `pending` once its grace ends, and its items are planned again (the bridge then finds them gone and says so). Once a trip reports back its items are in place, the stamp changes and the remaining trips renumber, so the page reloads the plan and runs the next site's first trip.

Put away (issue #131, `app/put-away.mts`) is Organize without the app window: the TazUO panel's button raises a target cursor, the container picked (the backpack, a bag in it, or a container in a labeled ground chest) is refreshed (the character refresh, or Scan here), and the panel drops `putaway-request.json` into its inbox, naming that container. That adapter's watcher hands the request to the server's `putAway` in its turn, after any scan dropped before it (`startWatcher`'s `request` option), so the plan sees the fresh container. The server checks the request (`checkPutAwayRequest`), refuses a container whose newest scan is older than the run's click (`FRESH_MARGIN_MS`) or that is not in the character's own backpack or a labeled ground chest, plans with `planOrganize`'s `putAway` source, which replaces every labeled root as the source of items (only what lies directly in the picked container, as `packItems` picks it for the pack, into the site within 24 tiles of where the character stands; or, on the ground, the scope's movable items directly in it), and queues the first trip through the same pending bookkeeping as `POST /api/organize/trip`; the answer goes to `bridge/<adapter>/putaway.json`, and the panel asks again after each trip. docs/bridge-protocol.md, Put away, has the files and the bridge's side.

The page (`app/ui/organize.mts` and friends, docs/ui.md "Organize") reads the presets from `GET /api/organize/presets`, counts what a rule being edited would take with `POST /api/organize/match` (`matchCount`: `scopeOf`'s movable items through `ruleMatches`, ignoring rule order; like the plan and Auto mode's proposal it is handed `suitPieces`, every piece of every saved run in `<data>/runs` (`runs-lib.mts`), which a rule with `skipSuits` leaves alone, issue #133), and follows a running trip through `GET /api/bridge/status`; it never builds a trip itself.

Auto mode (`app/organize-strategies.mts`, spec §5) is pure too. `STRATEGIES` holds the Simple, Detailed and By build group tables; each group is a list of ordinary `RuleMatch` filters (mostly the presets), and By build's gear groups use `RuleMatch.build`, which `ruleMatches` answers with `buildOf` in `app/organize.mts` (issue #91: the side with more distinct caster or melee markers, Hybrid on a tie; with neither, Caster for a spellbook (issue #129), Melee for a weapon, Tank for a shield (issue #123) or when the piece's resists add up to 20, else Other), and `groupItems` gives each item to the first group that takes it in table order, which is the order the rules get. `proposeOrganize(inv, cfg, overlay, opts)` offers every usable ground chest the player's characters scanned (never a pinned, blacklisted, unopened, position-less or fill-unknown one; a chest the player's own labels or rules use starts unticked, unless an earlier strategy rule fills it), labels the checked ones, groups the movable items no manual rule claims (no Other group when the player has a catch-all), and gives each group its home site (where most of it is; the rest is reported as at another house). `assignGroups` then works each house in two passes, largest group first. Whole chests: a group takes whole chests only while every family still to come (each group has a family: armor, jewelry, reagents, scrolls, resources…) keeps one free chest; it takes first the chests its earlier strategy rule fills (so a re-run after the trips keeps them even when two chests now hold the group equally), then the chest already holding most of the group, ties to more room and then the lower serial, more chests chained until it fits, then every other chest holding only that group's items, so a sorted house stays as it is. Where holding on to those chests leaves items with no room, the house is assigned again with each group taking its earlier rule's chests and the next best only until it fits, and that wins when it leaves fewer items without room (issue #146), so a group's surplus chests go to groups that would otherwise run short. Shared chests (issue #123): a group that cannot take a whole chest is packed first fit decreasing with its own family, into the first chest its family opened that still has room for all of it, else into the next free chest (its earlier rule's chests first, then the one holding most of its family's items), leaving a free chest for each family still waiting for one. Each group keeps its own rules, all targeting the shared chest, which is labeled with the family's name. A group with no chest still gets its rules, with no targets, so its items are claimed and stay put. The full layout (issue #132): each house is first assigned with every chest's room cut to `FILL` (80%) of its cap and each group a slot more for its bag, adding stand-in chests of 100 slots one at a time until everything fits; where none are needed that assignment is the proposal (`layout.roomy` when it differs from filling to the top, which the drawer explains), unless the house is already sorted by its earlier rules into the same chests with room at the top, which stays as it is; elsewhere the house is assigned to the top as above. The proposal's `layout` names the stand-ins as chests to add and, for each chest of that layout two groups share, the bags it lacks. In the proposal every group whose one chest is shared gets a bag lying in that chest (the one its earlier rule fills, else an earlier strategy's holding only this group's items, else the next empty one by serial, `emptyBagsOf`; an earlier strategy's bag holding other items goes to no one), labeled with the group's name and its rules' one target; a group left without a bag targets the chest itself (`needsBag`). Bags are never moved in: the player drops them in and rescans; `spareBags` counts the empty bags in the checked chests nobody was given. The proposal is the whole next setup (manual rules first, then the strategy's; manual labels never renamed; an earlier strategy's labels and rules replaced, except a label a manual rule or the catch-all still fills), checked with `checkOrganizeConfig`, with `planOrganize`'s counts for it. `POST /api/organize/propose {strategy, containers?}` serves it read-only (409 while `organize.json` needed salvage); the page saves `proposal.config` through the ordinary `PUT /api/organize`.

## What the bare server can and cannot do

Everything above except the token, the host bridge, and the two `logs/shell.log`/desktop-specific data-directory defaults applies equally to `node app/vault-server.mts` / `npm start`. The bare server watches the same inbox, runs the same installer routes, and serves the same page — it just has no native folder picker or Finder integration (`POST /api/host/*` answers 501 without an embedder-supplied `host`, so the wizard and Settings tab fall back to a plain text input for a folder path) and, without a `--token`/`PACKRAT_TOKEN` set, runs with no token check on `/api/*` at all. Nothing in `app/` imports from `electron/` — the dependency runs one way, shell to server, which is what keeps `npm start`, `npm test`, and every non-Electron embedding of `startServer()` working unchanged.

## Logs

`<data>/logs/server.log` is the server's own log, unchanged by the shell: an activity and error log, not a request log — successful requests are never logged. It carries watcher accepts and rejects (by absolute path, so it names the player's folder layout and their character names), install progress, and ref-keyed stack traces for a route or job failure (see "The server's request checks" below), never returned to the client itself. `<data>/logs/shell.log` is desktop-only, written by `main.mts`: its own lifecycle lines (`shell: starting …`, `shell: quitting …`) plus everything the server child prints to stdout/stderr, prefixed `server: `. A player reporting a bug needs to attach both files, or the ref from `server.log` alone if that's all that's relevant — and `PRIVACY.md` warns them what attaching one discloses.

The token appears in neither: the server prints `token: set` or `token: none (dev)` and never the value, and the 500 handler logs a request's method and pathname but not its query string or headers. Neither file is rotated or size-capped; both grow for the life of the install and are safe to delete at any point. `server.log` is written owner-only (`0600`); the shell creates the `logs/` directory `0700` and `shell.log` `0600` when it first makes them, so neither is readable by another account on a shared machine.

## Packaging

`package.json`'s `build` block is treated as product interface — `scripts/packaging.test.mts` asserts its shape — and two parts of it matter here.

**Fuses.** A packaged build flips the Electron fuses that would otherwise leave the installed binary usable as a general-purpose Node interpreter: `runAsNode`, `enableNodeOptionsEnvironmentVariable`, `enableNodeCliInspectArguments` and `grantFileProtocolExtraPrivileges` off, `onlyLoadAppFromAsar` on, and `resetAdHocDarwinSignature` on because flipping a fuse rewrites the binary and invalidates the ad-hoc signature it shipped with. `enableEmbeddedAsarIntegrityValidation` and `enableCookieEncryption` are deliberately left unset, each for a stated reason — `electron/README.md` and `docs/threat-model.md` both carry it. A practical consequence: `--inspect` does nothing in a packaged app, so anything that drives Electron over the Node inspector can only drive a dev checkout; use `--smoke` against a packaged build instead. None of this affects a dev checkout, where fuses are never flipped.

**What is unpacked.** `asar: true`, and `asarUnpack` is exactly `["adapters/**", "node_modules/highs/**"]` — nothing else. The adapters must be real files because the installer `copyFileSync`s the `.py` out of them into the player's client folder, and HiGHS ships a `.wasm` that is read from disk. Everything the app actually *runs* — the server, the config resolver, the installer, the watcher, the compiled page, and `scripts/optimizer-core.mts` — stays inside `app.asar`, which Electron's fs and module patches serve fine, worker threads and a dynamic `import()` of a `.mts` file included. The `--smoke` run's third check exists to prove exactly that end to end: it starts a real optimize job from the renderer, which is the one path that exercises a worker thread loading out of the asar and HiGHS loading out of `app.asar.unpacked` beside it.

## The dev loop in detail

`CONTRIBUTING.md` has the commands. What needs a rebuild or a restart, and why:

- The server loads `vault-server.mts` and every module it imports, `vault-lib.mts` included, once at startup, so an edit needs a restart (or `node --watch app/vault-server.mts`). The optimizer core and `optimize-worker.mts` are not: every build starts a fresh worker thread that imports them anew, so an edit applies from the next build (a matching saved run is still reused until `SOLVER_VERSION` in `app/runs-lib.mts` changes). The data-folder warning at startup and the page's banner come from `checkScriptsDataDir` in `app/installer.mts`, which compares the configured or auto-detected client's `packrat-paths.json`, or the scripts' own `~/.pack-rat` default when there is none, with the data folder.
- **Bare server vs. the desktop shell.** Most feature work only needs the bare server — it's `startServer()` either way, same routes, same page. Reach for `npm run desktop` (runs `electron .`, which loads `electron/main.mts`) only when the change is actually in `electron/` itself, or you need to exercise something the bare server can't do on its own: the native folder picker / Finder integration behind `POST /api/host/*` (501 without an embedder), the per-launch bearer token attached out-of-band (see "The server's request checks" below), or the utility-process/single-instance/restart-once lifecycle. `npm run desktop -- --demo` and `--data <dir>` work the same as `npm start`'s, except that with neither `--data` nor `PACKRAT_DATA` the desktop app's data folder is Electron's `userData` directory (`app.getPath("userData")`), not `~/.pack-rat` — pass `--data` to share one with the bare server. Only one desktop Pack Rat runs per data folder: `electron/main.mts` points `userData` at the data folder and takes Electron's single-instance lock there, so a second launch on the same folder quits and focuses the first. Electron main-process changes need a full relaunch to pick up (no hot reload); the page inside the window reloads the same way it does under the bare server. `docs/architecture.md` has the process diagram and the token/host-bridge writeups.
- **The inbox watcher.** Dropping a `*.json` file into `<data>/inbox/tazuo/` (by hand, or via a real adapter script) gets picked up within its 300 ms debounce and normalised into `<data>/scans/` — useful for exercising the watcher/import path without a live game client. `--demo` starts no watcher (its `scans/` is the committed `app/fixtures/`, which must never be written to), so watcher work needs a non-demo run.
- **The installer's running-script guard.** `POST /api/setup/install` refuses with 409 (`RUNNING_MESSAGE` in `app/installer.mts`) when `<data>/bridge/<adapter>/status.json` (the bridge's heartbeat) or `panel.json` beside it (the TazUO in-game panel's, `adapters/tazuo/packrat-panel.py`) — for the adapter actually being INSTALLED, from the request body, not necessarily the currently-configured client — looks like a script is still alive in the client (an `alive` timestamp inside the last 30 s, not `stopped: true`; one more than 5 minutes in the future counts as stale) — this is the same "orphaned script thread" trap the TazUO adapter's README warns about, guarding against overwriting a script file mid-run. Testing the install path against a real `LegionScripts/` folder: make sure nothing is running in the client first (or write a `status.json` / `panel.json` with `stopped: true` / an old `alive` timestamp into a scratch data dir), or the 409 is expected behaviour, not a bug.
- **Browser gates in the window.** `electron/main.mts`'s `BrowserWindow` refuses to navigate anywhere but the local server's own origin (`will-navigate`) and sends anything the page tries to open in a new window/tab (`target=_blank`, `window.open`) to the OS browser instead of a second Electron window, and only for `http(s)://` links (`setWindowOpenHandler`). A link to an external site (e.g. a GitHub URL in a future changelog view) is expected to open in the player's regular browser, never inside the app's own window — that's this gate working as designed, not a bug to route around.
- `npm run build:types` (`scripts/build-schema-types.mts`) derives `app/schema/types.d.mts` from the five JSON Schema files (`app/schema/scan.v2.schema.json`, `bridge.v1.schema.json`, `bridge-trip.v1.schema.json`, `rules.v1.schema.json`, `profiles.v3.schema.json`) — `ScanV2`, `BridgeV1Command`/`Result`/`Status`, `BridgeTripV1`, `RulesV1`, `ProfilesV3`, plus a named type for every nested object the schemas define. `app/schema/types.d.mts` is generated and **git-ignored**, the same as `app/dist/`; the JSON Schemas are the authority, and a shape change is made in the schema, never in the generated file (a hand-edit is simply overwritten on the next build). It's a hand-written, dependency-free generator — no JSON-Schema-to-TypeScript library — that understands exactly the keyword subset described in its own header comment and throws, naming the construct and where it appeared, on anything else, rather than silently emitting `any`. Every `pre*` hook runs it first (`pretypecheck` runs only it; `predesktop`, `predist` and `predist:dir` run `build:ui` after it — `tsconfig.browser.json` includes the generated file, so it must exist before `build:ui` type-checks the page), and `scripts/start.mts`, `scripts/test-runner.mts` and `app/server.test.mts` each call `buildSchemaTypes()` themselves ahead of `buildUi()`, the same pattern `build:ui` below uses. It only rewrites the file when the generated content actually changed, so it doesn't needlessly invalidate anything watching it.
- The optimizer core (`scripts/optimizer-core.mts`, a real ES module, kept paste-able: no imports/exports beyond the one export line) needs **no build step** — every caller (the server, both test harnesses, the bench) imports it straight from source, by the path `config.mts`'s `corePath()`/`paths.core` resolves, via Node's native `node:module` type stripping (no external compiler; requires the `engines.node` floor in `package.json`). `PACKRAT_CORE` (env var) overrides that path for every caller at once — point it at an alternate copy without touching `config.mts`. This holds in the packaged app too: `build.files` ships `scripts/optimizer-core.mts` as source (no `asarUnpack` entry needed for it — Electron's asar fs/module patches serve a dynamic `import()` of a `.mts` file straight out of `app.asar`, worker threads included, verified against a real `electron-builder --dir` tree).
- `npm run build:ui` (`scripts/build-ui.mts`) compiles everything the browser loads — all of `app/ui/**` (every module is TypeScript now) plus the shared modules it imports (`vault-lib.mts`, `item-query.mts`, `organize-config.mts`, `buffs.mts`, `evaluate.mts`, `run-settings.mts`, `guards.mts`, `data-dir-notice.mts`, `scan-schema.mts`, `paste-scan.mts`, `schema/validate.mts`) — into `app/dist/` with `tsc -p tsconfig.browser.json`, rewriting each `./x.mts` import to `./x.mjs` on the way out. The server serves the page's modules from `app/dist/` and never from the source tree, because a browser cannot parse TypeScript; stylesheets and the bundled fonts still come from `app/ui/`, since `tsc` copies only what it compiles. The `predesktop`, `predist` and `predist:dir` hooks run it, and `scripts/start.mts`, `scripts/test-runner.mts` and `app/server.test.mts` each call `buildUi()` themselves so that invoking them directly, with no npm hook, still serves a current page. It always recompiles — a cold build takes well under a second — and it throws with the compiler's output if the build fails, so a broken page is never served silently. **A page-source edit therefore needs a rebuild before a browser reload picks it up** — `npm run build:ui` by hand, or restart `npm start` (`scripts/start.mts` runs it) or `npm run desktop` (its `predesktop` hook runs it); a plain reload against a stale `app/dist/` just re-serves the old compiled page. `npm run typecheck` checks the whole project without emitting anything, and CI runs it on all three platforms.
- `app/vault-lib.mts` is loaded once by the server, like every other module: a server restart (or `node --watch`) picks up an edit. The page's own copy is the compiled `app/dist/vault-lib.mjs`, so the page needs a `build:ui` before a reload picks the change up.
- `app/index.html` is served as-is; `app/ui/*.mts` needs a `build:ui` rebuild first (see above), but every `app/ui/*.css` stylesheet (`tokens.css`, `britannia.css`, `components.css`, `styles.css`, `shell.css` and one per screen) is served as-is straight from the source tree (the `/ui/<name>` allowlist route in `app/vault-server.mts`) since `tsc` never touches it — a stylesheet edit only needs a reload. Restart the server (or run it under `node --watch`) if you change `vault-server.mts` or anything it imports, `vault-lib.mts` included.
- Embedding: `startServer(config)` (exported from `app/vault-server.mts`, `config` defaults to `ensureLayout(resolveConfig())`) starts a server with no side effects at import time and returns `{ server, port, url, close() }` — `close()` tears down every timer, SSE stream and worker so the process can exit cleanly. This is what `app/server.test.mts` uses to run isolated instances per test, and what `electron/server-entry.mts` calls inside the desktop app's utility process (passing a `host` bridge for the native folder picker and Open folder), instead of shelling out to `node app/vault-server.mts`.

## The server's request checks

`docs/threat-model.md` is the reasoning behind everything in this section: the processes, each trust boundary, which defence is load-bearing against which attack, and the findings deliberately left standing. This section is the mechanics; read that one before changing any of them.

The bare `node app/vault-server.mts` / `npm start` path is loopback-only and runs with no token at all — this is the default. Only the **token** stays inert until an embedder opts in; the Host, Origin and content-type checks below are always on, which is what keeps every route closed to a web page even in this mode. What the missing token leaves open is another process on the same machine, which is out of scope for the same-user case but is **not** out of scope on a machine shared with other people: there, use the desktop app. The Electron shell (`electron/main.mts`) generates a per-launch token and sets it as `PACKRAT_TOKEN` in the server child's environment when it forks it (a developer can do the same thing by hand against the bare server with `--token <t>` or `PACKRAT_TOKEN`); `resolveConfig()` reads it into `config.token`, and `startServer()` prints `token: set` or `token: none (dev)` on start — it never prints the token itself, in a log or anywhere else. See `docs/architecture.md`'s "The token" section for how the shell then attaches it to every request without the page ever seeing it.

Every request goes through this order, before any route runs:

1. **Host.** The `Host` header must be exactly `127.0.0.1:<port>` or `localhost:<port>` — the port the server actually bound (read from `server.address().port`, not the requested `--port`, since `0` asks the OS to assign one). Anything else is a 403. This is a DNS-rebinding guard: a hostile page a browser tab has open cannot make same-origin-looking requests to this server by pointing a different hostname at 127.0.0.1.
2. **Origin.** When an `Origin` header is present, it must be `http://` + one of the same two host:port forms, or 403. A missing `Origin` is fine — same-origin `GET`s, curl, and the TazUO adapters never send one.
3. **Token.** With `config.token` set, every `/api/*` route except the per-job optimize SSE stream (see below) must carry `Authorization: Bearer <token>` or get a 401. The comparison is `crypto.timingSafeEqual` on two equal-length buffers (unequal lengths fail closed without calling it, since `timingSafeEqual` throws on a length mismatch rather than returning false). Static routes (`/`, `/favicon.png`, `/ui/<name>`, `/vault-lib.mjs`, …) never need the token — only `/api/*` does. `GET /api/events`, the shared inbox stream, is **not** exempt.
4. **Content type.** Any `PUT`/`POST` whose body is read must declare `content-type: application/json` or get a 415 (body drained, not left unread). This is not a convenience check: a cross-origin form post cannot produce that content type, and a cross-origin `fetch` that declares it triggers a preflight this server never answers with allow headers. Together with the Host check it is what closes every route to a web page.

**The bare page never carries a token or an `Authorization` header** (spec §4.5: no token code lives in the page at all) — every page `fetch` instead goes through `app/ui/api.mts`'s `api(path, {method, body})`, which adds `X-Client-Id` (a `crypto.randomUUID()` cached in `sessionStorage`, or an in-memory fallback if storage throws) and throws with the server's own `{error}` message on any non-2xx response. Running the dev server with `--token` set therefore 401s the bare page's own fetches — that is the intended state until an embedder adds the header itself; see the Run / dev loop section above for what that looks like in a browser.

**Why the SSE events route is exempt from the token, and how it stays safe anyway:** `EventSource` cannot set custom headers, so it cannot carry `Authorization`. `GET /api/optimize/<id>/events` skips the token check but still passes Host/Origin, and separately confirms the request's `?client=` query parameter equals the job's own `clientId` (403 otherwise) — the page opens the stream as `new EventSource(`/api/optimize/${id}/events?client=${CLIENT_ID}`)`. Job ids are `crypto.randomUUID()` (not the old `Date.now()`-based id) so they are not guessable, which is what makes "no token, but the right id" an acceptable substitute for this one route.

**One running optimize job per client.** `POST /api/optimize` reads `X-Client-Id`; if that client already has a job in `state: "running"`, the server cancels it before starting the new one (`cancelJob`, which also ends any attached SSE stream) and the response carries `{superseded: <old id>}`. A caller with no `X-Client-Id` (curl, a test) is never deduped against itself — only the page's own header enables this.

**Every body is an object, and every route checks its own fields.** `asObject()` turns a body that parsed to `null`, an array, a string or a number into a 400 `body must be a JSON object` rather than an internal error, and every body-reading route calls it. Past that, a route validates each field it uses by name and type — never a bare destructure — and returns the reason it refused: `POST /api/optimize` takes an allowlist of `opts` keys with bounded ranges, whitelists five `meta` fields and caps the result, and refuses past four concurrent jobs with a 429; `POST /api/forget` requires a positive-integer `root` serial, takes an optional string `name` and caps it, and checks the tombstone it is about to write against the scan schema before writing (one file per root, named from the serial); `POST /api/forget-character` takes a bounded `character` that may not start with `_` and must be a character the inventory has (404 otherwise), and writes one schema-checked tombstone per character; `PUT /api/ui-prefs` accepts only its known fields — the lists `cols` and `sheetProps` (at most 200 bounded strings), the enumerated choices `theme`, `appearance`, `sidebar`, `density` and `colsVersion`, `colWidths` (at most 200 keys, whole widths 40-1200 px) and a bounded `dismissedUpdate`, among others (each field is checked by name in `app/http/routes/prefs.mts`); `POST /api/setup/install` and `PUT /api/settings` both run the folder through `validateScriptsDir` and persist the **resolved** path.

**Body caps.** `readBody`'s default is 50 MB, but most routes are far tighter: 1 MB for `PUT /api/profiles` (`tooLargeMsg: "profiles too large"`), 64 KB for `POST /api/bridge`, `POST /api/runs` and `POST /api/evaluate`, 16 KB for `PUT /api/ui-prefs`, 32 MiB for `POST /api/import/paste` (the watcher's own `MAX_INBOX_BYTES`, so a paste the watcher would reject is refused up front), and 8 KB for the setup, rescan, host, runs, forget, blacklist, tazuo-panel and retention routes. The 50 MB default is left on `POST /api/optimize` (a request carrying pools) and `PUT /api/settings`. Byte counting is on raw Buffers, and an overflow answers 413 and closes the connection rather than reading the rest.

**Profiles: size cap + schema.** `PUT /api/profiles` refuses a body below schemaVersion 3 (a page loaded before the update, which holds no buffs) with "reload the page", validates against `app/schema/profiles.v3.schema.json` (every character's and template's spec walked through `additionalProperties` subschemas; 400 with the first error, `{path, msg}`, e.g. `/characters expected object`), then holds each spec to `buildSpecError` (`app/build-spec.mts`, the value rules: known buffs and weapon skills, resist caps, the STR limit's range) before writing.

**Profiles: newer files and older builds.** A Pack Rat from before schemaVersion 3 reads a v3 file without rewriting it (its migration leaves a file at schemaVersion 2 or above alone) and shows a saved character as having no settings, and its `PUT /api/profiles` refuses the v3 body it would send back (its schema takes schemaVersion 2 only), so it cannot write over the file. Automatic's buffs it saves go to `ui-prefs.json`, where this build drops them on its next read: don't go back to an older version after updating (`app/build-spec.test.mts` replays the older code path on a v3 file).

**Stack-free 500s.** A route that throws no longer returns the stack to the caller. The catch-all handler generates an 8-character ref (`crypto.randomUUID().slice(0, 8)`), appends `<timestamp> <ref> <method> <path>\n<stack>\n` to `config.paths.log` (`<data>/logs/server.log` — the directory is created by `ensureLayout()`), and responds `{ok: false, error: "internal error", ref}`. A bug report only needs the ref to be actionable; the optimizer's own job-failure path (`runJob`'s catch, reported through the SSE `failed` event and `GET /api/optimize/<id>/status`) follows the same rule — a ref-keyed line (`<timestamp> <ref> job <job id>\n<stack or message>\n`) is appended to `config.paths.log`, same as a route-level 500, and only `internal error (ref <ref>)` reaches the job's `error` field. `safeAppendLog` never rotates or trims — a deliberate ruling, recorded in `docs/threat-model.md`, not an oversight to fix in passing.

**Response headers and file modes.** Every response sent through `send()` carries `x-content-type-options: nosniff`, `cache-control: no-store` and `x-frame-options: DENY`; the HTML response also carries the CSP, whose `frame-ancestors 'none'` is what actually stops the page being framed (`frame-ancestors` has no `default-src` fallback, so `default-src 'none'` does not deliver it). `ensureLayout()` creates the data directory and its subdirectories `0700` and writes files `0600` (`DATA_DIR_MODE`/`DATA_FILE_MODE` in `app/config.mts`) — use those constants for any new write into the data directory rather than letting the umask decide. The server's own state files (settings, profiles, saved runs, accepted scans, tombstones, a pasted scan's inbox file) are written through `writeFileAtomic` (`app/atomic-write.mts`), so a crash or power loss mid-write leaves the old file or the new one, never a truncated one, and a state file that is a symlink (a `settings.json` or `profiles.json` linked in from elsewhere) is refused on save rather than written through; an unreadable `settings.json` or `profiles.json` is moved aside as `<name>.corrupt` and replaced with defaults, and a damaged saved run answers a 404 saying so.

## Data model (what the fold produces)

`inventory = { characters, containers, items, scans }`. Items keyed by serial with `name, kind, gear, slot, twoHanded, props (optimizer keys), setBonus (the full-set block's props, kept out of props), extras (other numeric lines), flags (non-numeric lines, lowercased), tags, rarity, strReq, weight, slayers, gargoyle, lines (raw tooltip), root, container, equippedBy, layer, seenAt, scannedBy, location {kind, text, character, rootName}`. Fold rule: snapshots in time order; a scan REPLACES everything under each root it lists (and the scanner's worn set); roots it could not open are not listed, so their old contents survive; an opened-but-empty root is listed with no items, which clears it. Nested containers are items too (kind container, named by engraving), roots are not. Pseudo-character `_vault` = tombstone from Forget; one carrying `forgetCharacter` (from the Characters tab's Forget) drops that character's card, worn set, backpack and bank. Containers that share a label side by side get their serial as a suffix in location text (`labelContainers`). **Character refresh:** `packrat-character-refresh.py` (`adapters/tazuo/`, the panel's Character refresh button) writes `<Char>-<stamp>-quick.json` with the worn set + stats/skills/maxes/resists and the BACKPACK as its only root (nested bags walked). Because the fold replaces the worn set whole, that root is what keeps a just-removed piece — it reappears in the backpack instead of vanishing; bank and ground roots are not listed so their last scan survives. Its extra `meta` key (`{mode, name, roots}`) is ignored by the fold.

## Parsing and classification gotchas

- Tooltip name line carries the stack count ("2 Greater Heal"): stripped in `parseTooltip`; `amount` is separate.
- Spell scrolls are named after the spell ("Recall", "Blade Spirits"): `SPELL_NAMES` set gates both `classify` (not gear — "blade" would match the weapon regex) and `kindOf` (scroll, but only on a scroll graphic or none: the conjured Healing Stone is named after its spell). The names are kept school by school with each school's scroll graphics, and `spellSchoolOf` gives a scroll's school from its exact name (Magery's "Curse" is not Necromancy's "Curse Weapon"), which an Organize rule's `school` asks.
- Don't put bare words like `mystic`, `leather`, `rune`, `chest`, `scale` in the skip/spellbook regexes: "Mystic Ring", "Leather Gorget", "Rune Blade", "Woodland Chest" all broke that way.
- Engraved bags are named by their engraving (e.g. "DEXXER Armor") — force kind `container` for nested containers (except spellbooks/runebooks) or they classify as armour.
- Gargoyle gear: name `Gargish …` OR tooltip flag `gargoyles only` (throwing weapons only have the flag).
- Names lie about slots: every Armor Of Initiation piece is called "Armor", and artifacts ("Heart Of The Lion") carry no base name. `classify` asks the graphic first (the client's tiledata layer, `scripts/gen-graphic-layers.mts <tiledata.mul>` regenerates the table in `vault-lib.mts`), except for held items: tiledata files bows under the one-handed layer, so weapons and shields go by name and tooltip.
- A set piece's tooltip ends with its full-set bonus after an "Only When Full Set Is Present:" header; summing those lines into the piece's own props over-credited every set piece. `parseTooltip` stops at the header and keeps the rest as `setBonus`. While the full set is worn the order differs (ServUO `BaseArmor.AddNameProperties`): "Full Armor Set Present" or "Full Weapon/Armor Set Present" sits near the top, then the set's "(total)" lines, then the piece's own lines, so only the "(total)" lines count as set lines there.
- Tiledata also files fishing poles, candles and light sources under the hand layers: a held graphic with no weapon name and no weapon lines becomes a shield or off-hand candidate only when it carries item properties and is not one of those tools.
- Rarity line carries the client's colour as `<BASEFONT COLOR=#…>`; the shard's `rules.rarity` list (`app/rules/<shard>.json`) mirrors those in the same ascending order (uoalive: Major Artifact #FF8000, Greater Artifact #C9A800, Lesser Artifact #A335EE, Major Magic #0070FF, Greater Magic #1CB5B7, Lesser Magic #20E31C, Minor #A0A0A0).
- Worn totals on the character sheet include every worn piece (sandals etc.). Unexplained diffs vs the in-game sheet (small HP regen / LMC amounts that don't match any equipped item) come from non-item sources; not a parser bug.
- Resisting Spells adds a resist bonus toward the shard's resist cap, from the shard's rules file (`resistSkillBonus.breakpoints`, e.g. uoalive: `+0.4/pt to 100, +0.2/pt 100-120`; a shard with no such bonus ships an empty `breakpoints` array — see Shard rules below); the sheet applies it.
