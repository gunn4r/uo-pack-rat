# The suit solver

The Suit Builder's "exact" mode does not search a decision tree in JavaScript. It builds the suit problem as a mixed-integer program (MIP) and hands it to [HiGHS](https://highs.dev/) (the `highs` npm package, MIT-licensed, compiled to WebAssembly), which proves optimality or reports a bound gap. `app/mip.mjs` is the pure model builder (no solver import — it only produces sparse CSR arrays), `app/mip-solve.mjs` owns the HiGHS runtime (load, solve, callbacks, no-good cuts), and `app/exact-solver.mjs` is the orchestrator the rest of the app calls. This document describes the model as built; `app/bench/REPORT.md` has the measurements that motivated replacing the old branch-and-bound search with it, and `app/bench/mip-spike.mjs` is the validation harness the model was checked against before it became app code.

## The problem

Choosing the best suit is a multiple-choice knapsack: pick at most one item per slot (helmet, chest, arms, hands, legs, neck, ring, bracelet, talisman, cloak, and one of oneHanded/twoHanded) to maximize a score built from weighted property totals, subject to floors — required minimum totals on some properties, some of them hard (a suit that misses one is not a valid answer at all) and some soft (a preference the optimizer may trade away for a big enough gain elsewhere).

## Variables and rows

One binary `x_{slot,item}` per (slot, candidate item) pair, built from the server's pools (`buildPools`) plus whatever the character is currently wearing — a worn piece stays a candidate for its own slot even if a filter would otherwise exclude it, matching the core's "keep what you wear" rule. One row per slot: `Σ x = 1` if the slot is required and currently worn, else `Σ x ≤ 1` (an optional slot may end up empty). A two-handed weapon and the one-handed slot are mutually exclusive: one row over every two-hander plus every one-hander candidate, `Σ x ≤ 1`.

For an uncapped weighted property the weight is folded straight into each candidate's objective coefficient (`colCost[j] += w·v`) — no extra column needed. A capped property adds one continuous column `c_d` with `c_d ≤ total_d` and `c_d ≤ cap`, weighted `w·c_d` in the objective: since `min(t, cap)` is concave and the problem maximizes, the solver always drives `c_d` up to `min(total_d, cap)` on its own, so this is exact, not an approximation.

## Floors, hard and soft

A hard floor becomes a single row, `total_d ≥ floor`, plus a constant bonus (`HARD_FLOOR_BONUS = 1e7`, matching `scripts/optimizer-core.ts`) added to every feasible suit's score as `scoreOffset` — the same trick the JS core uses, so scores from the two paths are directly comparable. A soft floor (or a hard floor demoted to soft, see below) gets a binary "met" indicator `y_d` and a continuous partial-credit variable `s_d`: `t ≥ f·y` ties the indicator to actually reaching the floor, `s ≤ k·t` and `s ≤ bonus·partial·(1 − y)` cap the partial credit below it (`k = bonus·partial/floor`), and the objective pays `bonus·y + s` — full credit at the floor, a jump, `floorPartial × bonus × t/f` below it, matching the core's own soft-floor formula to the decimal.

**Negative totals.** A property can total below zero (an item that trades away mana regen for a big HCI number, say). The plain `s ≤ k·t` row would make such a suit infeasible outright when `t < 0` (since `s ≥ 0` too), rather than giving it zero credit like the core does. The fix is a second binary `u_d`, added only when some combination can drive the total negative (`minReach < 0`): the k-row becomes `s ≤ k·t + k·N·u` (`N = −minReach`), so `u = 0` leaves the row unrelaxed (forcing `t ≥ 0` there) and `u = 1` relaxes it enough that any reachable negative `t` still satisfies it, paired with a row that forces `s = 0` outright when `u = 1`. A suit with a negative total on a soft-floored dimension therefore scores exactly like the core: zero credit on that floor, nothing more.

**Unreachable floors.** Before adding any row for a dimension, the model computes each slot's per-item maximum and sums them — the best total any suit could ever reach. A hard floor above that reach is never turned into a hard row at all (it would make the whole model infeasible for no useful reason); it's demoted to soft with no `y` column (nothing can ever meet it, so there is nothing to indicate) and listed in `unreachableFloors`, which the page shows as "these required floors cannot be reached by any suit in the pool".

**Jointly unreachable floors.** Each hard floor can be individually reachable while no single suit reaches all of them at once — that shows up as HiGHS returning `infeasible` on the first solve, not as a per-dimension unreachable flag. `exact-solver.mjs` retries once with every hard floor rebuilt as soft (`hardAsSoft: true`) so the fallback still reports the best suit that honestly exists, marks `floorsConflict: true`, and if even that retry can't produce an incumbent, reports the heuristic's own suit with `solver: "fallback"` and `fallbackReason: "no suit satisfies the required floors"` rather than inventing an answer. The one rule this whole path exists to uphold: **the heuristic's result is never shown as meeting the floors without the requirements report** — the page's chips/unmet-requirements panel is computed from the actual suit returned, independently of what the solver claims, so a fallback suit that misses a floor is always visible as missing it.

## Score mapping

A suit's score, as the rest of the app understands it, is `objective + scoreOffset` (`HARD_FLOOR_BONUS` per satisfied hard row, folded in once at build time rather than carried as a variable) — `toScore()` in `exact-solver.mjs` applies this to every value HiGHS reports (primal, dual, the final objective) so `bestScore`/`bound`/`gapPoints` are always in the same units the rest of the page already shows.

## The MIP start and warm start

`startVector()` builds a full column assignment from the heuristic's own best suit (every `x` set to match it, every `c`/`y`/`s`/`u` column computed to be consistent with those totals) and hands it to HiGHS as a MIP start, so the exact search begins already at least as good as the heuristic — it can only find something better or prove that suit optimal, never regress from it.

## k-best alternatives

Finding the next-best suits is repeated re-solving with one more no-good cut added each time: `Σ_{picked} x − Σ_{unpicked} x ≤ |picked| − 1` over every `x` column. The naive form `Σ_{picked} x ≤ |picked| − 1` also excludes a superset of the picked suit — exactly the case where a tie just adds a zero-value item into an empty optional slot — so the proper cut subtracts the unpicked columns too. Each alternative costs one more solve; the loop stops early once a candidate scores below the tolerance the caller asked for.

## Progress: incumbent, bound, gap

HiGHS reports its own progress through callbacks (`mipImprovingSolution`, `mipLogging`); `exact-solver.mjs` throttles these to one `progress` event per 250 ms and turns them into `bestScore` (the best integer solution found so far, i.e. the incumbent), `bound` (the LP relaxation's bound on how much better the true optimum could still be), and `gapPoints = max(0, bound − bestScore)` — the same absolute units as everything else the page shows, not HiGHS's own relative `mip_gap`. A `k-best` phase's events instead report `found`/`wanted`. When time runs out with no incumbent at all (a large pool, a tight budget, no floors conflict), the job reports `proven: false` with the heuristic's own suit as `best` and whatever bound HiGHS reached — an honest "best found within the time budget", never silence. `bound` and `gapPoints` are `null` whenever HiGHS has not yet reported a dual bound at all — the common case early in a solve on a small model (not just an edge case), and the case for a timeout that never got an incumbent either; the page renders "no bound yet" in the live progress line and "no bound established" in the saved verdict for exactly this state.

## The pool-size warning

`POST /api/optimize` counts the candidate pool (`meta.poolSize` if the caller already computed it, else counted from the pools it was sent) and sets a warning on the job — surfaced in the POST response body and shown above the progress panel — once it exceeds 50,000 candidates, since a pool that large is outside anything the model has been measured against (see below).

## Measured performance

All of the following is single-threaded WASM (`mip_rel_gap` 0), from `app/bench/REPORT.md`'s addendum: on synthetic realistic inventories the model proves 20,000-item pools (3,900–4,700 candidates after slot-splitting) in 1.1–2.1 s and 30,000-item pools (5,900–7,100 candidates) in 1.6–2.5 s; pushed further the same morning, a 50,000-item all-gear pool (31,900–38,400 candidates) still proves in 7.6–8.6 s, with no cliff observed up to 38,000 candidates and solve time growing roughly linearly at about 0.2 ms per candidate — the LP's size, not a search explosion. On the real (non-synthetic) inventory fixture the four default templates prove in tens of milliseconds of actual HiGHS time (Task 2's measurement: melee 129 ms, caster 29 ms, archer 21 ms, tank 23 ms, all proven), and a generated 3,000-item cell proves in about 4.4 s of HiGHS time against a JS branch-and-bound reference that had not finished proving the same cell after 60 s (though it agreed with HiGHS's score to the decimal where both had an answer). This is the empirical basis for the pool-size warning above: everything measured so far, up to and including 50,000-item all-gear inventories, proves in single-digit seconds.

## Running the equivalence tests

`app/mip.test.mjs` is `buildSuitMip`'s own structural unit tests (columns, rows, the negative-total guard). `app/solver.test.mjs` checks `solveExact` against the JS core: each default template proves through HiGHS and agrees with the core's own proven optimum, soft floors and k-best alternatives match, an unreachable hard floor and a jointly-unreachable pair of hard floors both behave as described above, a negative soft-floor total gets zero credit, a HiGHS-unavailable environment falls back honestly, and a `[slow]` 3,000-item generated cell proves inside its time budget. Run them with `node --test app/mip.test.mjs app/solver.test.mjs`, or `TEST_SKIP_SLOW=1 node --test app/solver.test.mjs` to skip the generated-cell case; both are part of `npm test` (see `TESTING.md`).
