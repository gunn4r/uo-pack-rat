# The suit solver

The Suit Builder's "exact" mode does not search a decision tree in JavaScript. It builds the suit problem as a mixed-integer program (MIP) and hands it to [HiGHS](https://highs.dev/) (the `highs` npm package, MIT-licensed, compiled to WebAssembly), which proves optimality or reports a bound gap. `app/mip.mts` is the pure model builder (no solver import — it only produces sparse CSR arrays), `app/mip-solve.mts` owns the HiGHS runtime (load, solve, callbacks, no-good cuts), and `app/exact-solver.mts` is the orchestrator the rest of the app calls. This document describes the model as built; `app/bench/REPORT.md` has the measurements that motivated replacing the old branch-and-bound search with it, and `app/bench/mip-spike.mts` is the validation harness the model was checked against before it became app code.

## The problem

Choosing the best suit is a multiple-choice knapsack: pick at most one item per slot (the nineteen of `vault-lib.mts`'s `GEAR_SLOTS`, one per paperdoll layer: helmet, neck, chest, arms, hands, legs, outerLegs (a kilt or skirt over the legs), feet, oneHanded and twoHanded — the second hand, which holds a shield or a two-handed weapon — shirt, tunic (the middle torso: doublet, surcoat, sash), robe, waist, cloak, ring, bracelet, earrings and talisman) to maximize a score built from weighted property totals, subject to floors — required minimum totals on some properties, some of them hard (a suit that misses one is not a valid answer at all) and some soft (a preference the optimizer may trade away for a big enough gain elsewhere). The game refuses an item only when another worn item shares its layer, plus the hand rule below, so the slots need no other rule between them (issue #202). Every slot but the five armor pieces (helmet, chest, arms, hands, legs) is optional (`DEFAULT_OPTIONAL_SLOTS`); `app/mip.mts` derives both lists from `GEAR_SLOTS`, and the core, which imports nothing, keeps a copy that `app/solver.test.mts` holds to them.

## Variables and rows

One binary `x_{slot,item}` per (slot, candidate item) pair, built from the server's pools (`buildPools`) plus whatever the character is currently wearing — a worn piece stays a candidate for its own slot even if a filter would otherwise exclude it, matching the core's "keep what you wear" rule. A piece with no properties (a tag penalty aside) is no candidate in a slot that may stay empty, the hands aside: it can only tie with the empty slot, and a tie would send the player for a plain robe or shirt that changes nothing. A worn one stays current, and its slot is not optional (`optionalSlotsFor`, which the server uses for every search): else the search plans plain boots off for no gain and lists every on/off mix as another suit of the same score, each one more HiGHS solve. A piece that scores and is not worn can still tie with an empty slot under the profile (Luck boots when only HCI and DI are weighted): the core's last step takes any such piece off an optional slot, the hands aside, when the score stays the same, and since `solveExact` reports its suit through the core, both solvers' suits leave it off (the alternatives are left as found). One row per slot: `Σ x = 1` if the slot is required and currently worn, else `Σ x ≤ 1` (an optional slot may end up empty). A two-handed weapon and the one-handed slot are mutually exclusive: one row over every two-hander plus every one-hander candidate, `Σ x ≤ 1`.

For an uncapped weighted property the weight is folded straight into each candidate's objective coefficient (`colCost[j] += w·v`) — no extra column needed. A capped property adds one continuous column `c_d` with `c_d ≤ total_d` and `c_d ≤ cap`, weighted `w·c_d` in the objective: with a positive weight, since `min(t, cap)` is concave and the problem maximizes, the solver always drives `c_d` up to `min(total_d, cap)` on its own, so this is exact, not an approximation. A negative weight (the page accepts one on any property, and the shard rules cap most of them) would instead drive `c_d` down without limit, so it also gets a binary `z_d` that pins `c_d` from below: `c_d ≥ total_d − M1·z_d` and `c_d ≥ cap − M2·(1 − z_d)`, with `M1 = reach − cap` and `M2 = cap − minReach` (the widest either gap can be; see "Unreachable floors" for `reach` and `minReach`). `z = 0` forces `c_d = total_d` (so the total is at most the cap), `z = 1` forces `c_d = cap` (so it is at least the cap): exact again.

## Resist caps

The caps both solvers score against are the profile's `caps`, which `effectiveProfile()` (`app/vault-lib.mts`) resolves before a build: the shard's caps, each resist's cap made race-aware (`rules.raceCaps`) and then replaced by the player's own override where there is one (`resistCaps`, from the Builder's Resist caps section, a saved profile or template, or a saved run's settings; paperdoll values, whole numbers 0-150). Resisting Spells leaves the caps alone (below). A resist floor counts up to that same cap. A player building a suit for Reaper Form (which lowers Fire by 25) sets the Fire cap to 95, so Fire from gear is worth something up to 95 on the paperdoll instead of stopping at 70. Neither the MIP nor the JS core knows overrides exist: they read `caps` as they always did, so an override needs no model change, and `app/solver.test.mts` checks that the two agree with overrides set (a raised Fire cap taking a two-piece Fire suit past 70 only when the cap allows it, and every default template with Fire raised and Cold lowered). The effective profile carries `resistCapOverrides` (each overridden resist's cap and the shard's) only when one is set, so a profile without overrides hashes to the same run key as before, and one with overrides never reuses a run built at other caps.

## The Resisting Spells minimum

Resisting Spells holds each resist at a minimum and adds nothing to gear (issue #261; ServUO `PlayerMobile.GetMinResistance`, `docs/shard-rules.md` has the formula): the paperdoll reads max(min(total, cap), minimum). `effectiveProfile()` carries the character's own Resisting Spells as `resistSkill` (the scan's base, without what the worn suit adds) and its minimum as `resistMinimum` (null with none, as with no character or a skill under 40), and, for the solvers, `mins`: per resist, the minimum the planned buffs leave (Protection lowers the skill, `minimumWith` in `app/buffs.mts`) less that resist's in-cap share, in item terms. Caps and floors are not shifted by it. The solvers plan at the base skill, so they never count on a Resisting Spells bonus a candidate suit may drop; a suit that adds one gets no credit for the higher minimum it brings (a follow-up issue). Every display of a suit uses the base plus that suit's own bonus.

- **Scoring.** A weighted resist scores w × max(min, min(total, cap)). The core does it in `optScoreVector` (`OptProfile.mins`). A min makes the term non-concave, but its gain from any total never passes the plain w × min(total, cap)'s, which is concave, so the branch-and-bound's per-item bound reads that one and loses nothing in pruning. The MIP models a positive weight with one more continuous column `v_d` (cost w) and a binary `b_d`: `v_d ≤ min + (top − min)·b_d` and `v_d − total_d ≤ (min − minReach)·(1 − b_d)`, with `top` = min(cap, reach); b = 1 lets `v_d` reach min(total, cap), b = 0 holds it at the min, and the better of the two is the max. A negative weight drives `v_d` down on its own: `v_d ≥ min` (its lower bound) and `v_d ≥ c_d` (the capped column, pinned by `z_d`) or `v_d ≥ total_d` uncapped, with `c_d` costing nothing. Where no suit can fall under the min (minReach ≥ min) the term is the plain capped one; where no suit gets past it (top ≤ min, a cap under the minimum included, wherever the totals lie) it is the constant w × min, put in `scoreOffset`.
- **Floors.** A floor at or under its min is met by every suit, so both solvers drop it (no bonus, no row). Above it, a floor is the item total ≥ floor as before, and a soft floor's partial credit reads the item total.
- **Display.** `applyBuffs` takes the Resisting Spells skill of the suit shown (the base plus that suit's bonus) as its last argument and lifts each resist under it (its total, and its cap if that is lower), naming them in `lifted`; `requirementReport` reads a resist under its min as the min (`mins`), and `runBadges`, the sheet and the current-suit tiles use `paperdollResist`.
- **Tests.** `app/solver-buffs-fuzz.test.mts`'s random characters carry Resisting Spells 0-120, so both solvers prove the brute-force best with nonzero minimums, Protection among the buffs; `app/buffs-plan.test.mts` checks Protection's lower minimum and Vampiric Embrace's Fire loss held at it through both solvers.

## Faster Casting cap

Faster Casting's cap follows the casting school (issue #213, `fcCapFor` in `app/vault-lib.mts`): the shard's `fc` cap (2) for Magery, Necromancy and Mysticism, 4 for Chivalry, Spellweaving and Bushido, and a Chivalry caster drops to the shard's cap once Magery or Mysticism reaches 70. The profile's intent field `castingSchool` names the school (absent means "from skills", a spec carries it only when named, templates carry it, a run's settings keep it); without one the cap follows the character's skills: 4 when it has Chivalry, Spellweaving or Bushido at 30 base or more, unless the highest of them is Chivalry and Magery or Mysticism is at 70 (the scanned value; ServUO's `Spell.GetCastDelay` drops only Chivalry's cap), else the shard's cap. With no character and no school it is the shard's cap. `effectiveProfile()` puts the result in `caps.fc`, so the totals, the floors and both solvers read it through the caps they already read, and the run key follows it with no SOLVER_VERSION change. A named school wins over the skills, but a named Chivalry still drops at Magery or Mysticism 70. `fcCapFor` also returns the reason the panel shows ("Chivalry", "Chivalry (chosen)" for a named school, "Magery 70+", "no character"). The game caps FC per spell, by the spell's school, while a suit has one cap: "from skills" picks the cap of the character's Chivalry, Spellweaving or Bushido, so a mage-weaver (Magery 120, Spellweaving 120) gets 4, which its Magery spells stop at 2 of; naming Magery gives 2. The 70 check reads the scanned skill value, which includes the item bonuses of what the character wears now, so a suit that swaps that jewelry out can land on the other side of 70. With No character, a named school still sets the cap (Manual's totals strip and Fill the rest alike, "cap 4: Chivalry (chosen)"); from skills it stays at the shard's cap. Compare runs and the Saved runs drawer judge each run by its own casting school, for its character as scanned now.

## Buffs

Automatic plans with the buffs that are on (issue #12, `plannedProfile` / `planBuffs` in `app/buffs.mts`) as a constant base the gear needn't supply.

- **The translation.** `applyBuffs` works out the caps in the game's order (additions, Curse on the running caps, Corpse Skin's absolute caps) from the profile's paperdoll caps; each key's in-cap share then comes off its cap and its floor (`effectiveProfile`'s `shift`, built by `buffShift`). A negative share (Divine Fury's DCI −20, Wraith Form's Fire and Energy −5) adds to both, so the gear makes up the loss and can be worth up to the real cap plus the loss. The share comes off the Resisting Spells minimum's `mins` too, and Protection lowers the minimum itself. Neither solver knows buffs: both read the shifted `caps`, `floors` and `mins`.
- **Exact, so caps may go below 0.** min(gear + share, cap) = min(gear, cap − share) + share for any gear total, a negative one included, so the gear's cap is left below 0 when the shares pass the cap (gear earns nothing there). A resist a buff touches (a cap change or an in-cap share) takes this exact form; one no buff touches keeps its own cap, so buffs that touch nothing (Enemy of One) plan and key exactly as none. A floor stops at 0, which both solvers read as no requirement: the buffs alone meet it (only a negative gear total below 0 could really miss it).
- **Stat headroom.** Gear STR, DEX and INT extend a stat to 150 on this shard (`STAT_MAX`), so with a character's raw stats known (scanned less worn), the gear's `strBonus` / `dexBonus` / `intBonus` caps are 150 − raw − the buffs' share, buffs or none (a character at raw DEX 125 with a Greater Agility potion's +20 gets 5 from gear). No character, no stat caps. These caps are the one change from main's profile with no buffs, and they change those runs' keys.
- **Overrides.** A resist override above the shard's (race's) cap, on a resist a buff that is on lowers, would count that loss twice (a Fire cap of 95 for Reaper Form, with Reaper Form on), so the plan uses the shard's cap there; the profile's `buffs.overridesIgnored` names it and the requirement's note says so. Turning the buff on is the way to plan for a form, not the override.
- **Past the cap.** What a buff adds past the cap (Enemy of One, Consecrate Weapon, Horrific Beast's HPR) never counts toward a cap, so it plays no part: Enemy of One alone plans, and keys, exactly as no buffs.
- **Approximations.** A potion's strength (the suit's Enhance Potions) and Enchant's Spell Channeling (the held weapon) depend on the suit itself and are taken from the suit worn now; the result says so per buff. Handling them exactly would mean modelling them as MIP variables. A stat slot's largest share (Bless against a potion) is decided among the buffs, which item bonuses never share. Partial credit for a floor the suit misses is worked out on the gear's floor, (gear / (floor − share)) rather than ((gear + share) / floor), so suits that miss a requirement score slightly differently than they would on the real totals; hard floors, and whether a floor is met, are exact.
- **The run key** (`runs-lib.mts`'s `runKey`) leaves out the profile's `buffs` (which buffs, their numbers, the caps and floors before them, kept for the result): the shifted caps and floors are what the solvers read, so buff sets that plan alike share a run, and a number no buff on reads changes nothing.
- **Tests.** `app/buffs-plan.test.mts` checks the plan against its meaning case by case (every form with and without the cap-changing buffs, Resisting Spells, race locks, stat slots and stat headroom, potions, overrides, Enemy of One, the run key, and main's profiles with no buffs), and `app/solver-buffs-fuzz.test.mts` fuzzes random buff sets, stats and 0-150 resist overrides against brute force. That fuzz also found a MIP issue of its own: with several hard floors, two of them out of reach, HiGHS can stop at a suit the core scores lower; `solveExact` then reports the core's suit unproven with a warning, as designed, so the score is still the best.
## Manual's pinned pieces

"Fill the rest automatically" (issue #12) searches only Manual's empty slots, with no change to either solver. `POST /api/optimize` takes `pinned`, Manual's suit (`{slot: serial}`), and `buildPools(inv, character | null, { pinned })` makes each pinned slot's pool exactly that piece and that piece the slot's current one, whoever wears it and whatever the filters say; nothing else is current, and the pinned slots leave `optionalSlots`, so the "one per slot" row reads `Σ x = 1` there and both solvers keep the piece. The panel's locked slots are ignored: the placed pieces are the lock, and an empty slot is always filled when a piece helps. The hand rule holds in the pools as well as in the solvers: a pinned two-handed weapon empties the one-hand slot's pool, and a pinned one-hander keeps two-handed weapons out of the other hand. With no character (`character` null) nobody's suit is current and every worn piece counts as another character's, so the pool is the pieces nobody wears plus the pinned ones. A fill is never saved as a run nor answered by one, and has no warm start. The server refuses a pinned serial that is not a gear piece of its slot in the scans, and a pinned two-handed weapon beside a pinned one-hander.

Every gear slot is searched, so a placed sash is pinned like any other piece: with LRC 20 under an LRC requirement of 100 it leaves the rest of the suit 80 to find. `app/manual-handoffs.test.mts` checks that case in both solvers and fuzzes random pinned subsets in any of the nineteen slots against brute force over the unpinned slots in both solvers.

## Floors, hard and soft

A hard floor becomes a single row, `total_d ≥ floor`, plus a constant bonus (`HARD_FLOOR_BONUS = 1e7`, matching `scripts/optimizer-core.mts`) added to every feasible suit's score as `scoreOffset` — the same trick the JS core uses, so scores from the two paths are directly comparable. A soft floor (or a hard floor demoted to soft, see below) gets a binary "met" indicator `y_d` and a continuous partial-credit variable `s_d`: `t ≥ f·y`, written as `t − (f − minReach)·y ≥ minReach` so that `y = 0` leaves the total free down to the lowest any suit reaches (the plain form `t − f·y ≥ 0` forbade every negative total outright, so HiGHS could prove a worse suit optimal), ties the indicator to actually reaching the floor, `s ≤ k·t` and `s ≤ bonus·partial·(1 − y)` cap the partial credit below it (`k = bonus·partial/floor`), and the objective pays `bonus·y + s` — full credit at the floor, a jump, `floorPartial × bonus × t/f` below it, matching the core's own soft-floor formula to the decimal.

**Negative totals.** A property can total below zero (an item that trades away mana regen for a big HCI number, say). The plain `s ≤ k·t` row would make such a suit infeasible outright when `t < 0` (since `s ≥ 0` too), rather than giving it zero credit like the core does. The fix is a second binary `u_d`, added only when some combination can drive the total negative (`minReach < 0`): the k-row becomes `s ≤ k·t + k·N·u` (`N = −minReach`), so `u = 0` leaves the row unrelaxed (forcing `t ≥ 0` there) and `u = 1` relaxes it enough that any reachable negative `t` still satisfies it, paired with a row that forces `s = 0` outright when `u = 1`. Together with the met row's `minReach` form above, a suit with a negative total on a soft-floored dimension therefore scores exactly like the core: zero credit on that floor, nothing more.

**Unreachable floors.** Before adding any row for a dimension, the model computes each slot's per-item maximum and sums them — the best total any suit could ever reach (`propertyReach`, exported so the diagnostics below use the same bound, and kept on the built model as `BuiltMip.reach`). For an OPTIONAL slot that per-slot maximum includes a phantom 0 (leaving the slot empty is always a real choice there); for a slot the "one per slot" row already forces filled — not optional, and currently worn — there is no such choice, so its term is the max over its own real candidates alone, with no 0 folded in (the same required/optional distinction `scripts/optimizer-core.mts`'s own `sufHi`/`sufLo` pruning bound makes). The two hand slots count together, as the better of a two-hander with the one-hand slot empty and the best one-hander plus the best non-two-hander in the second hand, since summing both maxima would credit a suit the hands row forbids. Getting this wrong for a required slot whose every candidate is negative in the floored dimension overstates reach, reports a genuinely-unreachable floor as reachable, and only surfaces the truth as HiGHS declaring the whole model `infeasible` — see "Jointly unreachable floors" below for what that costs. A hard floor above the (correctly computed) reach is never turned into a hard row at all (it would make the whole model infeasible for no useful reason); it's demoted to soft with no `y` column (nothing can ever meet it, so there is nothing to indicate) and listed in `unreachableFloors`; the page shows the `floor_unreachable` diagnostic for it, with the best possible (see Diagnostics below). A soft floor out of reach likewise gets no `y` column, but is not listed: it is a preference, not a requirement.

**Jointly unreachable floors.** Each hard floor can be individually reachable while no single suit reaches all of them at once — that shows up as HiGHS returning `infeasible` on the first solve, not as a per-dimension unreachable flag. `exact-solver.mts` retries once with every hard floor rebuilt as soft (`hardAsSoft: true`) so the fallback still reports the best suit that honestly exists, marks `floorsConflict: true`, and if even that retry can't produce an incumbent, reports the heuristic's own suit with `solver: "fallback"` and `fallbackReason: "no suit satisfies the required floors"` rather than inventing an answer. The one rule this whole path exists to uphold: **the heuristic's result is never shown as meeting the floors without the requirements report** — the page's chips/unmet-requirements panel is computed from the actual suit returned, independently of what the solver claims, so a fallback suit that misses a floor is always visible as missing it.

## Diagnostics

`app/diagnostics.mts` names the settings that work against a build, each with the change that would fix it (issue #217). It is pure and browser-safe. The type, `Diagnostic` (`code`, `level` warn or info, `property`, `message`, `values`, `actions`), lives in `app/runs-types.mts`; later codes (`weight_dominates`, `swing_linear`, `swing_next_step`) only add to `DiagnosticCode` and `DiagnosticAction`.

- `floor_unreachable`: a floor above `propertyReach`'s bound, hard (warn) or soft (info). A floor exactly at the bound is reachable and raises nothing. "Best possible" is min(cap, bound) in the player's terms: held at the Resisting Spells minimum on a resist (`mins`), plus a planned buff's share (the floor before the buffs, `prof.buffs.floors`, less the floor after them), rounded down. A floor at or under its resist's minimum is met by every suit and raises nothing. Actions: Lower to that number (left out when it is 0 or less) and, for a hard floor, Make soft. A resist floor set above its cap is clipped to it, and the sentence says "(its cap)". For one property the bound is the exact optimum, so this costs no solve.
- `floors_conflict`: a hard floor the returned suit misses although one suit could reach it on its own, with the suit's value. With `floorsConflict` set the sentence says the floor can't be met together with the other hard requirements; without it (a timeout that left only the heuristic's suit) it says no such suit was found within the time limit. Actions: Make soft, Lower to the suit's value. An alternative suit's card leaves these rows out, since their values are the best suit's.
- `weight_dominates`: a weight that swamps the others, on the result only. A property's worth is its weight times its typical range (`vault-lib.mts`'s `typicalRange`: the registry's `typical` for a property the shard rules give no cap, else the build's cap before buffs in the player's terms, `playerCaps`, else 15 for a skill bonus; none, and the property is left out). Its share is |w × min(total, cap)| (a resist held at its minimum) over the sum of those terms for every weighted property on the suit found, floor bonuses and the tag penalty left out. It dominates when its worth is at least `DOMINANT_WORTH` (3) times the median worth of the OTHER positively weighted properties (with none other there is no check) and its share is at least `DOMINANT_SHARE` (25%). A thin suit (a new character, a small or narrowed pool) makes any big weight look dominant, so nothing is raised when the suit's score from the positive weights is below `THIN_SUIT` (half) of Σ w × min(reach, cap), with `reach` from `propertyReach`. Action: Set weight to the others' median ÷ typical, to one significant figure (a melee main's luck at weight 3: 3.6 times the others' median of 420 and 33% of the score, suggested 0.8). Saved weights keep their meaning; nothing is normalised.
- `swing_linear` (warn): swing steps were asked for, but SSI was scored per point, with the reason (the pool's weapons have different speeds, or none has a known speed). Action: Lock the hand the suit's weapon is in, offered only when that weapon is the one worn there, since a lock keeps the worn piece; otherwise the sentence says to equip the weapon and lock its slot.
- `weapon_missing_flag` (warn): the build requires weapon properties (pool `weaponMustHave`) and a locked hand holds a worn weapon without them. The lock wins, so the weapon stays; the sentence names the weapon and what it lacks. No action (no action kind unlocks a slot).
- `no_weapon_with_flag` (warn): the requirement left out every weapon the other settings let through, so the suit is built without one (the hand slots are optional in both solvers). No action.
- `swing_next_step` (info): steps are off, and the next faster swing step is within 10 SSI of the suit's effective SSI ("SSI 45 swings every 2.0 s at this suit's stamina (89). 51 would make it 1.75 s, and so would 1 more stamina."; the stamina half only when one stamina band up reaches the step). Actions: score swing speed by step, and an SSI requirement at that step (a `setFloor` that sets or raises the requirement and makes it soft, so it can't conflict with the other hard requirements; every other `setFloor` lowers).

`POST /api/optimize` answers `diagnostics` (the floor ones) right after the pools are built, before the search starts. The worker (`app/optimize-worker.mts`) adds the full list to the result on both solver paths, so a saved run keeps it; if computing them fails, the result goes out without them and the server logs a warning. A malformed hand-built profile is read as far as it goes (a non-list `hardFloors` counts as none). `unreachableFloors` stays on the result for MCP clients and for runs saved before SOLVER_VERSION 6, which the page draws from it.

## Swing steps

A swing's delay moves in whole steps, so SSI between two steps buys nothing (issue #217). `app/swing.mts` holds stock ServUO's formula (ML and later, `BaseWeapon.GetDelay`): ticks = max(5, floor(N · 100 / (100 + S))) with N = round(4 × weapon speed) − floor(stamina / 30) and S the effective SSI (gear plus the buffs' share, capped at 60), and a delay of ticks × 0.25 s. Every stock weapon speed is a whole number of quarter seconds; a speed that isn't is rounded to the nearest one (off by at most a tick). The least SSI for a delay of t ticks is floor(100 · N / (t + 1)) − 99. Stamina is full stamina: raw DEX (the scan's DEX less the worn suit's DEX bonus), the gear's Stamina pool (`stamPool`, DEX bonus plus Stamina Increase) and the buffs' in-cap shares on both. Two known errors: the game reads current stamina, so a tired character swings slower than shown, and gear DEX past the 150 stat ceiling adds no stamina in game but counts here (it matters only near DEX 150). The formula, the 0.25 s rounding, the 1.25 s floor, the stamina term, the cap of 60 and whether Divine Fury counts toward it are unverified on the shard (#207).

A weapon's speed comes from its tooltip (`extras["weapon speed"]`), as `OptItem.speed`. The profile's intent flag `swingSteps` (absent means off, a spec carries it only when on, templates carry it) asks for SSI by step. `planBuild` puts the character's swing on the profile whenever there is a character (`swing: {stamBase, refStamina, steps}`: stamina before gear, the worn suit's stamina, and the flag), and nothing without one.

**The step table.** The worker resolves it once, before either solver runs (`stepsFor`): steps need the flag, a positive SSI weight (a negative one stays per point, unsaid) and one weapon speed across the hand slots' candidates (`weaponSpeedOf`; a two-hander is no candidate while the one-handed slot keeps its worn weapon, and a one-hander none while the two-handed slot keeps a worn two-hander). Otherwise SSI stays per point and `swing_linear` says why. The table (`stepTable`) has one point `{ssi, stam, credit}` per delay reachable in each stamina band any suit can be in (the bands span the Stamina pool's `propertyReach` range): `ssi` is the item-terms SSI that delay needs in that band (the buffs' share taken off; it can be 0 or less), `stam` the gear Stamina pool the band needs, and `credit` what that delay costs in gear SSI at the reference (worn) stamina, at least 0. A delay reached only by more stamina keeps that price, so one band up can credit more than 60. Points another beats (no less credit for no more SSI and stamina), and points needing more item SSI than any suit reaches (`propertyReach`), are dropped. The best credit a suit reaches equals the credit of its own swing priced from the formula (`app/swing.test.mts` checks it for every SSI and stamina).

**Scoring.** With `profile.ssiSteps` set, SSI is worth `weights.ssi` × the largest credit among the points the suit reaches (SSI total ≥ `ssi` and Stamina pool total ≥ `stam`; 0 when it reaches none), in place of `weights.ssi` × min(SSI, cap). SSI floors still read the plain total. The core (`optScoreVector`) adds `ssi` and `stamPool` to its space, treats more stamina as better in dominance pruning, and bounds the step term at the top of the reachable range (the credit never falls as either total rises; it is not concave, so the item-coupled bound leaves it out). The MIP skips SSI's `c` column and adds one binary `a_p` per point with cost `w × credit_p`: Σ a_p ≤ 1, and `a_p = 1` forces t_ssi ≥ ssi_p and t_stam ≥ stam_p, each in the floor rows' form t − (v − minReach)·a ≥ minReach (no row when v is at or below the lowest total any suit reaches). The MIP start sets the best point the start suit reaches. `app/solver-fuzz.test.mts` checks both solvers against brute force with an oracle that prices each suit's own swing from the formula. **HiGHS is the solver that proves a step-scored build.** The core's own exact search stays correct but its bound on the step term is loose (it takes the best SSI and the best stamina piece in every remaining slot at once), so with steps on it may not finish its proof within the budget; the app's exact path proves through HiGHS and runs the core only as its heuristic.

**A result's swing.** The worker puts `swing` on every result whose suit holds a weapon with a speed and whose build has a character, steps on or off: the weapon's speed, the suit's stamina, its effective SSI, the buffs' share, the delay and the steps at that stamina (`swingOf`). A suit that leaves the hands empty is scored as if it held the weapon (wrestling has a speed of its own): a stated approximation, harmless for a build that carries a weapon. SOLVER_VERSION 7.

## Score mapping

A suit's score, as the rest of the app understands it, is `objective + scoreOffset` (`HARD_FLOOR_BONUS` per satisfied hard row, folded in once at build time rather than carried as a variable) — `toScore()` in `exact-solver.mts` applies this to every value HiGHS reports (primal, dual, the final objective) so `bestScore`/`bound`/`gapPoints` are always in the same units the rest of the page already shows.

## The MIP start and warm start

`startVector()` builds a full column assignment from the heuristic's own best suit (every `x` set to match it, every `c`/`y`/`s`/`u` column computed to be consistent with those totals) and hands it to HiGHS as a MIP start, so the exact search begins already at least as good as the heuristic — it can only find something better or prove that suit optimal, never regress from it. The server's warm start (the character's newest saved suit, one more starting point for the heuristic) maps each saved piece onto this run's candidates; where the saved piece is not one of them, a slot that may not be empty (a locked slot, Manual's pinned piece) keeps its current piece, else its first candidate. It used to become empty there, a suit no search may return, and the search stuck on it (SOLVER_VERSION 4).

## k-best alternatives

Finding the next-best suits is repeated re-solving with one more no-good cut added each time: `Σ_{picked} x − Σ_{unpicked} x ≤ |picked| − 1` over every `x` column. The naive form `Σ_{picked} x ≤ |picked| − 1` also excludes a superset of the picked suit — exactly the case where a tie just adds a zero-value item into an empty optional slot — so the proper cut subtracts the unpicked columns too. Each alternative costs one more solve; the loop stops early once a candidate scores below the tolerance the caller asked for, or once the time budget is spent. The hard floors stay rows in the model, so every alternative meets them; the core's own branch-and-bound also lists suits that miss a hard floor when they fall within the tolerance, so with hard floors the two lists can differ in length (HiGHS's is the one the app shows).

## Rarity preference

A build may prefer higher- or lower-rarity pieces among equally good suits (issue #262): intent field `rarity` (`"higher"` or `"lower"`, absent means any; templates carry it and a run's settings keep it). `planBuild` turns it into `opts.tieBreak = { rarity, tolerance: 0 }`: it breaks exact ties only, and "Within points" plays no part (a list knob silently trading score for rarity was the wrong coupling). The solvers take any tolerance, so a later "give up some points" setting is wiring only. `POST /api/optimize` stamps a `tieCost` on each pooled and worn piece from its rarity line and the shard's ladder (`rarityRank` in `app/item-query.mts`, Reforged ranking with its base tier, no line or an unknown name ranking 0): "lower" costs a piece its rank, "higher" the ladder's length less its rank, and an empty slot costs 0 either way, so padding an empty slot never helps (with "higher", a piece with no rarity line loses every tie to an empty optional slot). A build with no preference has no `tieCost` and no `tieBreak`, so its run key and result are what they were, with no SOLVER_VERSION change.

The solvers then run a second stage: among suits scoring at least the best less the tolerance that meet every floor (hard or soft) the best suit meets, the lowest summed tie cost, the higher score on an equal cost. Scores within `TIE_SLACK` (1e-3, `app/mip.mts`, the solvers' score precision) are equal, the same in HiGHS's row, the core's rule and the exact solver's guards (HiGHS's presolve called a 1e-6 row infeasible on a suit that met it exactly). The sum is a plain sum of ranks: one Legendary piece (8) counts as much as two Major Magic Items (4 + 4). The floors are fixed, not scored, so the preference never gives up a requirement. When several suits tie for the best score but meet different floors, both solvers hold the floors of the same one: stage 1's suit, handed to the core as `tieBreak.topStart`.

- **HiGHS** (`app/exact-solver.mts`): stage 1 is the usual solve with three quarters of what is left of the budget. Stage 2 (`tieBreakModel` in `app/mip.mts`) starts from stage 1's suit as `startVector` works it out (so a floor the suit meets counts as met even when an unproven incumbent left its indicator at 0) and copies the model: the objective becomes each `x` column's `tieCost`, minimized; each met floor's `y` is fixed at 1; one row holds the stage-1 objective at least the suit's value less the tolerance and the slack, leaving out the fixed `y`s and an unfixed hard-as-soft `y` but keeping an unmet soft floor's `y` (a suit meeting it gains its bonus); none when nothing is left (a floors-only build). It gets the rest of the budget, or half of it when other suits are asked for, so they keep a share. Alternatives still rank by score against stage 1's, and the first no-good cut is the returned suit. The hand-back to the core passes stage 2's suit as the warm start and the top-scoring suit (stage 1's, or the heuristic's when it leads) as `tieBreak.topStart`; the guards compare best scores and, where those agree and the same floors are held, costs. `proven` is the score's proof (stage 1 and the guards); a stage-2 timeout leaves it and sets `costProven: false`, which the Rarity row shows. The result's `tieBreak` is `{ rarity, tolerance, topScore, cost, costProven }`, with `bound` and `gapPoints` still stage 1's.
- **The core** (`scripts/optimizer-core.mts`): the hill climbing still maximizes the score. Every start's climbed suit, the warm start as given and the best suit are candidates; the cheapest qualifying one is then descended by single-slot swaps and weapon pairs, each pass taking the largest cost drop that keeps it qualifying. With `exact`, the branch-and-bound runs a second pass in tie mode (a quarter of the budget kept for it): leaves are judged by the rule, subtrees are cut on the score bound, an unreachable fixed floor, or cost so far plus each remaining slot's cheapest piece, and dominance pruning is skipped. The trim pass keeps every fixed floor. Its result's `tieBreak` is `{ topScore, cost, top, floors }` (the suit whose floors were held, and those floors; the exact solver and the worker pass on only `topScore` and `cost`).

## Progress: incumbent, bound, gap

HiGHS reports its own progress through callbacks (`mipImprovingSolution`, `mipLogging`); `exact-solver.mts` throttles these to one `progress` event per 250 ms and turns them into `bestScore` (the best integer solution found so far, i.e. the incumbent), `bound` (the LP relaxation's bound on how much better the true optimum could still be), and `gapPoints = max(0, bound − bestScore)` — the same absolute units as everything else the page shows, not HiGHS's own relative `mip_gap`. A `k-best` phase's events instead report `found`/`wanted`. When time runs out with no incumbent at all (a large pool, a tight budget, no floors conflict), the job reports `proven: false` with the heuristic's own suit as `best` and whatever bound HiGHS reached — an honest "best found within the time budget", never silence. `bound` and `gapPoints` are `null` whenever HiGHS has not yet reported a dual bound at all — the common case early in a solve on a small model (not just an edge case), and the case for a timeout that never got an incumbent either; the page renders "no bound yet" in the live progress line and "no bound established" in the saved verdict for exactly this state.

## The time budget

`timeBudgetMs` is wall-clock time for the whole job. The heuristic's seeded-random restarts stop once half of it is spent (the core's `heuristicBudgetMs` option; the fixed starts — the worn suit, the greedy seed, the gradient seed, the warm start — always run), so HiGHS always keeps at least the other half. Every HiGHS call — the first solve, the `hardAsSoft` retry, each alternative — gets only what is left (a limit of 0 still returns the MIP start as the incumbent), and the alternatives loop stops once the budget is spent. A heuristic-only run (Exact off) honors `timeBudgetMs` too: its random restarts stop once the whole budget is spent (15 s when none is given, which is what the page sends with Exact off).

## When the model and the core disagree

The winning suit is always re-scored by the core. Three guards compare that re-score with HiGHS's objective and the heuristic's score: the core finding more than HiGHS reported, the core scoring HiGHS's suit below HiGHS's objective, and the heuristic's suit beating HiGHS's. Any of them means the model does not match the core's scoring — a modeling bug, not a race — so each one reports the better suit with `proven: false` and posts a warning naming the HiGHS status, its objective and the heuristic's score. After an `optimal` status HiGHS's bound is then no bound on the core's scores, so `bound` and `gapPoints` are `null`. None of them fails the job. (A heuristic suit beating a `timeLimit` incumbent is the one legitimate case — the race was simply lost — and keeps its bound.)

## Saved runs

A manual run (Manual's Save as run, `manualRun`, method `manual`) is never reused: nothing was searched for it, and its key starts `manual:`. A saved run (`app/runs-lib.mts`) answers a new request with the same key when it was proven, was a plain heuristic run, or was an unproven exact run that already had at least the budget now asked for. A `solver: "fallback"` result (HiGHS failed to load, or the floors-conflict retry ran out of time) is never reused. The key hashes the effective profile, so resist cap overrides (which change its `caps` and add `resistCapOverrides`) are part of it. The key includes `SOLVER_VERSION`, bumped whenever the model, the orchestration or the core's scoring changes, so a result an older, since-fixed model reported as proven is never served again.

## The pool-size warning

`POST /api/optimize` counts the candidate pool (`meta.poolSize` if the caller already computed it, else counted from the pools it was sent) and sets a warning on the job — surfaced in the POST response body and shown above the progress panel — once it exceeds 50,000 candidates, since a pool that large is outside anything the model has been measured against (see below).

## Measured performance

All of the following is single-threaded WASM (`mip_rel_gap` 0), from `app/bench/REPORT.md`'s addendum: on synthetic realistic inventories the model proves 20,000-item pools (3,900–4,700 candidates after slot-splitting) in 1.1–2.1 s and 30,000-item pools (5,900–7,100 candidates) in 1.6–2.5 s; pushed further the same morning, a 50,000-item all-gear pool (31,900–38,400 candidates) still proves in 7.6–8.6 s, with no cliff observed up to 38,000 candidates and solve time growing roughly linearly at about 0.2 ms per candidate — the LP's size, not a search explosion. On the real (non-synthetic) inventory fixture the four default templates prove in tens of milliseconds of actual HiGHS time (Task 2's measurement: melee 129 ms, caster 29 ms, archer 21 ms, tank 23 ms, all proven), and a generated 3,000-item cell proves in about 4.4 s of HiGHS time against a JS branch-and-bound reference that had not finished proving the same cell after 60 s (though it agreed with HiGHS's score to the decimal where both had an answer). This is the empirical basis for the pool-size warning above: everything measured so far, up to and including 50,000-item all-gear inventories, proves in single-digit seconds.

**Nineteen slots** (issue #202, SOLVER_VERSION 5). Searching every gear slot instead of twelve costs little on real inventories, where few clothing pieces carry properties and the worn plain ones are kept (`optionalSlotsFor`). Measured as the page builds (Electron at 1440 × 900, the page's defaults: exact, 200 restarts, 5 other suits within 0 points; no buffs on), from Build to result on the maintainer's scans for four characters, main → this change: 2.3 → 2.2 s, 1.1 → 1.2 s, 3.6 → 2.7 s and 5.2 → 4.5 s, each proven both times; the last two had a tie alternative before and none now. Before the worn plain pieces were kept, the same builds took about twice as long, every on/off mix of a plain shirt or boots becoming an equal other suit and one more HiGHS solve. The core's own exact search keeps its speed the same way: its dominance pruning drops an optional slot's empty choice, outside the hands, for a piece that scores exactly like it (a worn plain pair of boots), else every such tie doubles the branch-and-bound (the fixture's melee proof with buffs took 7.7 s instead of main's 2.0 s, and ran out of budget on CI). The core's synthetic runtime check (`scripts/optimizer-core.test.mts`, 30 candidates in every slot) went from about 85 ms to 160 ms a run, in step with the slot count.

## Running the equivalence tests

`app/mip.test.mts` is `buildSuitMip`'s own structural unit tests (columns, rows, the negative-total guard). `app/solver-fuzz.test.mts` is a seeded brute-force check: 2,000 small generated inventories (negative values, negative weights on capped and floored properties, soft and hard floors, locked slots, shields and two-handers) where exhaustive enumeration of the core's `scoreSet` is the oracle for the heuristic, the core's exact search and `solveExact`. `app/solver.test.mts` checks `solveExact` against the JS core: each default template proves through HiGHS and agrees with the core's own proven optimum, soft floors and k-best alternatives match, an unreachable hard floor and a jointly-unreachable pair of hard floors both behave as described above, a negative soft-floor total gets zero credit, a HiGHS-unavailable environment falls back honestly, and a `[slow]` 3,000-item generated cell proves inside its time budget. Run them with `node --test app/mip.test.mts app/solver.test.mts`, or `TEST_SKIP_SLOW=1 node --test app/solver.test.mts` to skip the generated-cell case; both are part of `npm test` (see `TESTING.md`).

## The core's own search (`scripts/optimizer-core.mts`)

`optimizeSuit(pools, current, profile, opts)`: greedy + 200 restarts of single-slot hill-climbing with the weapon/shield pair handled together, then (with `opts.exact`) dominance pruning per slot and branch-and-bound with a per-dimension optimistic bound; returns `method`, `proven`, `nodes`, `pruned`. Caps are hard (`w·min(total,cap)`). Floors are HARD by default (profile `hardFloors`, bonus 1e7 — no mix of other gains can buy a miss; the page sends every floor not listed in the profile's `softFloors`); soft floors pay `floorBonus` (1000) when met with partial credit below. Lesson learned early: with soft floors the optimizer can trade away a hard requirement (e.g. a reagent-cost floor) for two resist floors plus a casting-speed stat, which is why hard is the default. Locked slots = empty pool for that slot and the slot removed from `optionalSlots` so only the current item remains. Verified against brute force in the tests (a hand-built case plus 150 random suits with caps, hard and soft floors and the tag penalty).

**Tighter bound.** Besides the per-dimension optimistic bound, the search tries an item-coupled one: for dimensions whose weight is >= 0 and whose item values are all >= 0, `w·min(t, cap)` is concave, so the most the remaining slots can add is the sum, over slots, of the best single item's gain at the current totals. It stops the bound from combining the best of every property from different items. It is computed only when the cheap bound fails to prune and 2+ slots remain, and the smaller of the two is used. Measured on a real inventory: a melee-profile build went from 148.4 s / 1.24 billion nodes to 0.7 s / 1.0 million nodes for the same proven suit. Tried and rejected: folding floors into the coupled bound through their concave envelope (valid, but the huge floor bonuses dominate the per-slot sum and it was 4-50x slower).

**Exact search.** `opts.exact` runs dominance pruning per slot then the core's own branch-and-bound with a per-dimension optimistic bound (see Tighter bound above) — this is what the `[slow]` brute-force tests in `app/gear-vault.test.mts` prove against, and what `optimize-worker.mts` falls back to when HiGHS is unavailable. In the app itself, `opts.exact: true` instead goes through `app/exact-solver.mts`: the core's heuristic for a fast incumbent, then HiGHS (`app/mip.mts` + `app/mip-solve.mts`) explores the tree itself and proves optimality or reports a bound gap — see `docs/solver.md`. There is no longer a multi-thread branch-and-bound pool to escalate to when a single thread can't prove a cell (retired in Phase 3 along with the shared-search module that ran it): one job, one worker, HiGHS does the exploring.

**Other suits.** `opts.alternatives = {count, tolerance}` (exact phase only) makes the search keep its best `count + 1` leaves scoring within `tolerance` of the best: pruning then drops only subtrees whose bound is strictly below `max(best − tolerance, the list's lowest score once full)`, so ties survive, and dominance pruning is skipped because a dominated piece can still belong in a runner-up. The result carries `alternatives` (other suits, best first, never the best itself) and `altTolerance`. `app/exact-solver.mts` gets the same list from HiGHS by walking `k − 1` more no-good cuts (`addNoGood`) after the winning solve. Brute-force tested against every suit's score in `app/gear-vault.test.mts`. The page's Other suits / Within points inputs (defaults 5 and 0) feed it; the result panel lists each suit's differing pieces and every property total that moves (unweighted ones too), and Show renders that suit's sheet, plan and fetch list (`state.builder.altView`).

**Shield rule in dominance pruning.** A two-handed weapon may no longer knock out a shield on properties alone: the shield leaves a hand free for a one-handed weapon, so the swap is not always legal. The hill climbing usually hid this; the exact search could have missed a shield + weapon optimum.

**Scale.** See `app/bench/README.md` and `app/bench/REPORT.md` for the full write-up (fold time, payload size, per-slot pool sizes, dominance pruning, heuristic and exact phases, and the MIP-solver spike, `app/bench/mip-spike.mts`, that led to `app/mip.mts` + `app/exact-solver.mts` proving the optimum well past where the branch-and-bound search alone gives up). Read `REPORT.md` before touching the exact search's scaling — it documents where the cliff is and which levers are already tried.

**Warm start.** The server passes the character's newest saved suit as `opts.warmStart` (slot → serial); the core maps it onto this run's candidates and uses it as one more search start. It can never lower a result.

## Saved runs in the app, instant repeats and the weapon filter

Every finished build is saved (`<data>/runs/`), except Manual's fills (`pinned`); Manual's Save as run adds a manual run (`POST /api/runs`, method `manual`, no score, never reused). `POST /api/optimize` computes `runKey` first: a match that cannot be bettered returns `{cached: true, run}` and the page renders it at once with a "reused the run from …" pill. Saved runs live in a drawer that slides in from the right (the Saved runs button with a count in the sidebar's Character panel; closes with ×, Esc or a click outside; opening or comparing a run closes it; a filter box matches names and changes). It lists a character's runs newest first; each row's text is its name, or what changed from the run before it (`settingsDiff` in `vault-lib.mts`: floors, weights, soft/hard, locks, tags, pool flags, weapons, STR, restarts, budget). Opening a run shows its suit against today's worn gear, the sidebar-vs-run differences and a Load these settings button; ticking two or three runs and Compare shows their settings side by side, slot by slot, and property totals with each run's floors. A run made before the latest scan carries an "inventory changed" pill. The page sends `meta: {character, settings, inventoryStamp, poolSize, skipped}` with each build; meta is not part of the key.

Weapons filter: profile `excludeWeapons`, the weapon skills left out of the pool (any of `WEAPON_SKILLS`, matched against the tooltip's Skill Required line; empty = any weapon). A weapon of an excluded skill never enters the pool; shields, spellbooks and weapons with no skill line are never removed by it. A weapon with Use Best Weapon Skill (the tooltip flag) bypasses `excludeWeapons` while any of Swordsmanship, Fencing and Mace Fighting is still allowed, since it swings with the best of those three; profile `ubwsAnyWeapon: false` holds it to its own skill (absent means true). The old single choice `weaponSkill` is converted to "exclude every other skill" (`migrateWeaponSetting`) by `migrateProfiles` and the runs steps of `app/migrate.mts` only. `buildPools` returns `blocked` for a worn weapon the filter rules out, and the page drops it from the optimizer's `current` so the keep-what-you-wear rule cannot sneak it back.

Weapon properties filter (issue #214): pool `weaponMustHave`, the yes/no properties every weapon must carry (any of `vault-lib.mts`'s `BOOLEAN_FLAGS`; the page offers `WEAPON_MUST_HAVE`, Spell Channeling and Balanced). A weapon is a held piece with a Skill Required or Weapon Speed line (`isWeapon`), so shields and spellbooks are never held to it. `buildPools` leaves out every weapon without them, in both hands, and blocks a worn one, except in a locked slot (its `lockedSlots` option): there the lock wins and `weaponFlags.kept` names the slot. `weaponFlags.none` says the requirement itself left both hands' pools without a weapon: it is checked after every other filter, and a pool the other settings already emptied of weapons is not blamed on it. `runKey` holds `weaponMustHave` when it lists any (other keys are unchanged), since the pools can come out the same with and without it while the warnings do not. `POST /api/optimize` turns both into the `weapon_missing_flag` and `no_weapon_with_flag` diagnostics, answers them with the floor ones and puts them ahead of the result's own (`app/services/jobs.mts`). A spec stores the field only when it lists any.

## Profile semantics: paperdoll resists, pools, skill bonuses, race

- **Resist floors and caps are paperdoll values.** A paperdoll resist is the item total, capped and held at the Resisting Spells minimum, so `effectiveProfile(p, character)` (`vault-lib.mts`) passes resist floors and caps to the optimizer as they are, with the minimum beside them (`resistMinimum`, `mins`: The Resisting Spells minimum, above), and a race can raise a resist's cap (`getRules().raceCaps[p.race]`, e.g. an Elf's Energy cap of 75). The player's own per-resist cap overrides (`p.resistCaps`, the Builder's Resist caps section: paperdoll values, whole numbers 0-150) replace the shard's cap for that resist, floors included; `EffectiveProfile.resistCapOverrides` lists the overridden ones (absent when there are none, so a profile without overrides keeps its old shape and run key) and `profileResistCaps()` gives every resist's paperdoll cap for display. The requirement pills, the compare view and the sheets show each resist held at the minimum. `optimizerProfile()` and saved-run views both go through `effectiveProfile`, which reads its caps from `getRules().caps` merged with any per-profile override (`p.caps`) — `setRules()` must have run first, or it throws. Both the Resisting Spells minimum and the race cap overrides are shard rules now (`app/rules/<shard>.json`, see Shard rules below) rather than constants in this file.
- **Buffs shift the profile the same way.** With buffs on in Automatic, `plannedProfile` (`buffs.mts`) takes each buff's in-cap share off the cap, the floor and the minimum, caps gear STR/DEX/INT at what raw stats and the buffs leave to 150, and sets aside a resist override above the shard's cap on a resist a buff lowers. The solvers never see buffs, only the shifted caps and floors (docs/solver.md, Buffs).
- **Pools** (`toOptItem`): `stamPool` = DEX bonus + Stamina Increase, `manaPool` = INT bonus + Mana Increase, `hitsPool` = STR bonus ÷ 2 + HP Increase. Floor the pool when a breakpoint depends on the total (swing speed needs stamina = base DEX + stamPool), weight the parts.
- **Skill bonuses** from tooltip lines ("Magery +10") become properties `sk:<skill>` (`SKILL_NAMES`), weightable and floorable; `labelOf`/`fullOf` name them. `excludeSkills` (profile, "Forbid skill bonuses" chips) drops any piece with a bonus to those skills and blocks a worn one — useful for classes whose rules forbid mixing certain skills.
- **Locked one-hander:** when the one-hand slot has no empty option, two-handed weapons are not candidates (core). Before this fix the hill climber could swap in a two-hander and drop a locked one-handed weapon.

## Templates

A build's intent is one document, a **BuildSpec** (`app/build-spec.mts`): `intent` (`floors`, `softFloors`, `weights`, `floorBonus`, `resistCaps`: what "good" means), `buffs` (`on`, the buffs counted as always on, and `skills`, the numbers edited for them), `pool` (`lockedSlots`, `excludeTags`, `excludeSkills`, `excludeRoots`, `excludeWeapons`, `ubwsAnyWeapon`, `allowOthersWorn`, `allowGargoyle`, `medOnly`, `strLimit`, a number or `"character"`: the character's STR, else 125, and `weaponMustHave`, present only when it lists any), and the optional `goal` (nothing reads it yet) and `search` (`budgetMs`, `exact`, `restarts`, `altCount`, `altTol`; absent ones take `RUN_DEFAULTS` in `app/run-settings.mts`). `buildSpecError` is the one check a spec is held to and `buildSpec` fills in the defaults. `planBuild(spec, {character, worn, race, suit?})` turns a spec into a build: the profile the solvers score with and its buff plan, the pool settings `POST /api/optimize`'s by-character form takes, the search options, and the settings snapshot a saved run keeps. The page's Build, Manual's fill, `POST /api/optimize`'s by-character form (whose missing fields take the spec's defaults, so a missing STR limit is the character's, as on the page) and the MCP tools all go through it, so they plan alike.

`profiles.json` is schemaVersion 3: `characters["<name>"] = {race?, template?, spec}` (`characters["_nobody"]` is the Suit Builder's No character: its requirements, weights and `buffs.on`, built on the shard's caps as race human, with its buff numbers in ui-prefs `manualBuffSkills` rather than its own `buffs.skills`) and `templates["<id>"] = {name?, spec}` (a template's spec may leave out `buffs`; one that carries them sets the character's buffs when applied). A character's Automatic buffs and the numbers edited for it are its spec's `buffs`, saved the moment they change, like a view choice; `ui-prefs.json` keeps only Manual's what-if buffs (`manualBuffs`, `buffsCount`), No character's numbers (`manualBuffSkills`) and the other view choices. `migrateProfilesV3` (`app/build-spec.mts`) is the pure v2 → v3 conversion, run by the server when it reads the file (`app/store/profiles.mts`): each character's settings become its spec with `ui-prefs.autoBuffs[name]` and `ui-prefs.buffSkills[name]` as its buffs (a character with buffs but no saved settings gets the settings the Suit Builder showed it, the first template with race human, but only when it has a buff or an edit and the scans still have it), each template's settings its spec; a value the v3 check refuses is left out, key by key in a map or list, and logged; `profiles.backup-<date>.json` and `ui-prefs.backup-<date>.json` are written first, then the two moved keys leave `ui-prefs.json`. Earlier shapes go through `migrateProfiles` (`app/vault-lib.mts`) first: `archetypes` became `templates`, a character's `archetype` its `template`, the global `caps` moved to the shard's rules, a single `weaponSkill` became `excludeWeapons`. A template's settings are `TEMPLATE_KEYS` (`templateFrom` snapshots exactly those, so race, STR limit and skipped containers never enter one). **Built-in templates** ship per shard in `app/data/templates/<shard>.json`, are read at run time (`GET /api/profiles` answers them as `builtinTemplates`) and are never copied into `profiles.json`, so a release can change them; they are named `builtin:<id>` wherever a template is named, listed after the player's own as "Name (built-in)", and read-only: Update and Delete are disabled for them, Save as… makes the player's own copy. A character with no saved settings opens on the first template, the player's own, else the first built-in. Sidebar: a template `<select>` with Apply (copies the template into the working profile and sets `template`; Save profile persists it, as before), Save as… (prompt; snapshots the sidebar's settings as a new template), Update (overwrite the selected template, confirm) and Delete (confirm). Template edits go through the whole-file PUT (`app/ui/profiles.mts`, one write at a time). The pill beside the picker is `settingsDiff(template's settings, templateFrom(working))`: "matches X" / "modified from X" (hover lists the diff lines) / "template X missing" after a delete; it is recomputed on every input/change/click in the sidebar. `readControls()` copies the pool checkboxes, weapon exclusions, race and STR into the profile, and the panel draws them back from the profile. A saved run keeps its flat settings snapshot (`planBuild`'s), so `runKey` and old runs are unchanged; `specFromRunSettings` reads one back as a spec.

## Build jobs and the progress panel

`optimizeSuit` takes `onProgress(p)` + `progressEveryMs` (default 250). The snapshot carries `phase` (heuristic → prune → exact → done), `restartsDone/restarts`, `nodes`, `explored` (fraction of the exact search tree behind the search, pruned subtrees included, so it is a true 0..1 bar that reaches 1 exactly when the optimum is proven), `budgetMs`, `improvements`, `lastImprovementMs`, `floorsMet/floorsTotal`, `candidates`. The end of every phase emits unconditionally (the throttle once swallowed the last heuristic snapshot when all restarts ran inside one millisecond). The page (`runPanel` / `runBuild`) opens an `EventSource`, keeps one job in `state.builder.job`, disables the Build button, and ticks a heartbeat every 200 ms: green while progress arrives, warn after 4 s of silence, bad after 12 s ("probably hung, cancel and retry"), warn with "reconnecting" when the stream drops. Cancel posts to the cancel route and closes the stream; a cancel during the initial POST cancels the job once its id arrives; `pagehide` sends a beacon so a closed tab does not leave a worker running. Custom SSE event names must not be `error` (the `EventSource` native error event fires for it too): failures are sent as `failed`.
