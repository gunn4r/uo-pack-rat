# Suit Builder

Part of the UI docs: [`docs/ui.md`](../ui.md) has the hard rules, tokens, components and the dependency rules every screen follows.

The screen's five modules (`ui/builder.mts`, `ui/builder-start.mts`, `ui/builder-result.mts`, `ui/builder-manual.mts`, `ui/runs.mts`) share one session, `ui/builder-session.mts`: the selected character and its panel profile, the result, the running job, the saved runs and compare picks, Automatic or Manual, and the knobs, each set through a setter that fires `builderchange` on `document`. They never import each other: what one does for another (render the panel or the result, open a suit in Manual, load the runs) is a command in the session's `commands`, registered by its owner with `provide()`. Today a session is one character, one result and one job.

**Layout** (issue #272). The top bar is one line down to about 1366 px with the sidebar open: the title, the **Character** select, the **Template** select with its state badge and ⋯ menu, **Automatic | Manual**, then, held right as one group that never splits (`.b-top-acts`), **Settings** (`#b-settings`, with its ⌘, hint, shown pressed while the drawer is open), **Saved runs** and **Build** (`#b-run`, ⌘↵); both buttons carry `aria-keyshortcuts`. On a narrower window the selects wrap and the group keeps to the right of its row; at 720 px and under the select labels, the Saved runs word and the key hints go (still named for a screen reader), so the bar is three rows on a phone. The result takes the full width under it. Every setting lives in the **Settings drawer** (`#b-drawer`): a right-side overlay 560 px wide (`--drawer-w-wide`; the full width on a phone-width window) over the result's right side, the result staying where it is underneath. It is not modal, so the top bar's Build and the result stay in reach, and a build started with it open leaves it open. Its head reads "Settings" and the template's name and state ("Melee · modified"), with ✕; under it a built-in template's description (`#b-tpl-info`); then five tabs, a proper ARIA tablist (←/→, Home and End move between them): **Requirements** (the requirements, then **Never wear a bonus to** with a removable chip per forbidden skill bonus and **+ Skill**, its checklist), **Weights** (with the SSI row's Score swing speed by step), **Buffs**, **Pool** (the switches, Rarity and the chips) and **Advanced** (Search: exact search, restarts, time budget, other suits; Character: Race, STR limit and Casting school; Resist caps). The footer holds **Save profile**, **Save as template** (the template menu's Save as…), "N changes since the last build" / "No changes since the last build" (on its own line above the buttons at 720 px and under) and **Build** (`#b-run-foot`). The count is the number of lines `runSettingsDiff` names between the shown run and the panel's settings snapshot, the same diff behind the runs drawer's "Same settings as the panel", so an older run's absent fields, a list in another order or the time budget without exact search count as nothing, and Load these settings leaves none. While the run on screen is the one a build just showed, the count is taken from the settings that build was asked with, since a build answered from an earlier run carries that run's own search knobs; any other run shown (opened from the drawer, that same run reopened, another character) is counted from its own settings, as its banner is. It is repainted 150 ms after the last edit (any field, every search knob included) and is empty while no saved run is shown. A build started from the drawer (its Build, or ⌘↵ in one of its fields) leaves the focus there; the footer's Build is only marked disabled (`aria-disabled`) while it runs, so it keeps the focus. The Settings button and ⌘, (Ctrl+, off the Mac) toggle the drawer while the top bar shows the button (not in Manual or the compare view, nor behind a dialog or the Saved runs drawer); opening moves the focus to the selected tab, and ✕, or Esc from anywhere on the screen, closes it with the focus back on the Settings button (an open popover takes the first Esc; ⌘, with one open closes both). A popover opened from it closes with it. Each tab is a `tabpanel` holding one group or three (`b-sec-<id>`: `req`, `weights`, `buffs`, `pool`, then `adv`, `char` and `caps` under Advanced), and `focusIn` and `focusKnob` open the drawer on the group's tab before they focus a control, so Build's own refusals (an Advanced field, a resist cap out of range, a requirement or weight that is not a number) and a server refusal naming a field open it on the right tab. The last tab shown is the ui-prefs `builderTab` (a page's origin changes with every launch of the desktop app, so a view choice is kept by the server, not `localStorage`). Manual closes the drawer and hides Settings, Build and the template controls, as the old panel did. The buff picker (below) opens beside the drawer on its left (`besidePlacement`).

**Arriving** (issue #272). **First visit** (`ui/builder-start.mts`, `#b-start`): while no result is shown for the selected character (or No character), the result column is a main column and a side column that wraps under it when narrow (`.b-arrive`). The main column asks "What should <name>'s suit be for?" ("What should the suit be for?" for No character), then the template cards (four to a row, two at 1023 px and under): the panel's own template first, badged Suggested, then up to three built-ins chosen for the character's skills (`builder-model.mts`'s `suggestTemplates`: each built-in scored by the skill points of the trained skills, 30 and up, that its name, description, its buffs' casting skills and its casting school name, ties and the rest in catalog order), then up to four of the player's own templates, newest first, each with a one-line description (a built-in's own, else its Needs line; "Saved Oct 7" for the player's own, from the `savedAt` that Save as and Update now write, or "Your template"). A card does what picking its template in the top bar's select does, then applies it as the template menu's Apply does (`builder.mts`'s `pickTemplate`), so Build builds from it; the selected card is the panel's template (`aria-pressed`). "All N built-in templates" focuses the top bar's select. Under them a read-only summary of the panel: "<template> will build for" with Needs (`needsLine`: the requirements, the five resists as one "Resists 65" when alike, a soft one marked "(soft)"), Buffs, Pool (`poolLine`: the weapons allowed, the gear pieces scanned, from `GET /api/items` filtered to the gear slots, and the rarity preference) and Search (`searchLine`), each term a link that opens the Settings drawer on its tab; and "What matters most", the top four weights by importance (`topWeights`, the resists as one row when they weigh alike) as importance bars in the Weights tab's style (`.b-wbar`), each opening its weight in the drawer (`tuneWeight`), then "+ N more in Settings" on the Weights tab. Last the big **Build <name>'s suit** (`#b-start-build`), which is Build. The side column has **<name> is wearing now** (`#b-wearing`, not for No character) with when it was scanned, the five worn resists (held at the Resisting Spells minimum) and up to four gauges, part 2's style without the tick, for the top weighted other properties against their caps; and **Other characters' recent runs** (`#b-others`, `runs.mts`'s `otherRunsCard`), the latest run of up to three other characters still scanned (`otherCharactersRuns`), named as the drawer names them, each switching to its character and opening that run the way the drawer does; hidden with none. The view is redrawn with every panel edit, keeping the focus on the control that had it. **Coming back**: when the builder first shows a character (a page load or a character switch: `selectCharacter`, then `loadRuns(true)`), its latest saved run (`latestRun`) is opened as the drawer opens one, unless a result or a build is on screen by the time the list is in; a refresh of the list or of the scans never opens one, so a result on screen stays. A result has **<name>'s runs** beside it (`#b-myruns`, `runsCard`): the latest three runs, the shown one in bold, **New build** (`#b-new-build`, back to the first-visit view, disabled while a build runs) and **All saved runs** (the drawer); the score breakdown stays in the headline card. A saved run's one banner (`.saved-run` in `#b-msg`, `paintRunBanner`) is the "Saved run · <time>" line with the settings diff and Load these settings, or, when a scan is newer than the run (`gearChangedSince`; no scan or no time recorded is no change), "This is your build from <time>. Your gear changed since: newer scans came in" with ", and N settings changed" (the footer's count) and the diff under it, **Build again ⌘↵** and Load these settings; a scan landing while it is up repaints it. Which pieces changed is #291's.

The panel (`ui/builder.mts`) is drawn from state, never read back from the DOM: the session's `profile` holds the template settings, requirements, weights and candidate pool, and its `knobs` object holds the solver fields as typed strings (STR limit, which sits beside Race because it decides which pieces are candidates at all, and the Advanced search options), so a bad value can sit in its field with its error until fixed. A build, a saved profile and a saved run's settings snapshot (`ui/runs.mts`'s `settingsSnapshot`) all read from there. Groups redraw one at a time (`redraw(id)`), so an edit keeps the drawer's scroll and focus. The numbers and words the screen shows (the changes count, validation messages with the allowed range, resist outcomes, other-changes badges, compare rows and best values, run labels and badges) come from `ui/builder-model.mts`, which has no DOM and is tested directly (`app/builder-model.test.mts`); its `KNOB_RANGES` come from the server's own table (`app/run-settings.mts`'s `RUN_SETTING_LIMITS`).

**No character** (issue #12) is the character select's first option in both modes (`#b-char`, value `NOBODY` = `"_nobody"`, defined in `app/scan-schema.mts` beside `isPseudoCharacter` and re-exported by `app/vault-lib.mts`), offered once there is a scanned character. In Automatic it is a character of its own: its panel is a normal `profiles.json` entry under `_nobody` (the first template until Save profile, then what was saved), its builds are saved and reused as runs under `_nobody` (`#/builder/_nobody`, the drawer's `?character=_nobody`), and every list of characters leaves it out (`roster.mts`'s `characterNames`). It builds on raw item totals from the pieces nobody wears: no Resisting Spells minimum, no stats and so no swing, the shard's caps (race human: the Race control is hidden, STR limit stays at 125 by default), and the Faster Casting cap of the Casting school named ("cap 2: no character" from skills); Allow gear worn by other characters adds the worn pieces, and the Resist caps section can still raise a cap. Its buffs are its entry's `buffs.on`, with No character's numbers, the ui-prefs `manualBuffSkills` Manual edits too. Picked in Automatic it also sets Manual to No character (`manualFor: "none"`); picked in Manual it leaves Automatic's character as it is. Before a build the first-visit view asks what the suit should be for, with no worn suit beside it; a result reads "Best suit · No character", its Plan's Now column is empty, its Fetch list holds every piece, the "after the change" card is **Suit totals** (the items' totals, `sheetParts` with no character), and Start from this result opens it in Manual's No character. Grab puts the pieces in the backpack of whichever character the bridge runs on (the toast names it), and is disabled with "Log a character in to grab" while no bridge is online. The labels go through `builder-model.mts`'s `who` ("No character" for `_nobody`).

**Templates** (issue #212) are picked in the top bar (`#b-tpl`): the shard's built-ins first, in a "Built-in" group under their own names, then the player's own under "Your templates" (`templateRefs` keeps its order, the player's first, for a new character's default and the MCP error text). A template with a `description` shows a line at the top of the Settings drawer (`#b-tpl-info`): a "Built-in" badge for a built-in, the description, "Loads:" with the buffs it turns on, and for a built-in "Source:" with each source page as a link (`builder-model.mts`'s `sourceTitle`), or "UO Alive defaults" when it lists none. Save as and Update store the character's Automatic buffs with the template (`templateSpecFrom(profile, buffs)`, without their numbers, which are the character's); the badge beside the picker counts a buff list that differs from a template's as one diff line ("Buffs: +Enemy of One, −Consecrate Weapon", `templateBuffsLine`), and a template saved without buffs ignores them. Apply on a template with buffs sets the character's Automatic buffs and, when Manual is for the same character, Manual's list too (its totals set to count buffs when the list has any), as one undo step named "<template> buffs" (`templateBuffs`); with No character Manual is left alone. The MCP tools plan with a template's buffs when none are named.

**Resist caps** is the last group under Advanced. One row per resist: the cap as a number field, "shard cap" when it is the shard's (race-aware), else an accent outline, a "raised from 70" / "lowered from 70" badge and a reset button. A value outside whole numbers 0-150 keeps its error under the row (`resistCapError`) and is held as typed in `capDrafts` (the profile keeps the last good cap), so Build refuses it even with the drawer closed, opening the drawer on the field; a race change drops any override that equals the new race's own cap (`pruneResistCaps`); a cap typed back to the shard's value removes the override (`withResistCap`), so a profile only stores real overrides (`resistCaps`, saved with Save profile, templates and each run's settings snapshot). The result measures resists against the build's caps (`profileResistCaps`): the resist tiles read "86 / 95" with "Cap raised from 70" under them, the outcome lines ("At cap", "N over cap") use the raised cap, the full now → after sheet gets `sheetNode(..., { resistCaps })` (the Characters screen passes none and keeps the shard's), a saved run's badge reads "Fire 86 · cap 95", and compare judges each run by its own caps and adds a "Resist caps" outcome row when any column overrode one. The Requirements note names the character's Resisting Spells minimum and says a resist requirement at or under it is met by any suit (`resistMinimumText`). A resist requirement set above its cap is kept (a saved profile may carry one) but counts only up to the cap, as `effectiveProfile` clamps it for the solver: its row warns "Counts only up to the Fire cap, 70" (`floorCapWarning`), and every view that says whether a requirement is met (the headline, the tiles, run badges, compare) uses `effectiveFloor`, min(floor, cap), so they all agree with the solver. The full sheet's Properties header reads "build cap" instead of "shard cap" when the build overrode one.

**Buffs** (Automatic, issue #12) is the Settings drawer's Buffs tab. It lists the buffs by school (issue #272), in `BUFF_GROUPS` order, each group's heading the character's skill in it when the group is a skill (`isSchool`: "skill 68.2", or "not trained"). A buff is a row with its switch (`#b-bf-<id>`, `data-buff`), its name, its effect tags (`buffs.mts`'s `buffEffectTags`: what its definition moves at the character's numbers, each property in its one word from `TAG_WORDS`, "hit chance up · damage up · swing speed up · defense chance down", all five resists moving together as "resists up", a cap change as "defense chance cap up", then its text-only parts, or "no suit effect"; a tag that lowers something for the suit, "defense chance down", is tinted in the warn tone) and a line. Whether it counts is the plan's own answer (`buffAvailability`: `buffNeeds` at the numbers a build plans with, `buffSkillValues` with the typed edits), so the tab never greys a buff a build counts: one the plan blocks is greyed (`.b-bf-cant`) with what it needs, in the warn tone with an alert icon ("Needs Necromancy 99"), and one that leans on a skill the scan lacks, which the plan counts at its default, says "Spellweaving not in the scan: counted at 120"; else the line is its note. A school's heading reads a typed number ("skill 90 (typed)"), else the scan's skill, "not trained" or "not in the scan". Until **Show all** (`#b-bf-all`, kept for the page session) the list holds what the character can use, entries that need no skill included (potions, food, the debuffs), and any that are on; the lead line says Show all adds the ones that need more skill or a skill not in the scan. A greyed buff can still be turned on, except another race's passive. With No character, or a scan that carries no skills, every buff is listed with no skill shown. Turning one on or off redraws the list only (`#b-bf-list`), with the focus kept on its switch, so the picker's anchor stays the same button: Esc closes the picker onto it and its `aria-expanded` follows. Under the list, the help line and **Search and edit numbers** (`#b-buff-add`), which opens the same picker as Manual's (`createBuffPicker`, its ids prefixed `abf` so they never clash with Manual's `bf`; its groups, tags, fields and notes are Manual's, below) in a popover beside the drawer, on its left (`popover`'s `beside`, `besidePlacement`, `--buff-picker-h` tall). In Manual a chip's × keeps the focus in its row (`keepChipFocus`). The picker's note offers Undo after a form replaced another and after **Clear all**. The buffs that are on are kept in the character's profile, its spec's `buffs.on` (`app/build-spec.mts`; `PUT /api/profiles` checks them, one form at most, and the page heals a saved list on reading with `normalizeBuffs`, a later form replacing an earlier); the numbers they scale with are the character's, and an edit is the same `buffs.skills` entry Manual edits (`editBuffInputs`); both modes save them at once through `setCharacterBuffs` (`ui/profiles.mts`), which gives a character with no saved settings the ones the panel shows it, and a by-name lookup never reaches a prototype (`Object.hasOwn`, so a character named "constructor" works). No character's numbers are a view choice, ui-prefs `manualBuffSkills`, shared by Manual's and Automatic's No character. Manual's own list (`manualBuffs`) stays apart: it is one list, not one per character, and a step in Manual's undo history. Each requirement a buff touches says what gear still has to supply (`gearNeedsText`: "Gear needs 35: Divine Fury gives 10", "Gear needs 75 of an 80 cap: Magic Reflection −15, Magic Reflection cap −5", "Gear needs its full 65 cap: Divine Fury takes 20"; the cap is named only when a buff changed it and it is above 0), and a resist override the plan set aside says so ("Fire 95 override ignored: Reaper Form's −25 is counted", `overrideNote`). The build sends the planned profile (docs/solver.md, Buffs: the shares, the stat caps and the set-aside overrides), and the run's settings carry `buffs` (`runBuffs`: the ids and the inputs' values; the server refuses a bad one with `isRunBuffs`), so its automatic label and the compare view's Settings row name a change ("+Divine Fury", "Chivalry 105 → 120", `buffsDiff`) and "Load these settings" turns them back on and restores the numbers the run used (`loadRunBuffs`); a run saved before buffs has none, and an old list with two forms is healed (`savedBuffs`). The result's headline reads **Planned with** and a badge per buff, then **Show without buffs** (`#b-buffs-shown`), a toggle button with one label and `aria-pressed` (as `#map-labels` is), its tooltip saying the totals are redrawn and nothing is searched again; it redraws the tiles, What changes and the "N requirements not met" count without them (with buffs planned the count is taken from the totals shown). The totals are drawn with `withBuffs` against the caps they leave; what they add past the cap is a line under that property's gauge in What changes ("+82 past the cap (Enemy of One)", a penalty applied after the cap "−2 after the cap (Protection)", `pastCapNotes`), and a potion or an Enchant gets a sentence each ("Greater Agility potion is worked out from the suit <name> wears now (its Enhance Potions)"). The runs drawer's badges and the compare view count each run's own buffs, and the drawer adds "with Divine Fury" / "with 3 buffs"; a compare column's long run name is cut with its whole name as the tooltip, so the verdict badge stays in view.

**Manual mode** (`ui/builder-manual.mts`, issue #12). An **Automatic | Manual** segmented control (`#b-mode`) sits in the top bar after the template; Manual puts `manual` on `#tab-builder`, which hides the Settings drawer, its button, Build and the results, and shows `#b-manual`: the totals strip, the slot cards and, beside them, the hint or the picker. The Saved runs button stays in Manual; opening or comparing a run from its drawer switches to Automatic, where runs are shown, and the compare view closes on the way into Manual. The character select's first option, **No character** (raw item totals), is Manual's in both modes (above); with a character, the totals take its Resisting Spells minimum (said in the strip's note) and race caps and the panel's resist caps, through `effectiveProfile` and `profileResistCaps` as a result does. The mode (`builderMode`), the No character choice (`manualFor`) and the suit (`manualSuit`, a serial per slot) are ui-prefs fields (the server takes only `GEAR_SLOTS` as `manualSuit` keys); a load or a scan reload resolves the serials again (`resolveItems`), and the screen is not drawn until they have, so a piece never flashes up as missing. A serial that no longer resolves is a **missing** card with Clear, and the suit card's subtitle counts them.
- **Totals strip.** One compact row (`.mb-totals-row`, a flex row that wraps, left-aligned, rather than ever scrolling the screen sideways): the five resists, then LRC, LMC, FC, FCR, SSI, DCI, HCI and DI against the shard's caps, then STR, DEX and INT uncapped, each "value / cap" with no meter. A total at its cap reads in the ok tone; past it, it shows the cap and "+N" in the warn tone (`manual-model.mts`'s `capped`); the fuller line ("+9 wasted", "23 to cap", "Nothing yet", `capLine`, with a resist cap's override) is each total's tooltip and, for a screen reader, part of its text.
- **Slot cards.** Every slot the classifier knows, `vault-lib.mts`'s `GEAR_SLOTS` (the values of `LAYER_TO_SLOT`, nineteen, one per paperdoll layer (issue #202), outerLegs being the kilt or skirt worn over pants or armor legs; both solvers search all of them), in `manual-model.mts`'s `MANUAL_GROUPS`: two columns, armor (head, neck, chest, arms, hands, legs, kilt / skirt, feet) over weapons, and clothing (shirt, tunic, robe, waist, cloak) over jewelry (ring, bracelet, earrings, talisman); a `[fast]` test holds the groups to `GEAR_SLOTS` exactly and in its order, which every slot list on the page follows (the result's Plan, compare, the Locked slots chip). The cards are tight enough that all nineteen sit beside the open picker at 1440 × 900. The hand rule is the only rule between slots: every other paperdoll layer holds its own piece in the game, so a shirt, chest armor, a tunic and a robe are worn together, and a kilt over leggings. A saved suit or an opened run holding a piece the classifier has since moved (a kilt saved under legs) shows it in its slot now (`reslotted`), unless that slot holds a piece of its own; then a toast says so ("Kilt moved to Kilt / Skirt; Fancy Kilt kept there.") and the piece leaves the suit. A card is a compact two-line `<button>` (`.mb-slot-pick`, `aria-expanded` and `aria-controls="mb-picker"`): the slot and the piece's name in its rarity's color, then its key properties (`builder-result.mts`'s `keyProps`); where it lives is in its item tooltip; Clear is a separate icon button over its top-right corner. The selected slot has the accent edge. The suit card's head has Undo and Redo, **Start from what <name> wears** (with a character; confirms before replacing a suit) and **Clear all** (confirms); its slot count reads "4 / 19" (in full for a screen reader and on hover) and gives way (ellipsis) before a button wraps. Undoing the last step from its button moves the focus to Redo (and back), else to the card's heading.
- **Undo and redo** (`manual-model.mts`'s `record`, `undoStep`, `redoStep`): every change to the suit is one step (a pick with the hand rule's clear, a Clear, Clear all, Start from what <name> wears, a buff turned on or off), 40 kept in memory (a reload starts afresh; another character keeps them, the suit being shared), a new change after an undo dropping the redo branch. ⌘Z / ⇧⌘Z on a Mac, Ctrl+Z / Ctrl+Y / Ctrl+Shift+Z elsewhere (`historyKey`), only while Manual is on screen, never from an input, textarea, select or anything editable (the search keeps its own undo), and not behind a dialog, a popover or a drawer. The page takes the key with `preventDefault`, which also keeps the desktop app's default Edit › Undo (Electron's default menu: the app sets none) from acting on it, since Chromium gives a key to the page before the menu. The Undo and Redo buttons say what they would do and the key ("Undo: Ring → Arcane Ring (⌘Z)"), disabled with "Nothing to undo" otherwise; after one, the status line (or a toast with the picker closed) says "Undid: Ring → Arcane Ring". The slot state classes are `mb-empty`, `mb-missing` and `mb-sel`: the old shared `.empty` class in `styles.css` would pad the card.
- **Fill the rest automatically and Save as run** (a row under the suit card's head, `.mb-suit-acts`, so the head keeps to one line). **Fill the rest automatically** (`#mb-fill`, primary) runs the search for the empty slots only (`POST /api/optimize` with `pinned`, Manual's suit; docs/solver.md, "Manual's pinned pieces"): every placed piece stays, and the Automatic panel's requirements, weights, pool settings and resist caps plan the rest with the buffs Manual's totals count (none with Count buffs off); a placed piece counts like any searched one, so a sash's LRC lowers the LRC the search looks for. The panel's locked slots play no part: the placed pieces are the lock. With No character it plans on the raw totals Manual shows (the panel's requirements and weights against the shard's caps: no Resisting Spells, race caps, cap overrides or stat headroom) from the pieces nobody wears plus the placed ones. While it runs the row holds a busy dot, the phase in words (`builder.mts`'s `progressText`, which the build's progress card reads too), a bar and **Cancel** (`#mb-fill-cancel`, which takes the focus and keeps it through a redraw); then the found pieces go into the slots that were empty when it started, never a placed piece again, as one undo step ("Fill the rest: 4 slots"), and the row says the outcome: "Filled 4 slots · best for the empty slots" (a proof, which holds for the empty slots only), else the result's verdict in lower case, or instead of either "short of SSI, DCI" (the strip's short labels) for the requirements the filled suit misses, in the warn tone; a polite live region (`#mb-live`) says it too. A fill lands only where it started (`manual-model.mts`'s `fillPicks`): another character or No character picked, or Open in Manual, cancels it at once, and a buff, the Count switch, the suit, or what it plans with (a requirement, weight, resist cap, pool setting or buff number) changed meanwhile drops its answer; the row then says why ("Fill canceled: the character changed", "…: the buffs changed", "…: the suit changed", "…: the settings changed"). The button is disabled with its reason while a build runs in Automatic, with missing pieces, with every searchable slot filled, or with no characters at all; Automatic's Build waits for a fill (and the fill for a build). A fill is never saved as a run. **Save as run** (`#mb-save-run`) saves the suit (`POST /api/runs`) in the character's Saved runs (No character's, with No character) with the panel's settings and the counted buffs; it is disabled with an empty suit or missing pieces, and a search knob typed out of range under Automatic's Advanced (which the run's settings would carry) is said in a toast that names the field, rather than saved.
- **Stats card.** Under the suit card, scrolling with it in the left column (`.mb-left`): the character sheet's Attributes and Pools and its Properties card with the skills, from `sheet.mts`'s `sheetParts` (which `sheetNode` composes, with the resist tiles, for the Characters screen and the result), for the manual suit; its resist tiles are left out, the totals strip having them. With a character, `before` is everything it wears, keyed by serial (a spellbook and a second legs piece included), so no worn piece is counted on the suit's side as an extra, and `statsOnly` skips the resist tiles, the worn gear card and the resist footnote, so its attributes are its own points plus the suit's bonuses, and `compare: false` draws only the suit's figures; with No character (`name` null) the figures are item totals, with no Attributes, Pools or skills. It redraws with every pick, clear and swap.
- **Fetch list** (`#mb-fetch`, under the stats card): the result's Fetch list (`builder-parts.mts`'s `fetchCard`) for the suit's pieces the character doesn't wear (`manual-model.mts`'s `fetchPieces`; every piece with No character), one row per container with Go to and Grab, and Grab all in its head (`grabAllButton`, the result headline's own); with No character Grab puts the pieces in the bridge character's backpack, and while no bridge is online it is disabled ("Log a character in to grab") and Grab all reads a plain disabled "Grab"; Go to always works. It is not drawn while every piece is worn.
- **The picker** is one item browser (`createItemBrowser`), mounted the first time a slot is opened and kept; a slot change sets the `fixed` object's `slot` (`slotQuery`: the slot itself, so `twoHanded` lists two-handed weapons and shields) and calls `setQuery`, so no second browser and no second set of document listeners is ever made. `persist: false`, `columns: ["tags"]`, the Inventory's row actions, and a **Change** column (`extraColumn`, `manual-model.mts`'s `slotDelta`): for the properties of the strip and those the profile has a floor or a weight on (`deltaKeys`), what the row would change if it replaced the slot's piece, as "LRC +20 → 77" with the capped new total, a gain in the ok tone and a loss in the bad tone, and "LMC +8 over cap", muted, for a change that lies wholly past the cap. A worn piece ("Worn by <name>", warn unless it is the chosen character's) and a gargoyle-only piece are tagged at the cell's start, since the Location column can be scrolled out of the picker. The piece in the slot reads "In this slot" and is marked selected through the browser's `detail.serial` hook (its `open` is always false: there is no detail panel). Activating a row (click or Enter) puts it in the slot and the picker stays on the slot; the one-hand/two-hand rule (`handConflict`, the optimizer's `optIsValidAssignment` rule: a two-handed weapon clears the one-handed slot and the other way round, a shield never does) clears the other slot, and `#mb-status` (a live region) says so. Every change of the suit refetches the rows so their deltas follow. Esc (from the screen, unless a popover, a drawer, a dialog or the search's own Esc takes it) and the close button close the picker and give the slot card the focus. Manual ignores `--page-max` and fills the content area (Automatic keeps it). With the picker closed the slot cards take the row beside the 360 px hint; with it open the picker takes about three fifths of the row (`flex: 3 1 0` against the cards' `2 1 0`, at least 480 px and 320 px), and the cards reflow into fewer columns (at least 160 px each). Below 1180 px the hint goes and the picker lies over the slot cards. - **Buffs** (`app/buffs.mts`, drawn by `ui/builder-buffs.mts`). The catalog is data: each entry (`BUFFS`) has an id, a name, its picker group (`BUFF_GROUPS`), the inputs it scales with (`BUFF_INPUTS`: skills by their scan name, plus Karma, Arcane Focus and Mastery level), an optional exclusive set (`form`: one form across Necromancy, Spellweaving, Mysticism and Ninjitsu; `enchant`), the skill it takes to cast, its effects as functions of those inputs (each on a real property key, `outside` for a bonus added after the cap, `slot` for a stat buff whose largest share counts), cap changes and the text-only parts. Each entry cites its ServUO file or shard wiki page; where they disagree the shard wiki's number counts and the other is said in the entry's note. An entry whose numbers are less sure carries `confidence` (medium or low; the picker marks it "unverified" with a tooltip), and one ServUO has but UO Alive may not (`unconfirmed`: the Eodon potions, Grapes of Wrath, the fish pies, the tinctures) is tagged "May not exist on UO Alive"; an unknown number (a tincture's size) is never invented, only said. The debuffs an enemy casts (Curse, Corpse Skin, Mind Rot) are their own group, folded until its show button or a search opens it. Racial passives (the Human's, the Gargoyle's and Gargoyle Berserk, by an HP-lost field) are off for another race. `applyBuffs(totals, caps, buffs, skills, stats)` is pure: it changes the caps first, adds the in-cap shares (a stat slot taking its largest share, the others listed in `beaten`), and keeps the past-cap shares in `outside`; `effective` is min(total, cap) + outside, and `shares` / `capShares` say which buff gave what. The totals card's **Buffs** row (`.bf-strip`) holds a removable chip per buff that is on (dashed while its numbers are planned: edited, or a skill the character lacks), **Add buff** and the **Count buffs in the totals** switch. Add buff opens the buff picker (`#mb-buffs`) in the side column in place of the slot picker (opening either closes the other; Esc closes it onto Add buff): a search over names, groups and effects, the entries by group with their numbers worked out from the character's skills (`buffSkillValues`; with No character every skill is 120), a number field per input in the group's head (edits are kept per character, and for No character, in ui-prefs `buffSkills`, and marked, with a reset; mastery level, Arcane Focus and karma are whole numbers), "Largest wins", "Stacks", "Outside cap" and "Cap +N" tags, and Clear all. Turning on a form that replaces another says so, with Undo. With the switch on, the totals strip, the stats card and every row's Change column count the buffs: a total they touch gets an accent marker line ("+10", "cap +5", "+82 past cap", or "+13%" of a stat with no character), with each buff's share on hover and for a screen reader, and a cap they raised is underlined; what they add past the cap to a property the strip doesn't show (Horrific Beast's HPR) is a line on the stats card. With the switch off, or no buffs, the stats card is exactly the suit's. Enchant reads the held weapon's Spell Channeling, a racial passive is off for another race, and with No character a percent stat share and a flat one in the same slot are both said, since which is larger depends on the base stat. The buffs that are on are ui-prefs `manualBuffs` (catalog ids, checked by the server with `isBuffList`), the switch `buffsCount`; turning one on or off is a step in the suit's undo history, whose steps hold the suit and its buffs.
