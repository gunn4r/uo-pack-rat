# Organize

Part of the UI docs: [`docs/ui.md`](../ui.md) has the hard rules, tokens, components and the dependency rules every screen follows.

The Organize screen (`#/organize`, issue #11) is two stacked cards at the page's width. Every decision and sentence on it comes from `ui/organize-model.mts` (no DOM, tested by `app/ui-organize.test.mts`); `ui/organize-data.mts` holds the page's copy of the setup (`state.organize`: the config from `GET /api/organize`, the problems its salvage reported, the blacklisted serials, the plan and the presets) and saves it whole with `PUT /api/organize`, dispatching `organizechange` on `document`; the Organize screen, the Containers view, the Scrolls view and the Items rows each listen for it and redraw.

- **Empty states.** No ground container scanned: say so. Nothing labeled: explain that Organize only touches labeled containers (so a friend's chest is never moved into) and offer Open Containers. Labels but no rules: the Rules card asks for one. A hand-edited `organize.json` the server salvaged shows what was dropped with **Save setup**, since no trip runs until the setup is saved as it now reads.
- **Rules card.** One row per rule in priority order (first match wins): a drag handle (`.org-grip`; ↑/↓ on the focused handle move the rule and a polite live region says where it went), the name with an Auto badge for strategy-made rules, a one-line summary of its filter (`matchSummary`, the Inventory's own token words), the target chain with each container's label color, fill meter and "61/125" (`targetChip`; a target in no scan keeps its label's name and reads "not in any scan"), the plan's counts (to move, in place, and no room as a warning badge) and a ⋯ menu (Edit…, Move up/down, Delete…). The row is a grid that drops the chain and counts under the name at 900 px of list width or less (a container query; a 1000 px window gets there even with the sidebar collapsed). Under the list, "Everything no rule takes" picks the catch-all from labeled, unpinned containers, and "Empty bags" picks where empty bags are gathered (issue #128), each with its counts.
- **Rule drawer** (`ui/rule-editor.mts`). Name; a preset to start from (`GET /api/organize/presets`; picking one replaces the names and the filter); "Name is any of" (one per line); Search, Kind pills and a rarity range; any other filter the rule carries (slot, weapon skills, property rules, yes/no properties, slayer, hidden and required tags, and the build a By build rule takes, "Build: Caster") as removable tokens; **Skip pieces of saved suits** (issue #133, `RuleMatch.skipSuits`: a piece of any saved Suit Builder run is left to the rules below, as the Undesirables presets have it); a live count, "Matches 12 items (e.g. …)", from `POST /api/organize/match` about 300 ms after typing pauses, with a note when rules above this one may claim some of them first; then the targets in fill order (↑/↓/× per container, "Add a container…" listing each labeled chest with the scanned bags inside it indented under it, never a pinned, blacklisted or unopened one). Picking an unlabeled bag labels it by its engraving or name when the rule is saved (`withTargetLabels`). The draft lives in the module, not the DOM, so a redraw keeps what was typed. The Inventory's filter strip has **Save as rule…**, which opens the drawer with the current item filters (`ruleQueryFrom`) and a note naming the location, character and seen filters it left out.
- **Auto organize drawer** (`ui/auto-organize.mts`, a wide drawer opened by **Auto organize…** in the Rules card's actions and in the no-labels empty state). Three sections: the strategy (a segmented Simple / Detailed / By build with one sentence each); the containers it may use (one checkbox per usable ground chest with its fill, under a "House N" heading when there are several houses; a chest the player's own labels or rules use starts unticked with a note saying why; the rest in a closed "can't be used" list with each reason); and the proposal (`POST /api/organize/propose`, worked out again 300 ms after a box is checked or cleared and at once on a strategy change; a headline, a line each for the items that have no room and the items no rule takes, which stay where they are (only when there are some), notes, then a table of groups with the chests each gets ("…, in a bag of its own" for a group given a bag in a shared chest, issue #132) and a Fits / Short / No container / No bag badge; the notes include what the full layout still needs, chests and the bags for each shared chest, when it needs any; Detailed with groups left over offers Try Simple instead). Accept saves the proposal's `config` whole with `saveConfig`. It is disabled, with its reason, while a proposal is being worked out, when nothing is checked, and when the proposal is the current setup; if the setup changed since the proposal was shown, Accept works it out again first.
- **Plan card.** Reports first: room shortfalls, items that belong at another house, the planner's warnings grouped by kind (containers named by label, timestamps as dates; a target nearly full after the plan among them), the empty bags in labeled containers (`emptyBagsNote`: how many, the first five by name and place, and how to gather them), what a stopped trip left in the backpack (with Put them away) and a trip's failed steps (each with Pin this item). Then the headline ("N items to move in M trips, about K minutes", from the planner's per-trip estimate, `tripSeconds` in `app/organize.mts`), Run trip N / Run all / Stop, and the trip list: one collapsed `<details>` per trip whose move table is built the first time it opens. A client whose bridge does not declare `trip` gets the plan and a sentence instead of Run buttons; offline or busy states disable the buttons with their reason (`tripGate`).
- **Running trips.** Run trip posts `{index, stamp}` to `POST /api/organize/trip` (a stale plan is fetched again, with a sentence). The page follows the trip on the `bridgestatus` event `ui/bridge.mts`'s poll dispatches with every status, and on a 5 s timer: a trip the bridge never picks up, or whose bridge stops answering, is given up after 95 s (just past the 90 s the server holds it), any trip after 15 minutes (`stepWatch`); a click while the trip is being queued queues nothing. When a trip reports back the plan is fetched again; Run all then runs the new plan's first trip, and stops on a stopped, partial or failed trip, or on a plan that did not get shorter. Stop posts `POST /api/bridge/stop`; the bridge halts after its current step. The Organize nav item shows a busy dot while a trip runs. `GET /api/organize/plan` also answers `running` (`{id, index, queuedAt, picked}`, the trip the server has queued and not heard back about, else null): a page that was reloaded mid-trip, or a second window, follows that trip from its queue time with the same rules, Stop included, and says so (`adoptWatch`, `resumedNote`); Run all is not resumed. A trip the page already stopped following (it reported back, or the page gave up on it) is not followed again.
- **Labels elsewhere.** Inventory › Containers has Highlight in game (issue #10: the bridge's highlight with the container itself as its target, gated like the item actions by `bridgeActionReason`) and Label… / Edit label… in each ground container's ⋯ menu (not for blacklisted ones: name, color, Pinned; pinning or removing a label that rules use says which rules lose it first) and a Fill column. Wherever the page prints an item's place (the Location column, the item peek and tooltip, grouped rows, the Suit Builder's plan and fetch list), `dom.mts`'s `whereText` reads a labeled container by its label (`labelledPlaces`).
